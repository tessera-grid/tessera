# Замер: Tessera против AG Grid Community на 100 000 строк

**Статус:** исследование, не решение. Находки уходят в работу через прожарку и ADR
([ADR 0001](../decisions/0001-spec-driven-development.md)).
**Дата:** 2026-11-09.
**Ревизия Tessera:** `master` после `ce3407bc` (ADR 0200, этап 4) с незакоммиченными шагами
этапа 5 (своя сборка модели ядра, серверная модель на движке).
**Вопрос автора:** проигрываем ли мы AG Grid из-за React и нужно ли идти к изменяемой модели
строк, как у AG Grid.

## Итог

- **Модель строк — не наше слабое место.** На смене данных Tessera быстрее AG Grid в 7–17 раз,
  если приложение отдаёт новый массив `data` (как принято в React), и в 2–5 раз — даже против
  транзакций AG Grid. Сортировка 100 000 строк на 25 % быстрее, монтирование 100 000×10 — в
  1,5 раза быстрее.
- **React — не причина отставаний.** На прокрутке Tessera делает **меньше** работы главного
  потока, чем AG Grid (на 20–40 %), но хуже распределяет её по кадрам: рендер идёт синхронно
  внутри события прокрутки, поэтому p95 задачи выше в 1,4–1,9 раза. Это наш выбор планирования
  (`flushSync` адаптера виртуализатора), а не цена React как такового.
- **Отставаний четыре, у всех — конкретная причина в нашем коде:**
  1. удаление строк после 8 смен `data` — 1,6 с против 0,6 с: сборка слоёного словаря
     `rowsById` через ловушки прокси (ошибка этапа 3 ADR 0200); **исправлено** (EN29) —
     теперь 156 мс против 759 мс у AG Grid;
  2. быстрый поиск — ×2,2: вызов функции поиска на каждую пару «строка × колонка»;
  3. p95 прокрутки 1000×1000 — ×1,4–1,9: синхронный рендер в событии прокрутки;
  4. монтирование 1000×1000 — ×1,6 по стене: одна длинная задача (180 мс) против нарезки
     работы у AG Grid (51 мс); всей работы почти поровну.
- **Разворачиваться к изменяемой модели AG Grid не нужно:** её выигрыш — в транзакциях без
  сравнения версий, а наш путь `data` и так быстрее. Четыре отставания закрываются точечно.

## Как мерили

- Стенд — Vitest browser mode, Chromium headless, prod-сборка React 19.3, **×4 CPU-троттлинг**
  на окне замера (команды перф-матрицы `perf.commands.ts`, ADR 0099). Серии вперемешку:
  Tessera, AG Grid, Tessera…; первый прогон — прогрев, в таблице медиана пяти.
- Одни и те же данные: 100 000 строк × 10 колонок (числа и строки вида `bravo 1`) и
  1000 × 1000; одна ширина колонок (120 px), область 1200 × 500 px.
- **Tessera:** `useCreateTable` с `columnSorting`, `quickSearch`, `rowSelection`; `DataGrid`.
  **AG Grid Community 36.3.0:** `AgGridReact` со всеми модулями Community, `getRowId`,
  выбор строк с флажками, сортировка в колонках, тема по умолчанию.
- Действие — через API таблицы (у обоих), конец — когда грид применил изменение (первая
  строка, данные узла) и прошло два кадра. Метрики: **стена** — время до отрисовки,
  **работа** — сумма задач главного потока в трассе, **длинная** — самая длинная задача.
- Прокрутка — со скоростью ниже порога быстрой прокрутки Tessera (600 px/с по вертикали,
  2000 px/с по горизонтали), 120 кадров; p95 задачи и средний кадр. В headless кадры не
  привязаны к 60 Гц, поэтому средний кадр — для сравнения, а не как частота кадров.
- Стенд, AG Grid и результаты — во временных каталогах вне репозитория (`tmp/` в
  `.gitignore`, пакет — в каталоге сессии); в проект ничего не добавлено.

## Разбор отставаний

### 1. Удаление после 8 смен `data` — 1,6 с

CPU-профиль удаления в той же последовательности, что в стенде: 1,53 с из 1,55 с —
`handOverRowsById` → `flatten` ([rowsByIdHandover.ts](../../src/lib/core/rowsByIdHandover.ts)).
На восьмом слое словарь собирается заново через `Object.keys(proxy)` и чтения сквозь прокси:
на каждый из 100 000 ключей — ловушки `getOwnPropertyDescriptor` и `get` по всей цепочке слоёв
(`keysOf` 748 мс, `get` 486 мс). Отдельно, без цепочки, то же удаление — 43–112 мс.

**Исправлено** (2026-11-09, требование EN29 ADR 0200; позже слоёный словарь заменён
изменяемым хранилищем — EN30, и EN29 снят): словарь собирается по цепочке
напрямую — плоская основа и записи слоёв по порядку, без прокси; ключи слоя — из той же
сборки, чтения после неё — из плоского словаря. Удаление в стенде — 1620 → 156 мс. Это дефект
этапа 3, к выбору устройства словаря (EN26) отношения не имеет.

### 2. Быстрый поиск — ×2,2

Профиль: `quickSearchFilter` 228 мс, `getValue` 98 мс, `textsOf` 97 мс, `checkRow` 94 мс,
формат типа и разрешение типа ~90 мс, `getColumn` 30 мс. Стадия фильтра вызывает функцию
поиска на каждую пару «строка × колонка» (1 000 000 вызовов) и создаёт на строку объекты
`columnFilters` и `columnFiltersMeta`. AG Grid склеивает текст строки один раз (кэш на узел) и
проверяет его одним `includes`.

**Исправление:** склеенный текст строки по видимым колонкам — один кэш на строку и одна
проверка; колонки и форматтеры — разрешить один раз на проход, а не на ячейку.

### 3. p95 прокрутки — ×1,4–1,9 при меньшей работе

Работы у Tessera меньше, но она идёт одним куском внутри события прокрутки:
`EventDispatch` — 180–558 мс из всей работы. Адаптер TanStack Virtual для React по умолчанию
рендерит синхронно (`useFlushSync = true`,
[react-virtual/index.tsx](../../src/vendor/tanstack-virtual/react-virtual/index.tsx)), и React
отрисовывает строки окна прямо в обработчике. AG Grid обновляет строки в кадре анимации и
тратит больше на слои композитора.

**Гипотеза к проверке:** рендер окна в кадре анимации, а не в событии (`useFlushSync: false`
или своя постановка в `requestAnimationFrame`), снизит p95. Цена — возможный кадр с пустым
местом у края окна; её нужно мерить вместе со скелетами быстрой прокрутки (ADR 0008).

**Итог (2026-11-09):** чистый async — кадр −10–16 %, но пустые места при быстрой прокрутке и
прыжках; своя очередь колонок — хуже. Решение — полоса окна, как у Handsontable и MUI
([ADR 0202](../decisions/0202-window-band.md)): запас по ходу прокрутки, перерисовка по
исчерпанию, синхронно — только при непокрытом крае. 1000×1000 со всеми плагинами по
горизонтали: кадр 32,5 → 7,9 мс, длинных кадров 32 → 1 из 60.

### 4. Монтирование 1000 × 1000 — ×1,6 по стене

Всей работы почти поровну (Tessera 271 мс, AG Grid 233 мс), но AG Grid рисует строки
частями по кадрам (самая длинная задача 51 мс), а Tessera — одним проходом (180 мс). По
стене до первой строки AG Grid быстрее, по общей работе — нет.

**Направление:** нарезка первого рендера (сначала видимая часть, затем остальное окно) — по
результатам пункта 3, тот же механизм планирования.

**Итог (2026-11-09):** [ADR 0203](../decisions/0203-whole-window-in-row-portions.md) — первый
рендер переходом React, первое окно — переходом, строки — порциями. Самая длинная задача
монтирования 1000×1000: без плагинов 111 → 27 мс, со всеми плагинами 526 → 51–62 мс.

## Что это значит для ADR 0200

- Путь движка (строки неизменны, инкремент по пути изменения, прежняя модель неизменна) по
  замеру выигрывает у AG Grid именно там, где AG Grid силён: смена данных.
- EN26 (память словаря): по итогам замера автор выбрал изменяемое хранилище, как у AG Grid, с
  неизменными моделями версий (ADR 0200, этап 5, EN30–EN31); слоёный словарь и его сборка
  (пункт 1, EN29) сняты вместе со слоями.
- Критерий пересмотра §1 ADR 0200 (слой ячеек TanStack) по этим данным не срабатывает: цена —
  в планировании рендера, а не в объектах TanStack.

## Ограничения замера

- Одна машина (Windows, Chromium headless), ×4 троттлинг; числа — относительные.
- AG Grid — с настройками по умолчанию (анимация строк, тема Quartz); Tessera — с тремя
  плагинами. Наборы функций не тождественны: у Tessera, например, линии, вспышки и кнопки
  ячеек готовы, у AG Grid — свои слои и анимации.
- Действия — через API, а не события указателя; клавиатура и фильтры колонок не мерились.

### Быстрый поиск после профиля (2026-11-10)

Профиль первого поиска «bravo 1» на 100 000 × 10 (только Tessera, тот же стенд и данные, ×4 CPU):
из ~970 мс прохода 750 мс уходило на сборку склеенного текста строки — `row.getValue` TanStack на
каждую ячейку (поиск колонки по id и запись в кэш значений строки) и форматирование значения с
проверкой вариантов и типа. Правка — [ADR 0201](../decisions/0201-quick-search-joined-row-text.md),
§4а, QT11: значение функцией доступа колонки, форматтер колонки без типа — строка значения. Первый
поиск — 1,02–1,16 с → 0,47–0,57 с; AG Grid Community 36.3 на этом стенде в прошлых сериях — 0,44–0,46 с,
то есть отставание с ×2,5 сократилось примерно до ×1,1. AG Grid в этой серии не перемерялся.

### Флажок шапки «выбрать всё» (2026-11-10)

Профиль монтирования 100 000 × 10 и выбора строки: флажок шапки строил список строк охвата и
считал по нему выбор при монтировании и на каждый выбор — ~40 мс JS-работы под ×4 CPU. Правка —
[ADR 0179](../decisions/0179-select-all-scope.md), §6, SE17: состояние флажка по ключам выбора и до
первой невыбранной строки охвата. Стенд, только Tessera, прежний и новый код вперемешку, 12 замеров:
монтирование 369 → 320 мс, выбор строки 68 → 21 мс; AG Grid в прошлых сериях — 337 и 53 мс.
Остаётся отставание монтирования 1000 × 1000 — отрисовка React, 5–6 компонентов на ячейку.
