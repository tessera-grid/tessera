# Roadmap

Планируемое направление развития Tessera. Это **намерение**, а не обязательство.
Принятые решения фиксируются как [ADR](decisions/README.md).

Здесь же ведётся список **известных проблем** — признанных краёв (непокрытых тестами
или нереализованных пробелов), которые относятся к проектной работе, а не к дефектам.

## На рассмотрении

- **Миграция на TanStack Table v9.** Стратегическое лечение ключевого ограничения v8:
  любое изменение состояния таблицы или данных пересчитывает **всю** модель таблицы —
  это архитектурный удар по производительности. Pub-Sub
  ([ADR 0007](decisions/0007-reactivity-pubsub.md)) смягчает его на v8, но не
  устраняет. Миграция оценивается, решение ещё не принято.

## Запланировано

- **Полная поддержка сводных таблиц (pivot).** Первоклассный режим pivot, со **всеми
  существующими плагинами, адаптированными** к работе под ним.
- **Гибкий, настраиваемый внешний вид.** Развить тема-независимый слой CSS-переменных в
  по-настоящему настраиваемую визуальную систему.
- **Переход на последнюю версию dnd-kit для React.** Обновить DnD-фундамент
  ([ADR 0006](decisions/0006-dnd-with-dnd-kit.md)) до актуальной версии dnd-kit для
  React ради свежего API, исправлений и улучшений производительности.
- **Опыт разработчика (DX).** Постоянные улучшения DX по всему API и тулингу.
- **Тестирование сквозных (межплагинных) кейсов.** Проработать отдельный слой
  тестов на взаимодействие плагинов — то, что не принадлежит ни одному плагину в
  отдельности (например, выбор строк при их перетаскивании: выбор должен быть
  привязан к идентичности строки, а не к слоту). Оформить как отдельную
  спецификацию с собственным префиксом требований (сквозной ADR взаимодействий),
  выявить сложные кейсы — как поддерживаемые комбинации, так и заведомо
  несовместимые (тогда требование — «недоступно вместе»), — и покрыть их
  тестами в отдельных файлах `visual/`, переиспользуя общую механику (напр.
  DnD-хореографию из `rowDragging.dnd.ts`) и читая состояние из контракта DOM.
  Пересечение с текущим правилом «один тест = одно требование одного плагина»
  ([ADR 0009](decisions/0009-test-coverage-visual-and-performance.md)): его
  нужно расширить на межплагинные требования, не размывая однокомпонентные спеки.

## Известные проблемы

Признаны и относятся к greenfield — относитесь к ним как к проектной работе, а не к
дефектам, и не «чините» их походя (см. AGENTS.md §6 «Архитектурная дисциплина»).
Когда край закрыт или обнаружен новый — обновляйте этот список и соответствующий
`docs/architecture/*.md`, держа их синхронными.

- **Pub-Sub на масштабе** — fan-out не измерен на тысячах подписчиков.
- **Grouping + RowDragging** — не реализованы вместе (считается осуществимым).
- **Вложенные заголовки + ColumnPinning/Dragging** — другой путь раскладки (`grid`, без
  виртуализации колонок); не реализованы вместе.
- **Коллизия ключей `externalState`** — кастомные ключи `TState` вливаются в общий
  `table.getState()`; могут столкнуться с будущими полями TanStack.
- **`getRowId: row => row.id` захардкожен** — данные обязаны нести `id`.
- **Нет «снимка» инертных плагинов** — уровневый логгер (`logLevel`,
  [ADR 0022](decisions/0022-plugin-compatibility-contract.md)) даёт ленивый поток
  предупреждений по мере исполнения, но не сводит «какие плагины сейчас инертны и
  почему» одним взглядом. Осознанно отложено; при необходимости — отдельная
  потребность.
