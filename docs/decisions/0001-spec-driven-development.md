# 0001 — Spec-driven development: любая потребность начинается с ADR и списка требований

- **Статус:** Принято
- **Дата:** 2026-08-06
- **Связано:**
  - [ADR 0006](0006-dnd-with-dnd-kit.md) — образцовый ADR с явной таблицей требований
    (D1–D30), связанной с тестами; образец, который этот ADR делает нормой.
  - [visual-tests.md](../architecture/visual-tests.md) — нормативные правила покрытия;
    «одно требование = один ID = один тест» — нижняя половина того же цикла.

## Контекст

Реестр решений уже фиксирует _как_ устроена Tessera, а [ADR 0006](0006-dnd-with-dnd-kit.md)
и [visual-tests.md](../architecture/visual-tests.md) уже связали **требования** (`R<n>`)
с визуальными тестами один-к-одному. Но нигде не зафиксировано _само правило процесса_:
что любая потребность обязана **сначала** превратиться в спецификацию — нумерованный
список требований в ADR — и только потом в код. Без этого правила возможен обратный
порядок: сначала реализация, потом (может быть) документация и тесты «по факту», где
спецификация подгоняется под то, что уже написано.

Человек хочет закрепить обратную дисциплину: **разработка Tessera ведётся через
spec-driven development**. Спецификация — источник истины; код и тесты производны от неё,
а не наоборот. Это смыкает уже существующие половины (ADR как место решения, требования
как критерии приёмки, `R<n>`-тесты как доказательство) в один обязательный цикл.

## Решение

**Любая потребность — новый плагин, UI-компонент, фича, изменение поведения публичной
поверхности — сначала описывается как ADR с обязательным нумерованным списком требований,
и только затем реализуется.** Спецификация первична; реализация и тесты выводятся из неё.

Конкретно:

1. **Нет спецификации — нет реализации.** Работа над потребностью начинается с ADR в
   [`docs/decisions/`](.), а не с правки кода. Если задача выявляет потребность, ещё не
   покрытую ADR, — сперва пишется ADR (или расширяется существующий), затем код.

2. **Список требований обязателен.** Каждый такой ADR содержит секцию **«Требования»** —
   нумерованный список с устойчивыми ID `R<n>`. Требования нумеруются последовательно и
   **никогда не перенумеровываются**; изъятое требование помечается, а не переиспользует
   свой ID.

3. **Каждое требование — атомарно и проверяемо.** Одно требование описывает ровно один
   наблюдаемый факт о поведении грида, сформулированный так, что его можно доказать одним
   тестом. Требование, которое нельзя пометить единственным `R<n>`, — это два требования и
   должно быть разбито.

4. **Требования управляют тестами один-к-одному.** Каждое `R<n>` реализуется **ровно одним**
   визуальным тестом, названным по этому требованию с префиксом `R<n>:`, согласно
   [visual-tests.md](../architecture/visual-tests.md). Спецификация — чек-лист покрытия:
   плагин/компонент «покрыт», когда каждое его требование имеет соответствующий тест.
   Требование, ещё не покрытое тестом, явно помечается таковым в таблице требований (как это
   сделано в [ADR 0006](0006-dnd-with-dnd-kit.md) для вложенного переупорядочивания).

5. **Спецификация ведётся вместе с изменением.** Меняется поведение — сначала правится
   список требований в ADR, затем код и тесты приводятся к нему. ADR отменяется только
   новым ADR (согласно [decisions/README](README.md)); требование не «тихо перестаёт
   действовать» вслед за кодом.

6. **Процессные ADR — исключение по природе.** ADR, фиксирующие способ работы, а не
   потребность библиотеки (например [ADR 0002](0002-develop-on-master-human-owns-git.md) и
   этот), сами являются спецификацией процесса: их нормативные пункты играют роль требований,
   и таблица `R<n>`/тестов к ним не применяется.

## Последствия

- **+** Единый источник истины: поведение сначала утверждается как спецификация, а код и
  тесты доказуемо ей соответствуют. Обещание плагина honest by construction.
- **+** Диагностируемость: красный `R<n>`-тест называет точное сломанное требование, а сам
  `R<n>` — прямая ссылка на его определение в ADR.
- **+** Обозримость ревью: диффы поведения читаются как изменения списка требований, а не
  как археология по коду.
- **+** Смыкает уже существующие конвенции ([ADR 0006](0006-dnd-with-dnd-kit.md),
  [visual-tests.md](../architecture/visual-tests.md)) в один обязательный цикл вместо двух
  разрозненных практик.
- **−** Больше трения на входе: даже небольшая потребность требует ADR со списком требований
  прежде, чем будет написана первая строка кода. Это намеренная цена дисциплины, а не
  издержка, которую нужно оптимизировать обходом.
- **Уточняет** [visual-tests.md](../architecture/visual-tests.md): правило «одно требование =
  один ID = один тест» теперь имеет явный верхний конец — _откуда_ берётся требование (ADR),
  — а не только правило про тесты.
