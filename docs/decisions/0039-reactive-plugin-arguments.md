- **Статус:** Принято (фазы 1–4 реализованы)

## Контекст

Потребитель настраивает плагин аргументами фабрики: `rowSelection({ selectedCount })`,
`columnSorting({ server, multiSort })`, `rowExpanding({ maxDepth })`. Сейчас реактивны
только `enabled`, бизнес-колбэки (`hooks`) и поле `liveOptions`. Всё, что фабрика
выводит из остальных аргументов, фиксируется на первом рендере. Смена значения потом
**молча игнорируется**: счётчик выбранных строк не появляется и не пропадает, порог
кебаба не меняется, ширина колонки действий остаётся прежней.

У заморозки две причины. Одна наша, одна upstream.

1. **Сборка по сигнатуре набора.** `useCreateTable` пересобирает записи плагинов,
   только когда меняется состав `id|enabled`. Так защищены инлайн-массивы
   `plugins: [...]`, у которых каждый рендер новые записи, и функции в опциях с
   нестабильной ссылкой, от которых зависят мемо row-моделей (DP2).
2. **TanStack Table v9 собирает фичи и атомы только в конструкторе.** `setOptions`
   сливает опции, но фичу не добавляет и не убирает. Поэтому плагин, добавленный в
   массив после монтирования, не подключается, а удалённый — не отключается.

При этом почти у каждого параметра есть законный сценарий смены на лету:

| Источник значения                 | Реальный случай                                                         |
| --------------------------------- | ----------------------------------------------------------------------- |
| Настройки пользователя            | панель «Настройки таблицы»: мультисортировка, счётчик выбранных строк   |
| Права и роль                      | права на правку и перетаскивание пришли или отозваны после монтирования |
| Режим экрана                      | переключатель «Режим редактирования»                                    |
| Окружение                         | узкий экран: кебаб всегда, узкая колонка действий                       |
| Данные и ответ сервера            | `rowCount`; предикат строки «можно раскрыть / править»                  |
| Асинхронные права и фича-флаги    | `[rowSelection(), canEdit && cellEditing()]` после ответа сервера       |
| Ленивая загрузка тяжёлых плагинов | экспорт в Excel подключается по первому клику                           |

### Как это решают другие библиотеки

- **Конфигурация по умолчанию реактивна у всех.** В AG Grid пропсы обновляемы, кроме
  явно помеченных Initial. MUI X Data Grid — обычные пропсы. LyteNyte Grid — поток
  данных React. TanStack применяет опции каждый рендер.
- **Исключения — явные.** AG Grid помечает Initial-свойства в справочнике; режим данных
  `rowModelType` — Initial, для смены грид пересоздаётся. LyteNyte выносит режим
  данных в отдельный объект-источник.
- **Начальное и текущее состояние разделены везде:** `initialState` читается один
  раз (AG Grid, MUI, TanStack), текущее — контролируемые модели или API.
- **Возможности после создания не добавляются:** модули AG Grid регистрируются до
  создания грида, нехватку ловят dev-валидации.
- **Согласование при сужении параметра не документирует никто.** Встречаются два
  подхода: «сохранять» (TanStack для сортировки игнорирует колонки без
  `getCanSort()`, но оставляет их в срезе; AG Grid не трогает состояние пользователя
  без явного значения) и «подрезать» (MUI снимает выбор со строк, ушедших из
  результата; отказ — флаг `keepNonExistentRowsSelected`, в issues — трения с
  контролируемым режимом).

## Решение

### 1. Живое по умолчанию (RX1–RX3)

Все аргументы фабрик плагинов реактивны: смена значения после монтирования
применяется без пересоздания таблицы. Это касается и значений, и функций.

- **Функции тоже живые.** Предикаты (`canSelectCell`, `canEdit`, `enable` у
  перетаскивания, `multiSort.event`) после смены действуют со следующего вызова.
  Стабильность ссылок — забота библиотеки: потребитель **не обязан** мемоизировать
  массив `plugins`, и инлайн-вызов фабрики не должен пересчитывать row-модели.
- **Сравнение по значению.** Новый объект с теми же значениями (`multiSort: { max: 3 }`
  каждый рендер) — не смена: ни пересчёта, ни согласования.
- **Цена предсказуема по классу воздействия** (§3): ни один класс не пересоздаёт
  таблицу целиком.

Граница «мемо/живо» из ADR 0028 (DP2) перестаёт быть заботой автора плагина: что
держать стабильным, решает ядро, а не выбор поля (`options` против `liveOptions`).

**Как это устроено.** Запись `definePlugin` несёт аргументы фабрики (`args`), их
ключ по значению (`argsKey`, функции входят только фактом наличия) и `configure` —
настройку `options`/`slots`/`actionMenu`/`setup` из аргументов. Ядро держит
`features` и сервисные колонки по составу набора, а настройку пересобирает при смене
ключа из вида аргументов, где функции — стабильные обёртки на последнюю версию.
Поле `liveOptions` удалено: его поглощает этот механизм. Записи, написанные
вручную, `args` не несут — их поля статичны на время состава.

### 2. Два явных исключения (RX4–RX7)

**Договор на время жизни таблицы.** Не меняется на лету, как Initial-свойства AG Grid:

- **Режим данных** — `server` у `columnSorting` и `pagination`, в будущем у фильтрации и
  Server-Side Row Model. Смена меняет то, что потребитель обязан класть в `data`, а
  для SSRM — саму модель данных. Смена после монтирования не применяется, ядро выдаёт
  dev-warn; для смены таблицу пересоздают (например, новым `key`).
- **Состав массива плагинов.** Плагин, добавленный после монтирования, не
  подключается: он инертен с причиной `'addedAfterMount'` и сопровождается dev-warn.
  Удалённый после монтирования ведёт себя как `enabled: false` и сопровождается
  dev-warn с советом держать его в наборе с `enabled: false`: его фича осталась в
  таблице, а v9 сливает новые опции с прежними, поэтому без выключения она работала
  бы со старыми опциями. Запись `definePlugin` ядро пересобирает с `enabled: false`
  («призрак» с причиной `'removedAfterMount'`); у записи, написанной вручную,
  нейтральных опций нет — остаётся только предупреждение. Переключение на лету —
  только через `enabled`.

  Плагин объявляет аргументы-договоры полем `lifetime` в `definePlugin`
  (`columnSorting` и `pagination` — `['server']`): ядро берёт их значение с момента
  монтирования.

**Начальные значения — семена состояния.** Задают стартовый срез, дальше им владеет
пользователь или контролируемый `state`. Их имя показывает, что это начальное
значение. Сейчас такой параметр один — `pagination({ pageSize })`, он переименовывается
в `initialPageSize`. Текущий размер страницы меняется через `state.pagination`.

### 4. Сужение не разрушает сохранённое состояние (RX8–RX13)

Когда новое значение сужает допустимое, сохранённое состояние **не переписывается**.
Все читатели работают с **эффективным состоянием** — «сохранённое ∩ допустимое»:
row-модель, отрисовка, производные (счётчик выбранных, копирование), публичные
геттеры. Вернули параметр — вернулось и прежнее состояние.

- **Контролируемый потребитель** не получает `on*Change` из-за сужения: его срез
  корректен по его правилам.
- **Перезапись — только явно**, самим потребителем через контролируемый `state` или
  сброс, как stateful-атрибуты AG Grid.
- **Исключение — смена смысла состояния.** Если параметр меняет не допустимость, а
  значение записей (`subRows`: каскадный выбор против поштучного), состояние
  сбрасывается. Такие параметры явно названы в требованиях.

Прецеденты в кодовой базе: гейт группировки (выбор и перетаскивание инертны, выбор не
стирается, ADR 0022) и `useControlledPinning` (показывается эффективный пиннинг,
внешний срез не переписывается).

**Как это устроено (слой эффективного состояния).** TanStack кэширует row-модели по
срезам состояния, общего сброса кэша нет, поэтому учитывать сужение только при чтении
нельзя: кэш не узнал бы о смене `maxDepth` или `max`. Плагин объявляет сужение
среза полем `narrow` в `definePlugin` — функцию «сохранённое → допустимое»
(`rowExpanding` — `expanded`, `columnSorting` — `sorting`, `columnPinning` —
`columnPinning`). Ядро (`core/effectiveState.ts`) хранит сохранённое значение само
(неконтролируемый срез) или берёт у потребителя (контролируемый) и передаёт TanStack
эффективное через `state`; мемо row-моделей видят изменившийся срез штатно. Пиннингом
ядро уже владело — для него слой только сужает значение. Сужение, которому нужны
строки, получает экземпляр таблицы только с текущими данными; иначе оно
откладывается на повторный рендер (не больше двух подряд, чтобы немемоизированные
`data` не зациклили рендер). Цена: неконтролируемые срезы под слоем становятся
внутренне контролируемыми — их смена перерисовывает компонент-хост `useCreateTable`,
как уже было для пиннинга.

**Предикаты и отрисовка.** Функции-аргументы — стабильные обёртки (§1), поэтому смена
функции модель не трогает. Но предикат, который проверяется при отрисовке ячейки
(`canSelectCell`, `canEdit`, `enable` у перетаскивания), без сигнала обновился бы
только при следующей перерисовке ячейки. Сигнал — **новая ссылка на функцию**, как у
MUI X и AG Grid: плагин перечисляет такие аргументы в `refreshOn`, ядро ведёт версию
отрисовки, и ячейки перерисовываются мимо мемоизации. Колбэки `on*` в `refreshOn` не
входят. Инлайн-предикат, новый на каждый рендер хоста, перерисовывает видимые ячейки
на каждый такой рендер — мемоизация предикатов нужна ради производительности, не ради
корректности.

### 5. Запрет идущего действия (RX14–RX16)

Если новое значение запрещает действие, которое идёт прямо сейчас (перетаскивание,
ресайз, правка), сессия действия **отменяется так, будто нажат Escape**. Разрешённое
действие продолжается.

Для правки ячейки отмена по запрету **не сохраняет** значение и **не теряет черновик
молча**. Как черновик отдаётся приложению и какие ещё бывают причины завершения
сессии — предмет отдельного ADR о сессиях действий.

## Границы

- **Сессии действий и причины завершения** (сохранено / отменено / запрещено /
  конфликт), хранение черновика правки в состоянии плагина, сохранение при потере
  фокуса — отдельный ADR.
- **Асинхронный контракт бизнес-колбэков** (`Promise`, ожидание, откат при отказе
  сервера) — отдельный ADR.
- **Автоматическое пересоздание таблицы** при смене договора или состава плагинов —
  не делается: библиотека предупреждает, пересоздаёт потребитель.
- **Публичный API эффективного состояния** (узнать, что скрыто сужением) — не в этом
  ADR; пока хватает dev-лога.

## Последствия

- **+** Поведение совпадает с ожиданием React-разработчика и с рынком: аргументы
  фабрик — живые пропсы.
- **+** Пользовательское состояние переживает кратковременные сужения (узкий экран,
  права ещё грузятся, мигание флага).
- **+** Условный массив плагинов перестаёт быть тихим багом: dev-warn и причина в
  снимке диагностики.
- **−** **Ломающее изменение:** `pagination({ pageSize })` → `initialPageSize`; режим
  данных после монтирования больше не «как-то работает», а явно игнорируется с
  предупреждением.
- **−** Каждый новый читатель состояния обязан брать эффективное состояние — иначе,
  например, экспорт выгрузит скрытое. Нужен единый шов в ядре.
- **−** Отладка «в `state` есть, на экране нет» — компенсируется dev-логом.
- **−** Растёт тестовая матрица: параметр × направление смены × идущее действие.

### Риски

| Риск                                            | Чем закрывается                                                        |
| ----------------------------------------------- | ---------------------------------------------------------------------- |
| Ложные срабатывания от новых объектов           | сравнение по значению (RX3)                                            |
| Upstream держит значение в мемо без зависимости | тест «сменили на лету → модель верна» на каждый параметр классов Б и В |
| Гонка параметра с асинхронной `data`            | режим данных — договор на время жизни (RX4)                            |
| Потеря данных пользователя                      | §4 и §5: состояние не стирается, черновик не теряется молча            |

## Требования

По конвенции ([ADR 0001](0001-spec-driven-development.md),
[ADR 0009](0009-test-coverage-visual-and-performance.md)) каждое требование — один
тест с префиксом ID.

**Механизм**

| ID  | Требование                                                                                                                                                                                        | Вид        |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------- |
| RX1 | Смена значения аргумента фабрики после монтирования применяется без пересоздания таблицы                                                                                                          | unit (DOM) |
| RX2 | Смена функции-аргумента после монтирования применяется со следующего вызова, а предикат отрисовки (`refreshOn`) — сразу; инлайн-массив `plugins` с теми же значениями не пересчитывает row-модели | unit (DOM) |
| RX3 | Новый объект-аргумент с теми же значениями не считается сменой: нет пересчёта модели и согласования                                                                                               | unit (DOM) |

**Исключения**

| ID  | Требование                                                                                                                                                             | Вид        |
| --- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------- |
| RX4 | Смена `server` у `columnSorting` или `pagination` после монтирования не применяется и сопровождается dev-warn                                                          | unit (DOM) |
| RX5 | Плагин, добавленный в массив после монтирования, инертен с причиной `'addedAfterMount'` и сопровождается dev-warn с его `id`                                           | unit (DOM) |
| RX6 | Удаление плагина из массива после монтирования выключает его как `enabled: false` (причина `'removedAfterMount'`) и сопровождается dev-warn с советом `enabled: false` | unit (DOM) |
| RX7 | `pagination({ initialPageSize })` задаёт стартовый размер; его смена после монтирования текущий размер не меняет                                                       | unit (DOM) |

**Сужение (эффективное состояние)**

| ID   | Требование                                                                                                                                     | Вид        |
| ---- | ---------------------------------------------------------------------------------------------------------------------------------------------- | ---------- |
| RX8  | `rowExpanding` `maxDepth` ↓: строки глубже предела показаны свёрнутыми, срез `expanded` не меняется; вернули значение — строки снова раскрыты  | visual     |
| RX9  | `columnSorting` `multiSort` выкл или `max` ↓: модель сортирует по первым N, срез `sorting` не меняется; вернули значение — порядок прежний     | unit       |
| RX10 | `columnPinning` `leafPinning` выкл: листья под группами показаны незакреплёнными, срез `columnPinning` не меняется; вернули — снова закреплены | unit (DOM) |
| RX11 | `cellSelection` `canSelectCell` сузился: невыбираемые ячейки не показаны выбранными и не попадают в копирование; срез не меняется              | visual     |
| RX12 | Сужение не вызывает `on*Change` у контролируемого потребителя                                                                                  | unit       |
| RX13 | `rowSelection` `subRows` сменился: выбор сбрасывается (смена смысла состояния)                                                                 | unit       |

**Идущее действие**

| ID   | Требование                                                                                                 | Вид    |
| ---- | ---------------------------------------------------------------------------------------------------------- | ------ |
| RX14 | Перетаскивание строки или колонки, запрещённое посреди действия, отменяется как по Escape                  | visual |

## План внедрения

- **Фаза 1 — механизм.** Живые аргументы фабрик, стабильность функций, сравнение по
  значению; пересмотр DP2/DP14 в ADR 0028 (RX1–RX3).
- **Фаза 2 — исключения.** Договор режима данных, состав массива плагинов,
  `initialPageSize` (RX4–RX7).
- **Фаза 3 — отображение и политика.** RX17–RX23.
- **Фаза 4 — сужение.** Единый шов эффективного состояния в ядре, случаи RX8–RX13.
- **Фаза 5 — идущее действие.** RX14–RX16 (отмена сессий; причины завершения — в
  ADR о сессиях).

Новые причины инертности в снимке диагностики: `'addedAfterMount'`,
`'removedAfterMount'`.
