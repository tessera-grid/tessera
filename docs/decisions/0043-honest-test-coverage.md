# 0043 — Честность покрытия: тест ловит то, что обещает требование

- **Статус:** Принято (реализовано)
- **Дата:** 2026-09-30
- **Связано:**
  - [ADR 0001](0001-spec-driven-development.md) — требования в ADR, код и тесты
    производны.
  - [ADR 0009](0009-test-coverage-visual-and-performance.md) — виды покрытия и «одно
    требование — один тест». Этот ADR его дополняет: 0009 говорит, **сколько и каких**
    тестов нужно, 0043 — **что тест обязан доказывать**.
  - [ADR 0021](0021-keyboard-navigation.md) (KN30),
    [ADR 0040](0040-action-sessions.md), [ADR 0041](0041-async-business-callbacks.md),
    [ADR 0042](0042-demo-story-smoke-tests.md) — где найдены пробелы, описанные ниже.

## Контекст

ADR 0009 считает тесты: у каждого требования есть тест с его ID, у каждого плагина —
визуальные, перформанс и модульные. Работа над ADR 0040–0041 показала, что этого мало:
все тесты были зелёными, а пользователь не мог открыть правку ячейки мышью. Разбор
нашёл пробелы, которые правило 0009 пропускает:

1. **Тест не падал без реализации.** SS1 закреплял ошибочное поведение (сохранение
   неизменённого значения); AS2 мог пройти, даже если защита не срабатывала, — фокус
   не был на ячейке.
2. **Тест проверял часть формулировки.** AS6 требует «`Enter` или кнопка» — проверялась
   только кнопка. SS4 проверял путь, которого у пользователя нет.
3. **Взаимодействие было ненастоящим.** Мгновенный `userEvent.click` не воспроизводит
   паузу между нажатием и отпусканием — гонка фокуса KN30 его не замечала. SS14
   покрывался только выдуманными событиями dnd-kit.
4. **Сочетания не проверялись.** KN30 жил только в паре «правка + клавиатурная
   навигация».
5. **Доступность — только у состояния по умолчанию.** axe у плагинов не видел ни
   контраста 4:1 у текста ожидания (нужно 4.5:1), ни `aria-expanded` у строк с ролью
   `table`: в тестах не было ни ожидающих ячеек, ни раскрываемых строк.
6. **Перф — только общей матрицей.** Цена нового состояния рендера (1500 ячеек в
   ожидании) не мерилась отдельно.
7. **Инварианты документации без тестов.** «`setup` — один раз на сигнатуру» записан в
   `docs/architecture`, но нарушается на каждом рендере: теста нет.
8. **Демо-истории без тестов.** Логика историй (сервер, журнал, данные) ломалась
   отдельно от библиотеки; модуль историй при импорте пересевал общий `faker` и менял
   данные чужих снимков.
9. **Тесты читали устройство, а не поведение.** Проверки формы внутреннего среза
   ломаются при рефакторинге и не доказывают, что пользователь что-то видит.
10. **Сверка «требование ↔ тест» держится на внимательности.** Нет проверки, что у
    каждого ID есть ровно один тест и что тест не ссылается на несуществующий ID.

## Решение

Требования TQ1–TQ10 обязательны для каждого нового требования и каждого багфикса с
момента принятия. Уже существующие тесты под TQ1–TQ9 не переписываются разом — они
приводятся к правилу, когда их трогают; расхождения TQ10 фиксируются базовым списком,
который только сокращается.

### 1. Тест должен падать без реализации (TQ1)

Новый тест показан **красным** до того, как он зелёный: на коде без изменения, или
мутацией реализации (снять защиту, вернуть старую ветку), или откатом фикса. Для
багфикса — обязательно на старом коде. В отчёте об изменении называется, что было
испорчено и какой тест упал. Тест, который не удалось сделать красным, не считается
покрытием: либо он проверяет не то, либо требование ничего не меняет.

### 2. Проверена вся формулировка (TQ2)

Каждая часть требования — перечисление, «и», «или», «без X» — проверена. «Без
колбэка отмены» проверяется так же явно, как «колбэк успеха вызван». Если одним тестом
всё не охватить — требование делится на два ID, а не проверяется частично.

### 3. Настоящее взаимодействие (TQ3)

Пользовательский путь — мышь, клавиатура, фокус, перетаскивание — проверяется хотя бы
одним визуальным тестом через **настоящие события браузера**: `userEvent`, Playwright
drag, `humanClick` там, где важен фокус (AGENTS.md, §4). Модульный тест на
синтезированных событиях upstream (dnd-kit, TanStack) допустим как дополнение для
недостижимых через интерфейс веток, но не как единственное покрытие пользовательского
пути.

### 4. Обязательные сочетания (TQ4)

Фича, чувствительная к одному из механизмов ниже, проверяется в каждом его режиме:

| Фича чувствительна к                | Обязательные прогоны                                         |
| ----------------------------------- | ------------------------------------------------------------ |
| фокусу (открывает редактор, меню)   | `enableKeyboardNavigation` вкл и выкл                        |
| монтированию строк или ячеек        | строка ушла из окна виртуализации и вернулась                |
| модели строк (индексы, порядок)     | со сменой страницы (пагинация) и с сортировкой               |
| роли грида (`aria-*` строк и ячеек) | роли `table`, `grid`, `treegrid` — те, в которых фича бывает |

Прогон может быть параметром одного теста требования (`for` по режимам), если
требование одно, — ID от этого не множится.

### 5. Доступность каждого нового визуального состояния (TQ5)

Новое визуальное состояние (ожидание, ошибка, «перетаскивается», «раскрыто в
ожидании»…) проходит axe без нарушений **с включённым `color-contrast`** в светлой и
тёмной темах, в каждой роли грида, где состояние возможно. Проверка по умолчанию у
плагина (PQ4, ADR 0036) этого не заменяет: она видит только начальное состояние.

### 6. Перф каждого нового состояния рендера (TQ6)

Состояние, которое добавляет DOM, стили или подписки ячейке или строке массово, имеет
перф-кейс: та же выборка с состоянием и без него, база пишется в дашборд рядом,
регресс-потолок ≈2× замера (как AS14). Общая матрица P1–P8 этого не заменяет:
состояние в ней не включено.

### 7. Инварианты документации покрыты или названы (TQ7)

Утверждение-гарантия в `docs/architecture/*` — «один раз», «никогда», «всегда», «не
перерисовывает», «не зовёт» — либо ссылается на требование с ID в ADR-владельце и на
его тест, либо внесено в roadmap «Известные проблемы» как непокрытое. Описание
«как устроено» остаётся в `docs/architecture`; обещание, на которое опирается код,
становится требованием.

### 8. Демо-истории с логикой и чистота модулей историй (TQ8)

История, у которой есть собственная логика — имитация сервера, журнал колбэков,
данные, которые держит демо, — получает дымовой визуальный тест на главный сценарий
(обобщает ADR 0042 на все группы историй). Модуль историй не делает побочных эффектов
при импорте: данные, сиды генераторов и таймеры создаются при рендере.

### 9. Тест читает поведение, а не устройство (TQ9)

Визуальные тесты и тесты историй проверяют DOM, `aria-*`, `data-*`, публичный API
таблицы и вызовы бизнес-колбэков. Форма внутренних срезов (`table.atoms`, поля
состояния плагина) проверяется только в модульных тестах модуля-владельца. Засев
состояния для перф-кейса допустим (его нельзя набрать через интерфейс за разумное
время), утверждение о нём — нет.

### 10. Автоматическая сверка «требование ↔ тест» (TQ10)

Скрипт `npm run check:requirements` входит в барьер (AGENTS.md, §4) после `typecheck`:

- собирает ID из таблиц требований принятых ADR (`| ID | Требование | … |`); строка с
  составным ID (`R6/R8/R10`, `AM15–AM19`) — ссылка на чужие требования и не считается;
- собирает ID из имён тестов (`test('<ID>: …')`); имя-шаблон `${c.id}: …` в цикле по
  кейсам даёт ID всех `id: '…'` своего файла;
- падает, если у ID нет теста, если у ID больше одного теста, если тест ссылается на
  ID, которого нет ни в одной таблице, или если один ID определён в нескольких ADR;
- расхождения, существующие на момент принятия, лежат в базовом списке скрипта с
  причиной; запись из списка, которая больше не расходится, тоже роняет скрипт — список
  только сокращается.

## Требования

| ID   | Требование                                                                                                                                                             | Проверка  |
| ---- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------- |
| TQ1  | Новый тест требования или багфикса показан красным без реализации (старый код, мутация, откат фикса); в отчёте названо, что испорчено и какой тест упал                | отчёт     |
| TQ2  | Каждая часть формулировки требования проверена; неохватываемое одним тестом требование делится на два ID                                                               | ревью     |
| TQ3  | Пользовательский путь проверен хотя бы одним визуальным тестом на настоящих событиях браузера; синтезированные события upstream не единственное покрытие               | ревью     |
| TQ4  | Фича, чувствительная к фокусу, монтированию, модели строк или роли грида, проверена во всех режимах таблицы §4                                                         | ревью     |
| TQ5  | Новое визуальное состояние проходит axe с `color-contrast` в обеих темах и в каждой роли грида, где оно возможно                                                       | тест фичи |
| TQ6  | Новое массовое состояние рендера имеет перф-кейс против базы без него; база в дашборде, регресс-потолок ≈2× замера                                                     | тест фичи |
| TQ7  | Гарантия в `docs/architecture` ссылается на требование и тест или записана в «Известные проблемы» как непокрытая                                                       | ревью     |
| TQ8  | История с собственной логикой имеет дымовой тест главного сценария; модуль историй не делает побочных эффектов при импорте                                             | тест фичи |
| TQ9  | Визуальные тесты и тесты историй не утверждают о форме внутренних срезов; это только в модульных тестах модуля-владельца                                               | ревью     |
| TQ10 | `check:requirements` в барьере: у каждого ID принятого ADR ровно один тест, у каждого ID-префикса теста есть требование; базовый список расхождений только сокращается | unit      |

**Проверка** — чем подтверждается само правило: «тест фичи» — требованием конкретной
фичи по TQ5/TQ6/TQ8, «unit» — модульным тестом самой сверки (TQ10), «ревью» и «отчёт» —
отчётом об изменении (AGENTS.md, §5), где для каждого нового требования названо, как
выполнены TQ1–TQ9. Сверка TQ10 не требует теста с ID для строк «тест фичи», «ревью» и
«отчёт».

## Отвергнутые альтернативы

- **Процент покрытия строк (Istanbul/V8).** Мерит исполненные строки, а не требования:
  SS1 и AS2 исполняли весь нужный код и были бы «покрыты» на 100%.
- **Инструмент мутационного тестирования (Stryker).** Новая зависимость, а прогон
  браузерного набора на каждую мутацию занимает часы. TQ1 — ручная мутация одного
  места, которое тест должен защищать, — даёт тот же сигнал на новом коде. К
  инструменту можно вернуться, если ручная мутация начнёт пропускать дефекты.
- **Переписать все существующие тесты сразу.** Сотни тестов, большая часть проверена
  годами прогонов; правило применяется при касании, а TQ10 сразу даёт общую картину.
- **Отдельный вид тестов «интеграционные».** Сочетания (TQ4) — режимы существующих
  визуальных тестов требования, а не новый вид: иначе один сценарий получил бы два ID.

## Последствия

- **+** Зелёный тест доказывает требование, а не исполнение кода: дефекты класса KN30,
  SS1, AS13 ловятся при написании теста, а не пользователем.
- **+** Сверка ID автоматическая: пропущенный или лишний тест виден в барьере.
- **+** Цена новых состояний — доступность и кадр — видна сразу, а не при следующей
  общей матрице.
- **−** Дороже каждое требование: красный прогон, режимы §4, axe и перф нового
  состояния. Это намеренная цена.
- **−** Часть правил проверяется ревью, а не машиной (TQ2–TQ4, TQ7, TQ9): их
  соблюдение держится на отчёте об изменении.
- **−** Базовый список TQ10 на старте может быть длинным: он показывает долг, а не
  создаёт его.

## План внедрения

- **Фаза 1 — правило** (реализовано). ADR 0009 ссылается на этот ADR; AGENTS.md §4 получает TQ1–TQ9
  кратко, §5 — пункт отчёта «как выполнены TQ1–TQ9».
- **Фаза 2 — сверка (TQ10)** (реализовано). Скрипт `check:requirements`
  (`scripts/check-requirements.mjs`, логика — `scripts/requirements.ts`), базовый список
  `scripts/requirements-baseline.json`, шаг 4 барьера в AGENTS.md. На старте в базе 137
  расхождений: 35 коллизий (префиксы `R` в ADR 0004 и 0010, `CR` в 0013 и 0029, `LP` в
  0011 и 0017; `AM22`–`AM23` в 0024 и 0035; `CP14`, `CP23`–`CP25` повторены в 0025),
  21 лишний тест (следствия коллизий и несколько модульных тестов под одним ID), 34
  требования без теста с их ID и 47 ID в тестах без таблицы требований (матрица
  темизации ADR 0018/0019 описана прозой).
- **Фаза 3 — долг TQ7** (реализовано). Гарантии `plugins-and-slots.md`,
  `reactivity.md` и `table-assembly.md` сверены с требованиями: покрытые помечены ID
  (PE, SS, SB, AM, RX), непокрытые — в roadmap «Известные проблемы». Одна гарантия
  нарушена: `setup` перезапускается на каждом рендере. Пять не закреплены тестом, две
  покрыты тестами без ID. Описания поведения upstream (однократные
  `constructTableAPIs`/`getInitialState` TanStack) — не гарантии Tessera и не
  сверяются.
