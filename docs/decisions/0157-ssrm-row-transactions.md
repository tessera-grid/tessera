## Контекст

Серверная модель (ADR 0138) обновляет данные двумя способами: `refreshRows` перезапрашивает
блоки окна, `setRowData` меняет загруженную строку. Новая запись или удалённая строка требуют
перезапроса: окно мигает свечением обновления, а приложение с потоком изменений с сервера
(push, WebSocket) вынуждено перезапрашивать окно на каждое событие. Для CRUD-приложения и
живых данных на миллионе строк этого мало.

### Как у других

- **AG Grid SSRM** — `applyServerSideTransaction({ route, add, addIndex, update, remove,
rowCount })`: без `addIndex` строки добавляются в конец загруженных; удаление действует
  только на строки в кэше, новый итог задаёт `rowCount`; `route` — ветка группы;
  `applyServerSideTransactionAsync` склеивает пачки за окно `asyncTransactionWaitMillis`
  (50 мс).
- **MUI X** — с серверным источником данных изменения отражают перезапросом источника.

## Решение

### 1. Транзакция

`table.applyRowTransaction({ add?, index?, update?, remove?, parentId?, rowCount? })` —
только в SSRM; `setRowData` остаётся для одной строки. Возвращает итог: `'applied'`,
`'refetch'` (добавление без места) или `'branchNotLoaded'`.

- **Добавление с `index`** — строки встают на это место списка без запроса, итог растёт
  на их число, индексы ниже сдвигаются.
- **Добавление без `index`** — порядок списка знает только сервер (сортировка, фильтр):
  грид тихо перезапрашивает окно, как `refreshRows()` без `purge`; строки на экране
  остаются до ответа.
- **Удаление** — по id; уходят загруженные строки, итог уменьшается. Незагруженные id
  игнорируются, если приложение не передало `rowCount`, — тогда итог задан им.
- **Обновление** — как `setRowData`, пачкой; незагруженные строки игнорируются.
- **`parentId`** — изменение в загруженной ветке ленивых детей или серверной группы. Числа
  и агрегаты строки-группы приложение обновляет её `update`. Ветка не загружена — итог
  `'branchNotLoaded'`, кэш не меняется.

### 2. Кэш блоков

Транзакция меняет список на месте: загруженные строки встают на новые места, блоки по
границам, кратным `blockSize`, собираются заново. Блок, собранный не целиком, держит
известные строки «запасными»: они видны, а запрос блока уходит, только когда окно дойдёт до
строки, которой нет. Запросы блоков с места изменения и дальше, ушедшие до транзакции,
отменяются — их ответ в прежних местах, в кэш он не попадает: ни дублей, ни пропусков.
Следующие запросы идут по сдвинутым смещениям, как их видит сервер, уже применивший
изменение. Блоки до места изменения не трогаются.

### 3. Что держится на месте

Позиция прокрутки и активная ячейка держат свою строку; активная ячейка на удалённой
строке переходит к соседней. Диапазоны выделения на индексах следуют за списком
(`rowListFollow`). Активная ячейка и прокрутка следуют тому же журналу смен списка: строку
они держат при любой его смене, в том числе при раскрытии ветки выше; у начала списка
прокрутка, как якорь прокрутки браузера, не держит. Правка удалённой строки отменяется с
причиной `unavailable` (ADR 0040). Выбор: удалённые id
выпадают из выбранных и из исключений `{ all, except }`, счётчик пересчитывается.

### 4. Вид

Строки ниже места изменения едут (ADR 0107), добавленная вспыхивает «пришла» (ADR 0056) —
и добавленная без места, когда придёт перезапрошенное окно. Удалённая сперва гаснет на своём
месте, затем строки ниже закрывают щель: иначе соседи наезжают на её призрак и удаления не
видно. Уход — нейтральный, без вспышки: красный в Tessera — отказ и ошибка (ADR 0134), а
удаление успешно. Вне окна — без движения; при уменьшенном движении — без анимации. Живая
область объявляет «Добавлено / удалено N строк».

### 5. Живые обновления

Транзакции одного кадра применяются вместе одной задачей после кадра: одна перерисовка,
одно объявление, — без опции задержки (как ответы ленивых детей, ADR 0066). В журнал смен
списка каждая пишет свою пачку: следующие за списком сдвигаются по ним по порядку.

### 6. Канал действий

Транзакция — действие канала `rowTransaction` (ADR 0125) с числами строк `add`, `update`,
`remove` и источником `api`.

## Границы

- **Клиентский режим** — метод есть, только когда подключён плагин `serverRowModel`: его
  несёт фича плагина, и тип таблицы знает о нём только с плагином. Плагин подключён, но
  выключен или без `getRows` — строки у приложения в `data`, вызов ничего не делает и
  предупреждает в dev; причина без `getRows` — `noGetRows` в `diagnose` (SD37). Метода в
  ядре нет: ради предупреждения он тянул бы API серверной модели в каждую таблицу.
- **Пересчёт агрегатов групп** — делает сервер; приложение передаёт строку-группу в
  `update`.
- **Отмена и повтор (undo/redo)** — «Пакетная правка» в roadmap.
- **Транзакция во время перезапроса окна** правит строки на экране; окно, которое придёт,
  несёт то, что вернул сервер, — правку, если он её уже применил.

## Отвергнутые альтернативы

- **Отдельные методы `insertRows` и `removeRows`.** Смешанное изменение — несколько вызовов
  и несколько кадров.
- **Без индекса — в конец загруженных строк, как в AG Grid.** В отсортированном списке
  строка встаёт не на своё место до следующего обновления.
- **Только с индексом.** Приложение без места новой записи не смогло бы её показать.
- **Опция задержки склейки, как `asyncTransactionWaitMillis`.** Склейка до кадра даёт
  одну перерисовку без лишней настройки.

## Последствия

- У SSRM появляется движение строк и вспышка прихода — как в клиентском режиме; строки едут
  и при раскрытии ветки.
- Активная ячейка и прокрутка SSRM держат свою строку при любой смене списка, а не только
  при транзакции.
- Двухфазный уход удалённой строки — в обоих режимах: в клиентском признак удаления — строки
  нет в источнике, строки фильтра и поиска в нём остаются (ADR 0107, RM32).

## Внедрение

Внедрено 2026-10-29.

- **Хранилище и дерево.** `BlockStore.applyEdits` ставит загруженные строки на новые места
  (`editedIndex`) и собирает блоки заново; неполный блок держит строки в `loose`, `covered`
  не запрашивает его, пока окно не дойдёт до пропуска; пришедший блок выбрасывает
  «запасной» дубль своей строки. `BlockTree.applyTransaction` удаляет по `id` в любых ветках,
  вставляет в ветку `parentId`, уносит ветки удалённых строк и пишет смены одной пачкой в
  журнал (`plugins/serverRowModel`).
- **Источник.** `applyRowTransaction` в `source.ts`: склейка задачей после кадра (запасной
  таймер 100 мс для фоновой вкладки), `refetch` без `index`, `branchNotLoaded`, канал
  `rowTransaction`, выбор (`dropRowsIn`), вспышка `arrived` — и у строк, добавленных без
  места, с приходом окна; одно объявление на пачку, конец перезапроса не перебивает его
  «загружено» (`markLoadAnnounced`).
- **Что держится на месте.** `followActiveCell` в плагине `keyboardNavigation` (фокус —
  без прокрутки, `tracking.quiet`), якорь прокрутки в `useRowVirtualizer` по журналу
  (`followIndex`).
- **Движение.** `RowMotion` в SSRM — по номеру раскладки, прежние места — `priorIndex`;
  удалённая строка гаснет до того, как строки закроют щель.
- **Попутно.** В SSRM флажок и `Space` выбирают строку и при пустом выборе: стоковый
  переключатель TanStack не находил строку в модели (SD50, ADR 0138).
- **Тесты.** Модульные `serverTransactions.dom` (RT1–RT7, RT10–RT11, RT13–RT14, SD50),
  визуальный `server-transactions` (RT8–RT9), перф RT12 — в `interaction`. TQ1: каждое
  требование роняет своя мутация (снята вставка, перезапрос, итог, `update`, отмена запроса,
  `covered`, проверка ветки, выбор, словарь, склейка, предупреждение, источник канала,
  `followActiveCell`, якорь, согласование правки, журнал, движение, фаза, вспышка).
- **Истории.** «Data loading/Server row model/Transactions»: `Playground` с потоком
  изменений, S1–S4 с гайдами и близнецами высокой контрастности; бюджет снимков — 950.
