# 0157 — Добавление и удаление строк в серверной модели без перезапроса

## Контекст

Серверная модель (ADR 0138) обновляет данные двумя способами: `refreshRows` перезапрашивает
блоки окна, `setRowData` меняет загруженную строку. Новая запись или удалённая строка требуют
перезапроса: окно мигает свечением обновления, а приложение с потоком изменений с сервера
(push, WebSocket) вынуждено перезапрашивать окно на каждое событие. Для CRUD-приложения и
живых данных на миллионе строк этого мало.

### Как у других

- **AG Grid SSRM** — `applyServerSideTransaction({ route, add, addIndex, update, remove,
rowCount })`: без `addIndex` строки добавляются в конец загруженных; удаление действует
  только на строки в кэше, новый итог задаёт `rowCount`; `route` — ветка группы;
  `applyServerSideTransactionAsync` склеивает пачки за окно `asyncTransactionWaitMillis`
  (50 мс).
- **MUI X** — с серверным источником данных изменения отражают перезапросом источника.

## Решение

### 1. Транзакция

`table.applyRowTransaction({ add?, index?, update?, remove?, parentId?, rowCount? })` —
только в SSRM; `setRowData` остаётся для одной строки. Возвращает итог: `'applied'`,
`'refetch'` (добавление без места) или `'branchNotLoaded'`.

- **Добавление с `index`** — строки встают на это место списка без запроса, итог растёт
  на их число, индексы ниже сдвигаются.
- **Добавление без `index`** — порядок списка знает только сервер (сортировка, фильтр):
  грид тихо перезапрашивает окно, как `refreshRows()` без `purge`; строки на экране
  остаются до ответа.
- **Удаление** — по id; уходят загруженные строки, итог уменьшается. Незагруженные id
  игнорируются, если приложение не передало `rowCount`, — тогда итог задан им.
- **Обновление** — как `setRowData`, пачкой; незагруженные строки игнорируются.
- **`parentId`** — изменение в загруженной ветке ленивых детей или серверной группы. Числа
  и агрегаты строки-группы приложение обновляет её `update`. Ветка не загружена — итог
  `'branchNotLoaded'`, кэш не меняется.

### 2. Кэш блоков

Транзакция меняет список на месте: загруженные блоки после места изменения сдвигаются
вместе со строками. Блок, запрошенный до транзакции и пришедший после, сверяется по id —
ни дублей, ни пропусков; следующие запросы идут по сдвинутым смещениям, как их видит
сервер, уже применивший изменение.

### 3. Что держится на месте

Позиция прокрутки и активная ячейка держат свою строку; активная ячейка на удалённой
строке переходит к соседней. Диапазоны выделения на индексах следуют за списком
(`rowListFollow`). Правка удалённой строки отменяется с причиной. Выбор: удалённые id
выпадают из выбранных и из исключений `{ all, except }`, счётчик пересчитывается.

### 4. Вид

Строки ниже места изменения едут (ADR 0107), добавленная вспыхивает «пришла» (ADR 0056),
удалённая уходит призраком. Вне окна — без движения; при уменьшенном движении — без
анимации. Живая область объявляет «Добавлено / удалено N строк».

### 5. Живые обновления

Транзакции одного кадра склеиваются в одно изменение списка: одна сборка, одна
перерисовка, одно объявление, — без опции задержки (как ответы ленивых детей, ADR 0066).

### 6. Канал действий

Транзакция — действие канала `rowTransaction` (ADR 0125) с числами строк `add`, `update`,
`remove` и источником `api`.

## Границы

- **Клиентский режим** — метод инертен с причиной: `data` у приложения, и оно меняет её
  само.
- **Пересчёт агрегатов групп** — делает сервер; приложение передаёт строку-группу в
  `update`.
- **Отмена и повтор (undo/redo)** — «Пакетная правка» в roadmap.

## Отвергнутые альтернативы

- **Отдельные методы `insertRows` и `removeRows`.** Смешанное изменение — несколько вызовов
  и несколько кадров.
- **Без индекса — в конец загруженных строк, как в AG Grid.** В отсортированном списке
  строка встаёт не на своё место до следующего обновления.
- **Только с индексом.** Приложение без места новой записи не смогло бы её показать.
- **Опция задержки склейки, как `asyncTransactionWaitMillis`.** Склейка до кадра даёт
  одну перерисовку без лишней настройки.

## Последствия

- У SSRM появляется движение строк и вспышка прихода — как в клиентском режиме.
- Смещения блоков после транзакции расходятся с границами, кратными `blockSize`: блок
  кэша хранит своё начало.
