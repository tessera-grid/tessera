## Контекст

В CRM сужают по дате чаще, чем по любому другому типу: «созданы за период», «сделки
после такого-то числа», «обновлены сегодня». Первый срез ([ADR 0045](0045-filtering.md))
отложил даты в свой ADR, потому что у них свои развилки: как пользователь вводит дату,
в каком виде дата приходит в ячейке и где проходит граница суток.

Опоры в репозитории нет: в Base UI нет календаря, в библиотеке нет ни `Intl`, ни понятия
локали дат. Граница суток — главная ловушка: один и тот же момент `2026-10-03T22:30Z` в
Лондоне — 3 октября, в Москве — уже 4-е. Если сутки считать в поясе браузера, фильтр
«в день 3 октября» даёт разным сотрудникам разные выборки и расходится с сервером.

## Решение

### 1. Тип фильтра (DF1)

Тот же плагин `columnFiltering`, два новых типа в `columnDef.filter`:

```ts
{ accessorKey: 'birthDate', header: 'Birth date', filter: 'date' }
{ accessorKey: 'createdAt', header: 'Created', filter: 'datetime' }
{ accessorKey: 'closedAt', header: 'Closed', filter: { type: 'datetime', parse: v => … } }
```

- **`date`** — календарный день без времени.
- **`datetime`** — момент времени.

Кнопка в заголовке, пункт кебаба, сводка «Фильтры», «показано N из M», заглушка пустого
результата и серверный режим — как у остальных типов ([ADR 0045](0045-filtering.md),
§4–§10).

### 2. Значение ячейки (DF2–DF3)

- Принимаются `Date`, число миллисекунд и строка ISO 8601.
- **`'YYYY-MM-DD'` — календарный день**, к которому пояс не применяется. Встроенный
  `new Date('2026-10-03')` разбирает такую строку как полночь UTC и сдвигает день — этот
  разбор не используется.
- ISO с временем без смещения (`'2026-10-03T14:30'`) — время на стенных часах пояса
  `timeZone` (§4); со смещением или `Z` — точный момент.
- Свой формат — функция `parse(value) => Date | string | number | null` в объектной
  форме `filter`; её результат проходит тот же разбор.
- Значение, которое не разбирается (и `null`, `undefined`, `''`), **пустое**: проходит
  «пусто», не проходит остальные условия.
- Разобранное значение кэшируется на строку и колонку и сбрасывается при смене `data`:
  фильтр на 1000×1000 не разбирает даты на каждое применение.

### 3. Условия (DF4–DF7)

| Условие          | `date`                       | `datetime`                                           |
| ---------------- | ---------------------------- | ---------------------------------------------------- |
| в день           | тот же календарный день      | тот же календарный день в поясе `timeZone`           |
| до / после       | строго раньше / позже дня    | строго раньше / позже минуты (секунды отбрасываются) |
| между            | дни включительно             | минуты включительно                                  |
| пресет           | см. ниже                     | см. ниже — по календарным дням в поясе `timeZone`    |
| пусто / не пусто | значение пустое (§2) или нет | то же                                                |

По умолчанию — «в день». У «между» пустая граница — открытый интервал, как у числа.

**Пресеты** — «сегодня», «вчера», «последние 7 дней», «последние 30 дней», «этот месяц»,
«этот год». «Последние N дней» — сегодня и N − 1 предыдущих. Пресет хранится в состоянии
как пресет, а не как даты: фильтр «сегодня», сохранённый вчера, сегодня отбирает
сегодняшние строки. «Сегодня» берётся в момент применения фильтра; грид не
перефильтровывает сам в полночь (§ «Границы»).

**Значение в срезе** `columnFilters` — сериализуемое, без `Date`:

```ts
type DateFilter =
  | { operator: 'on' | 'before' | 'after'; value: string } // 'YYYY-MM-DD' | 'YYYY-MM-DDTHH:mm'
  | { operator: 'between'; value: [string | null, string | null] }
  | {
      operator: 'preset'
      value:
        | 'today'
        | 'yesterday'
        | 'last7Days'
        | 'last30Days'
        | 'thisMonth'
        | 'thisYear'
    }
  | { operator: 'empty' }
  | { operator: 'notEmpty' }
```

У `date` и у «в день» значение — `'YYYY-MM-DD'`; у «до», «после», «между» колонки
`datetime` — `'YYYY-MM-DDTHH:mm'`, стенное время пояса `timeZone`.

### 4. Часовой пояс (DF8)

```ts
columnFiltering({
  timeZone?: string,   // IANA ('Europe/Moscow') или 'UTC'; по умолчанию — пояс браузера
  dateLocale?: Locale, // § 5
  …
})
```

Сутки, «сегодня», пресеты и стенное время значений `datetime` считаются в `timeZone`.
Задайте пояс, когда пользователи сидят в разных поясах или фильтрует сервер: тогда
выборка одинакова на любой машине и совпадает с серверной. Аргумент живой
([ADR 0039](0039-reactive-plugin-arguments.md)): смена пояса пересчитывает фильтр. На
`date` пояс не влияет (§2).

### 5. Поповер и календарь (DF9–DF15)

- **Календарь — `@daypicker/react` v10** (`react-day-picker` под рекомендуемым с v10
  именем; тянет `date-fns` 4 и `@date-fns/tz`). Решение автора: готовый доступный
  календарь вместо своего и вместо нативного `<input type="date">`, вид которого
  тема не стилизует. Зависимость бандлится в `dist`
  ([ADR 0003](0003-formalize-tech-stack.md)); ставится отдельным одобрением при
  реализации.
- Поповер: выбор условия, пресеты списком, календарь (`mode="single"` или `"range"` у
  «между»), «Сбросить». Месяц и год переключаются выпадающими списками в заголовке
  календаря (`captionLayout="dropdown"`) — к дальним датам не листают помесячно.
- У `datetime` под календарём — поле времени (`<input type="time">`) для «до», «после»,
  «между»; у «в день» и пресетов поля нет.
- **Применение:** выбор дня, диапазона, пресета, условия — сразу; поле времени — через
  `debounceMs`, как текстовый ввод.
- **Клавиатура** — календаря: стрелки по дням, `PageUp`/`PageDown` по месяцам,
  `Home`/`End` по неделе; `Escape` закрывает поповер и возвращает фокус на кнопку (FL11).
- **Тема:** стили `@daypicker/react/style.css` не подключаются; классы календаря
  (`classNames`) — CSS-модуль на токенах `--tsr-comp-*`, обе темы, движение через
  токены. Стрелки навигации — из `icons`.
- **Ленивый модуль:** календарь (и `date-fns`) грузится при первом открытии фильтра даты,
  до этого — плейсхолдер в поповере. Грид без колонок дат его не загружает.
- **Локализация:**
  - подписи (условия, пресеты, «время», сброс) — из `localization`;
  - названия месяцев и дней, первый день недели — из `dateLocale`: объект `Locale`
    `date-fns` (приложение берёт его из `date-fns/locale` или
    `@daypicker/react/locale`); по умолчанию `en-US`.

### 6. Сводка, поиск, экспорт, сервер (DF16–DF20)

- **Сводка «Фильтры»** и доступное имя кнопки называют дату через
  `Intl.DateTimeFormat` с локалью `dateLocale.code` и поясом `timeZone`; пресет —
  своей подписью («Сегодня»).
- **Быстрый поиск** колонки `date` и `datetime` не обходит: «10» находило бы совпадения
  внутри ISO-строк.
- **Экспорт `view`** учитывает фильтр дат, как остальные фильтры (EX10).
- **Серверный режим:** `onFilterChange` получает срез как есть — ISO-строки и пресеты
  без раскрытия в даты. Пояс сервер берёт у приложения: оно само задало `timeZone`.

## Границы

- **Ввод даты с клавиатуры текстом** (маска «дд.мм.гггг») — не входит; календарь
  проходит WCAG 2.1.1 своей клавиатурой.
- **Произвольное «последние N дней/недель/месяцев»** — не входит; набор пресетов
  фиксирован.
- **Точность до секунд** у `datetime` — не входит.
- **Перефильтрация в полночь** по пресетам — не входит: «сегодня» обновится при
  следующем применении или смене данных.
- **Форматирование самих ячеек** — дело приложения (`cell` колонки); грид даты в
  ячейках не форматирует.
- **Справочник и селект** — третий срез ([ADR 0045](0045-filtering.md), «Границы»).

## Последствия

- **+** Самый частый фильтр CRM; одна выборка для всех поясов и для сервера.
- **+** Пресеты не устаревают: сохранённый «этот месяц» остаётся этим месяцем.
- **+** Доступный календарь без своей реализации сетки дней.
- **−** Новая зависимость (`@daypicker/react` + `date-fns` + `@date-fns/tz`) в `dist`;
  вес снижается ленивым модулем и не попадает в другие плагины (`check:tree-shaking`).
- **−** Стилизация календаря по классам `@daypicker/react` — связка с его разметкой,
  мажорный апгрейд может её сломать (ловят визуальные тесты DF13).
- **−** Расширение публичного API: типы `date` / `datetime`, `parse`, аргументы
  `timeZone` / `dateLocale`, ключи локализации и иконки.
- **−** Разбор дат на 1000×1000 может не уложиться в INP — тогда `knownShortfall` с
  регресс-потолком, как FL36.
