# 0240 — Кэш числового форматирования холодного поиска

- **Статус:** Принято.
- **Дата:** 2026-11-25
- **Слой:** плагин `quickSearchModel` — кэш форматирования чисел при построении поискового текста строки.
- **Связано:** [ADR 0201](0201-quick-search-joined-row-text.md), [ADR 0234](0234-filter-tree-and-optional-acceleration.md).

## Контекст

При первом поиске грид читает значения, форматирует их для отображения и
склеивает текст строки. На FL35 с 126 668 узлами Chromium ×4 диагностический
повтор по блокам из 2048 строк дал следующие медианы в миллисекундах.

| Колонки FL35                        | Чтение | Форматирование | Склейка | Нижний регистр и проверка |
| ----------------------------------- | -----: | -------------: | ------: | ------------------------: |
| Стандартные                         |   96,4 |          155,9 |    62,8 |                      79,5 |
| С тремя числовыми форматтерами Intl |  120,4 |          826,2 |    62,1 |                      77,5 |

Этапы измерялись отдельно от основного A/B-прогона. Для каждой комбинации
колонок и варианта использовались три свежих монтирования. Запрос
`switzerland` во всех 12 замерах дал одинаковые 603 узла в том же порядке.

| Колонки FL35                        | До кадра, мс, база → прототип | Самая долгая задача, мс, база → прототип |
| ----------------------------------- | ----------------------------: | ---------------------------------------: |
| Стандартные                         |                 782,2 → 802,5 |                            707,8 → 734,1 |
| С тремя числовыми форматтерами Intl |                1443,7 → 756,9 |                           1370,3 → 668,4 |

В типизированном сценарии повторное использование текста сократило
380 004 числовых форматирования до 851. В стандартном сценарии подходящих
колонок было 0. Исходные замеры лежат в
`performance-results/cold-search-cache-comparison.json`, медианы в
`performance-results/cold-search-cache-summary.json`.

## Решение

На проход подготовки текста держать отдельный кэш для каждой числовой колонки
со встроенным форматированием Intl. Ключ — исходное число. Отрицательный ноль,
значения других типов, колонки с подписями вариантов и пользовательские
`formatValue` проходят через обычный форматтер. Кэш принадлежит одному проходу,
поэтому настройки формата и локаль соответствуют этому проходу. Готовый текст
строки переиспользуется по правилам ADR 0201.

Ограничить кэш 1024 значениями на колонку и 16 384 значениями на проход.
Бюджет прохода делится поровну между колонками поиска. Когда лимит исчерпан,
новые значения форматируются без записи, а накопленные записи продолжают
использоваться.

## Требования

| ID   | Требование                                                                                         | Проверка |
| ---- | -------------------------------------------------------------------------------------------------- | -------- |
| QTN1 | Повтор числового значения в одной колонке использует результат одного форматирования Intl.         | unit     |
| QTN2 | Отрицательный ноль сохраняет собственное представление в тексте поиска.                            | unit     |
| QTN3 | Пользовательский числовой форматтер вызывается для каждой строки с её исходными данными.           | unit     |
| QTN4 | Кэш перестаёт пополняться при достижении лимита, оставляя текст новых значений доступным в поиске. | unit     |

## Последствия

Выигрыш зависит от повторяемости форматируемых чисел. Кэш расходует ограниченную
временную память в обмен на сокращение числа вызовов Intl. Публичная
конфигурация поиска и форматирование в самом гриде сохраняются.
