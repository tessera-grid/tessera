# 0005 — Виртуализация через TanStack Virtual

- **Статус:** Принято
- **Дата:** 2026-08-02

## Контекст

Производительность на больших наборах данных была первоочередной целью. Рендерить
все строки (а для плоских заголовков — и все колонки) невозможно, поэтому
виртуализация была необходима. Кандидаты, которые мы оценивали:

- **react-virtuoso** — эргономичный, но виртуализирует только по **Y**
  (в стиле списка). Tessera нужна ещё и виртуализация **колонок**, а не только
  строк.
- **react-window / react-virtualized** — уже устаревшие.
- **TanStack Virtual** — низкоуровневый и без навязанных мнений, виртуализирует
  любую ось и естественно сочетается с ядром TanStack Table
  ([ADR 0004](0004-core-on-tanstack-table.md)).

## Решение

Используем **TanStack Virtual** и для виртуализации **строк** (всегда), и для
виртуализации **колонок** (только для плоских заголовков). Принимаем его
низкоуровневую природу как цену за тот контроль и производительность, которые он
даёт.

## Последствия

- **+** Виртуализированы обе оси; хорошая измеренная производительность на больших
  таблицах.
- **+** Единая ментальная модель и жизненный цикл с ядром TanStack Table.
- **−** Это **низкоуровневый инструмент**: корректная настройка (извлечение
  диапазона, измерение, паддинги) потребовала значительных усилий на тюнинг и
  остаётся самой деликатной частью пути рендеринга.
- **−** Виртуализация колонок отключена для **вложенных (многоуровневых)
  заголовков**, которые используют CSS-раскладку `grid` — другой путь
  рендеринга. Именно поэтому вложенные заголовки пока не сочетаются с
  закреплением/перетаскиванием колонок (известное ограничение).
- См. [virtualization.md](../architecture/virtualization.md) про виртуализаторы и
  [rendering.md](../architecture/rendering.md) про разделение раскладки flex vs grid.

### Требования и покрытие тестами

Критерии приёмки, которые кодирует визуальный тест. Каждое требование — это
**отдельный именованный тест** в `stories/__tests__/visual/virtualization.test.tsx`
(vitest-browser, реальный Chromium), с именем-префиксом `V<n>:`, совпадающим с ID
из таблицы ниже, — так `npm test` отчитывается и падает по каждому требованию
поимённо (см. правило именования в [ADR 0009](0009-test-coverage-visual-and-performance.md)).
Основная часть тестов гоняет каноническую историю `All Features`, подобранную по
размеру так, чтобы переполнять по **обеим** осям (иначе виртуализация «схлопнется»
и требования пройдут вхолостую); guard-тест V11 защищает их от «тихого» прохождения.
Путь с **вложенными заголовками** (V3) проверяется на истории `Header Groups`
(`grid`-layout).

| ID  | Требование                                                                       |
| --- | -------------------------------------------------------------------------------- |
| V1  | Строки виртуализированы всегда: в DOM — только видимые строки + overscan, а не весь набор данных |
| V2  | При плоских (одноуровневых) заголовках столбцы виртуализированы: в DOM — только видимые столбцы + overscan |
| V3  | При вложенных (многоуровневых) заголовках виртуализация столбцов **отключена** — рендерятся все leaf-столбцы, а набор не меняется при горизонтальном скролле |
| V4  | Pinned/action-столбцы удерживаются в диапазоне при любой позиции горизонтального скролла — не «выпадают» из окна (кастомный column range extractor) |
| V5  | Диапазон строк расширен overscan'ом: над и под вьюпортом смонтирован запас строк, сглаживающий быстрый скролл (кастомный row range extractor) |
| V6  | Высота body соответствует полному числу строк: вертикальный скроллбар отражает весь набор, а не только смонтированные строки |
| V7  | Левый/правый виртуальные отступы не «перепрыгивают» через значения: `отступ слева + суммарная ширина отрендеренных реальных столбцов + отступ справа = полная ширина прокрутки`, даже когда реальный размер столбца расходится с размером его виртуального клона |
| V8  | Строка достижима прокруткой и рендерится в **начале**, **середине** и **конце** списка (окно виртуализации едет точно за скроллом по всей высоте) |
| V9  | Столбец достижим горизонтальной прокруткой и рендерится в **начале**, **середине** и **конце** списка (окно виртуализации едет точно за скроллом по всей ширине) |
| V10 | При горизонтальном скролле left/right filler-padding пересчитывается: левый отступ растёт по мере ухода столбцов за левый край (`useColumnVirtualizerScroll`) |
| V11 | *(setup-guard, не требование)* Канонная история переполняет по обеим осям — иначе V1/V2/V5/V7–V10 прошли бы вхолостую |

### Известные ограничения

- **V3** фиксирует текущее ограничение как контракт: виртуализация столбцов не
  сочетается с вложенными заголовками (`grid`-layout), поэтому весь ряд leaf-столбцов
  всегда в DOM. Снятие ограничения потребует пересмотра этого теста.
- Пороги overscan (V5) подобраны эмпирически; тест проверяет **наличие** запаса,
  а не конкретные числа.
