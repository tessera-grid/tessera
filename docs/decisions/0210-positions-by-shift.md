# 0210 — Пересчёт позиций сдвигом: прежние отрезки списка строк без ключей и размеров

- **Статус:** Принято (решение автора 2026-11-11)
- **Дата:** 2026-11-11
- **Слой:** вендор TanStack Virtual (`src/vendor/tanstack-virtual`, правка через `tessera.patch`) и
  ядро — журнал смен строк (`core/rowChanges.ts`), виртуализатор строк
  (`core/virtualization/rowVirtualizer.ts`). Не плагин: позиции строк нужны любой таблице,
  журнал пишут модели строк ядра и плагинов моделей.
- **Дополняет:** [ADR 0143](0143-tanstack-virtual-fork.md) — пересчёт позиций от места изменения;
  [ADR 0145](0145-first-changed-row-hint.md) — подсказка места первого изменения.
- **Связано:**
  - [ADR 0199](0199-row-shifts-in-the-middle-of-data.md) — сдвиги в середине `data`, перф MS9–MS11.
  - [ADR 0200](0200-own-row-engine.md) — свой движок строк: смена модели с наборами id.

## Контекст

После ADR 0145 виртуализатор пересчитывает позиции с первого изменённого индекса, а не с нуля. Всё
после него — заново: ключ строки, размер из кэша по ключу (`Map`), запись начала и размера. При
удалении или вставке в середине списка хвост — те же строки в том же порядке, у них меняется только
начало, на одну и ту же сумму.

Замер MS10 (2026-11-10, ×4 CPU): удаление 100 строк из середины 100 000 при сортировке — 79 мс против
48 мс у дописывания 100 строк в конец, ×1,6 при пороге 1,3. Из разницы ~18 мс — пересчёт позиций:
при сортировке по колонке с повторами удалённые строки разбросаны по списку, первое изменение — у
начала, пересчитывается почти весь список.

### Как у других

- **AG Grid** — модель хранит `rowTop` у узлов и пересчитывает их проходом от места изменения;
  сдвига без прохода нет, но проход дешёвый — поле узла, а не поиск по ключу.
- **react-window / TanStack Virtual upstream** — `resetAfterIndex(i)` / `pendingMin`: всё после
  индекса — заново.

## Решение

### 1. Отрезки прежних строк — в подсказке

Подсказка виртуализатору (`getFirstChangedIndex`, ADR 0145) может вернуть вместо числа
`{ from, kept }`: `from` — первый изменённый индекс, `kept` — отрезки после него, где стоят прежние
строки в прежнем порядке, тройками «новое начало, прежнее начало, длина» по возрастанию. На отрезке
ключ и размер строки — те, что были у неё в прежней сборке; у отрезка меняется только начало.

### 2. Вендор: перенос отрезков

`getMeasurements` при отрезках пишет позиции в новый буфер: до `from` — прежние, на отрезке — ключ и
размер из прежней сборки по прежнему индексу, начало — нарастающим итогом; между отрезками — как
прежде, ключом и размером. Условия те же, что у пересчёта от места изменения (ADR 0143): прежние
отступы, оценка размера и кэш измерений. Отрезок за пределами прежней или новой сборки — подсказка
отбрасывается целиком, пересчёт с `from`.

Отрезок предполагает, что размер строки зависит от строки, а не от её индекса: так у грида — размер
по строке и кэшу измерений по ключу. В разработке вендор сверяет каждый перенесённый ключ и размер с
пересчётом; расхождение — одно предупреждение на виртуализатор и пересчёт с `from`.

### 3. Журнал: отрезки по тождеству строк

Отрезки считаются, когда их спрашивает сборка виртуализатора, а не на каждой смене модели: модели
выше по конвейеру их не читают. Журнал хранит у смены наборы id из смены модели (`inserted`,
`changed`, `removed`, ADR 0194/0200). Сравнение идёт двумя указателями по прежнему и новому спискам:

- тот же объект строки — отрезок продолжается;
- прежняя строка удалена или изменена (её id в `removed` или `changed`) — пропускается прежняя;
- новая строка вставлена или изменена — пропускается новая;
- иначе — порядок менялся (сортировка, перенос без наборов): дальше берётся только общий конец
  списков — по тождеству с конца.

Отрезок — только из совпавших объектов строк, поэтому неверные наборы делают отрезки короче, но не
неверными. Цепочка нескольких смен между сборками — объединение наборов её шагов. Смена без наборов
(модель раскрытия, ADR 0070) — общий конец списков: раскрытие вставляет участок, хвост — прежний.

## Отвергнутые альтернативы

- **Отрезки при каждой смене модели** — работа на стадиях, чьи списки виртуализатор не читает.
- **Сдвиг одного хвоста** (общий конец списков) — не помогает при сортировке: удалённые строки
  разбросаны, общий конец короткий.
- **Позиции у строк** (как `rowTop` у AG Grid) — поле в объекте строки и запись на каждый сдвиг;
  отвергнуто замером ADR 0199 (запись позиций хвоста сама стоит 6–9 мс).

## Последствия

- **+** Удаление и вставка в середине и перенос строки пересчитывают позиции только изменённых строк;
  остальные — копия числа из прежнего буфера со сдвигом начала.
- **−** Ещё одна правка вендора; при обновлении TanStack Virtual — перенос патча (README вендора).
- **−** В разработке сборка с отрезками дороже: сверка каждого перенесённого ключа.
- **Публичный API** не меняется: опция `getFirstChangedIndex` — внутренняя для вендора.

## Внедрение

2026-11-11, рабочая копия против `a92bdd52`; в рабочей копии вместе с этим ADR — ADR 0208 и 0209.
`perf:compare` (VS5), 15 раундов, ×4 CPU, порог ±10 %:

| Случай                                | A, мс | B, мс | B/A       | Вердикт       |
| ------------------------------------- | ----- | ----- | --------- | ------------- |

| MS9-base — дописывание в конец        | 47,0  | 34,4  | 0,733     | улучшение     |
| MS10 — удаление 100 строк из середины | 80,5  | 54,1  | 0,672     | улучшение     |
| MS10-base — дописывание в конец       | 48,0  | 33,5  | 0,699     | улучшение     |
| MS11 — перенос строки                 | 51,8  | 47,7  | 0,919     | не определено |
| IU13, HV8, IS16, SD46                 | —     | —     | 0,95–1,01 | без изменений |

Регрессий нет. Порог ADR 0199 для MS10 (×1,3 к дописыванию) не взят: дописывание тоже подешевело
(тонкая ячейка ADR 0208), отношение — ×1,6, как до внедрения. Остаток разницы (~20 мс) —
не виртуализатор: удаление в середине `data` сдвигает места ~50 000 строк (`index` и запись
позиции у каждой, ADR 0199), дописывание — нет. Это следующий рычаг — места строк блоками.
