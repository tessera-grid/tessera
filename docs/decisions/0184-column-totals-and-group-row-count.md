# 0184 — Итоги колонок и число строк группы на клиенте

- **Статус:** Принято и внедрено (решения — по итогам прожарки 2026-11-05)
- **Дата:** 2026-11-05
- **Слой:** плагин `columnTotals` (`plugins/columnTotals`) — итог на клиенте: без него агрегация
  не входит в сборку, поэтому он не в ядре. Функции агрегации нужны ему и модели группировки,
  плагин другой плагин не импортирует, поэтому они переезжают в `shared/aggregation.ts`.
  Ядро — метод `table.getColumnTotal` и включение футера: футер уже возможность ядра, а итог в
  серверной модели приходит из источника строк. Источник строк ядра — число строк группы:
  его читает грид, считают источники.
- **Изменяет:**
  - [ADR 0118](0118-column-footer.md) §1, FT16 — футер закреплён как шаблон колонки; у колонки
    без `footer` содержимое может дать плагин, а не только пустая ячейка.
  - [ADR 0144](0144-server-side-grouping.md) §2, §4 — подпись группы считает строки данных,
    `getColumnTotal` — метод ядра.
  - [ADR 0016](0016-row-grouping.md) — число строк группы; `aggregatedCell` не рисуется.
  - [ADR 0083](0083-text-overflow.md) «Границы» — подпись «значение (N)» внедряется здесь.
- **Связано:**
  - [ADR 0046](0046-toolbar-and-status-bar-visibility.md) — панели по наличию содержимого,
    флаг запрещает.
  - [ADR 0138](0138-server-side-row-model.md) — источник строк, `totals` ответа.
  - [ADR 0169](0169-data-mode.md) — режим данных, часть строк у грида.
  - [ADR 0163](0163-layer-boundaries-and-guards.md) — границы слоёв.
  - [ADR 0178](0178-drafts.md) — черновики не меняют данные модели.

## Контекст

Аудит паритета моделей строк 2026-11-04 оставил две разницы, где серверная модель умеет больше
клиентской:

- **Итог в футере.** В SSRM колонка без `footer` показывает значение из `totals` ответа
  (ADR 0144, §4). На клиенте итог приложение считает само: истории обходят строки вручную
  (`sumFooter`), хотя TanStack 9.2 уже умеет считать итог колонки.
- **Число строк группы.** В SSRM подпись `(N)` стоит рядом со значением группы, на клиенте её
  нет. Подпись стоит в одном текстовом блоке со значением, поэтому `…` режет и число, хотя
  ADR 0083 обещал целый счётчик. Число приходит из `getGroupChildCount`, а это размер ветки:
  прямые дети. На верхнем уровне вложенных групп человек видит число подгрупп.

Документы называют футер «строкой итогов», а контракт FT16 шире: в ячейке любое содержимое
`columnDef.footer`. Роль футера нигде не решена, и от неё зависит, где жить итогу.

Агрегация пришла в сборку только с `rowGrouping`: `rowAggregationFeature` и набор функций
лежат в его модели, а итог без группировки — самый частый случай футера.

### Как это сделано у других (проверено 2026-11-05)

- **TanStack Table** — футер: «Footer template rendered with header context», об агрегации не
  знает. `rowAggregationFeature` — независимая фича значений групп и итогов корня; её
  документация показывает итог внутри шаблона:
  `footer: ({ column }) => column.getAggregationValue()`. Без аргументов считает
  `getPreGroupedRowModel()` — строки после фильтров, на всех страницах — и кэширует результат
  по модели. `maxAggregationDepth` задаёт глубину дерева.
- **Kendo** — своя ячейка футера у колонки (`GridFooterCellProps`). В группах — ячейка футера
  группы; без группировки приложение считает итог и передаёт в футер (подтверждено для Angular).
- **Ant Design** — два механизма: `footer` — свободная область не по колонкам, `Table.Summary` —
  строка по колонкам с `fixed`.
- **DevExtreme** — футер и есть область итогов: `summary.totalItems` описывает колонку, тип
  агрегата и формат.
- **AG Grid** — ячеек футера у колонок нет: итог — строка `grandTotalRow`, закреплённые строки —
  данные (`pinnedBottomRowData`).
- **MUI X** — строка агрегатов: `getAggregationPosition` выбирает футер или строку группы,
  значение рисует `renderCell` с параметром `aggregation`. Число потомков в ячейке группы видно
  по умолчанию, `hideDescendantCount` его скрывает.

Два подхода: итог — отдельная сущность с данными (AG Grid, MUI X, DevExtreme) или футер — шаблон
колонки, а итог — одно из его содержимых (TanStack, Kendo). Tessera стоит на TanStack.

## Решение

### 1. Футер — шаблон колонки

Футер — строка под колонками с ячейкой у каждой колонки и любым содержимым, как в TanStack.
Итог — один из источников содержимого. Порядок для ячейки: `columnDef.footer`, затем итог
колонки, затем пустая ячейка.

### 2. Плагин `columnTotals`

```ts
useCreateTable({
  columns: [{ accessorKey: 'amount', aggregationFn: 'sum' }],
  plugins: [columnTotals()],
})
```

Плагин приносит `rowAggregationFeature` и набор функций из `shared/aggregation.ts` — тот же
объект, что у модели группировки, поэтому вместе они не перезаписывают друг друга. Аргумент один —
`enabled`. Без плагина футер работает как сейчас, агрегации в сборке нет.

### 3. Что считается итогом

- Только колонка с явным `aggregationFn`, именем из набора или определением `{ aggregate }`
  TanStack. Значение `'auto'` итога не даёт:
  оно суммировало бы и числовой id, а на сервер `auto` не уходит (ADR 0144, §1).
- Итог считает `column.getAggregationValue()`: строки после фильтров и поиска на всех страницах.
  Страница и группировка его не меняют.
- В дереве — верхний уровень, `maxAggregationDepth` колонки идёт глубже: родитель часто уже
  содержит сумму детей, и обход всех уровней считал бы дважды.
- Итог — по данным, черновики его не меняют, как и модели строк (ADR 0178).
- Текст — по типу колонки, как её ячейка (GS14). Итог-массив (`extent`, `unique`) — элементы
  по типу через запятую. `aggregationFn` списком даёт объект: его читает свой `footer`.

### 4. `table.getColumnTotal`

Метод переезжает из фичи серверной модели в ядро: один код `footer` в обоих режимах. Значение —
`totals` источника, иначе `columnTotalOf` — опция таблицы, которую ставит плагин, иначе `undefined`. Ячейка футера читает
итог этим же методом.

### 5. Часть строк у грида

Страница с сервера и лента (`partialRowsReason`): клиентская сумма загруженных строк выглядела бы
как настоящий итог, поэтому плагин не считает, `getColumnTotal` даёт `undefined`, в разработке —
предупреждение. Настоящий итог приложение показывает своим `footer`.

### 6. Серверная модель строк

Плагин ничего не считает: футер и метод берут `totals` ответа. Плагин в SSRM активен и включает
футер, поведение ADR 0144 прежнее; без плагина итог SSRM показывается при `enableFooter`, как сейчас.

### 7. Включение футера

С опцией `columnTotalOf` ядро включает строку футера без флага, `enableFooter: false` её запрещает, а
плагин становится инертным с причиной `'noFooter'`. Так же, как тулбар и нижняя панель по ADR 0046: приложение не настраивает два места.

### 8. Число строк группы

- Подпись — число строк данных в группе: `(120)` у города при трёх подгруппах. На клиенте — листья
  группы после фильтров и поиска.
- Источник строк отдаёт число методом `groupRowCount(row)`, грид читает только его.
- В SSRM — новый необязательный `getGroupRowCount(row)`: подпись. Без него — прямые дети, как
  сейчас. `getGroupChildCount` по-прежнему задаёт размер ветки: у него другая роль, менять её нельзя.
- Подпись видна по умолчанию в обоих режимах, `rowGrouping({ groupRowCount: false })` убирает её.
- Подпись — отдельный элемент: `…` сокращает значение, число целое и в свойстве ячейки `cell`.

## Границы

- Итоги групп (`groupTotalRow`) и несколько строк футера — вне объёма, как в ADR 0118.
- Подпись «Итого» из коробки — нет: её задаёт свой `footer`.
- Выбор при клиентской группировке — [ADR 0185](0185-selection-with-client-grouping.md).
- `aggregatedCell` TanStack грид не рисует ни в одной модели (ADR 0144, §2).
- Настройка метода агрегации человеком — нет.
- Заглушка ждущей ветки при `maxAggregationDepth` больше нуля — до ответа она стоит вместо родителя:
  значение родителя не входит в итог, `count` считает заглушку. Обход без неё лишил бы итог кэша
  TanStack, а случай редкий: глубина и ленивое дерево вместе.
- Итог по выбранным строкам — нет: его считает приложение через
  `column.getAggregationValue({ rows })`.

## Отвергнутые альтернативы

- **Футер только для итогов, как в DevExtreme.** Ломает FT16 и уносит раскладку футера из грида
  ради чистоты смысла.
- **Итог в ядре.** Удобно подключать, но агрегация уходит в каждую сборку и увеличивает бюджет
  `DataGrid` (LB4).
- **Итог только с `rowGrouping`.** Без группировки итога нет, а это самый частый случай футера.
- **Включать итог и для `auto`.** В футере появятся суммы всех числовых колонок, в том числе id, и
  клиент разойдётся с SSRM.
- **Считать загруженные строки при части данных.** Число меняется с догрузкой и вводит в заблуждение.
- **Новая опция итогов для страницы с сервера.** Полный паритет, но новая опция ядра; свой `footer`
  уже решает задачу.
- **Прямые дети в подписи на клиенте.** Паритет без нового API, но на верхних уровнях число мало что
  говорит.
- **Только `enableFooter` включает футер.** Без флага плагин инертен: два места настройки.

## Последствия

- **Публичный API:** новые `columnTotals`, `rowGrouping({ groupRowCount })`,
  `serverRowModel({ getGroupRowCount })`. `table.getColumnTotal` — метод ядра, вызов прежний.
  `RowSource.groupRowCount` — новое поле источника.
- **Ломающее изменение вида:** клиентские группы получают подпись `(N)` по умолчанию; отмечается в
  `CHANGELOG.md`, снимки историй с группировкой обновляются.
- **Перф:** итог — один проход по отфильтрованным строкам на колонку, результат в кэше по модели
  (CT11). Подпись считает листья только у видимых групп, первый подсчёт большой группы заметен (GC7).
- **Документация:** `docs/architecture/rendering.md` (футер), `plugins-and-slots.md` (источник
  строк), roadmap — пункт «Агрегация в группах».
- **Истории:** `sumFooter` моков заменяется итогом плагина там, где сценарий не про свой `footer`.

## Внедрение

- **Этап 1 внедрён 2026-11-05.** `shared/aggregation.ts` — общий набор функций; плагин
  `plugins/columnTotals` ставит опцию таблицы `columnTotalOf`, с ней `useCreateTable` включает футер
  без флага. `table.getColumnTotal` — метод `commonFeature`, ячейка футера читает итог им.
  Новые причины инертности — `'noFooter'` и `'partialRows'`. Истории — раздел «Core/Column totals».
- **Этап 2 внедрён 2026-11-05.** `RowSource.groupRowCount`: на клиенте потомки без строк-подгрупп,
  счёт хранится по массиву потомков; в SSRM — `getGroupRowCount`, иначе `getGroupChildCount`. Опция
  таблицы `groupRowCount` приходит из `rowGrouping`, значение и число — отдельные элементы, тултип
  обрезанного текста читает значение (`[data-group-value]`).

## План внедрения

1. **Этап 1 — итоги.** CT1–CT12, S1–S4: `shared/aggregation.ts`, плагин `columnTotals`,
   `getColumnTotal` в ядре, включение футера, раздел историй с `Playground`.
2. **Этап 2 — число строк группы.** GC1–GC7, S5–S7: `RowSource.groupRowCount`, подпись отдельным
   элементом, `getGroupRowCount`, аргумент `groupRowCount`; снимки историй с группировкой.

Внедрение этапа меняет вид требований и сценариев на итоговый, ADR 0118, 0144, 0016 и 0083 правятся
в том же этапе.
