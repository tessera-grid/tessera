# 0011 — Закрепление столбцов: плагин columnPinning

- **Статус:** Принято
- **Дата:** 2026-08-07
- **Изменён:** 2026-09-10 — кнопка закрепления переведена с опакового слот-компонента
  (`ColumnPinningComponent`→`PinButton`) на единый дескриптор `slotActions`
  ([ADR 0024](0024-slot-action-descriptor-and-menu.md)): при подключённом
  `headerActionMenu` уезжает в кебаб-меню. Инлайн-DOM (`column-pin__button`, иконка,
  `data-button-active`) сохранён; `PinButton` остаётся публичным примитивом.
- **Изменён:** 2026-09-11 — закрепление выведено в UI **и влево, и вправо** (было
  только влево). Стороны берутся из `columnDef.meta.pinSides` (`both` | `start` |
  `end`, по умолчанию `both`). При `both` инлайн-подача — мини-меню-поповер
  «Закрепить слева / справа» (`inlineAsMenu`, дескриптор `SlotAction`); при одной
  стороне — прямой тумблер без поповера. В кебаб-меню: два направленных пункта при
  `both`, одна строка-тумблер Pin/Unpin при одной стороне. Рендер правого края
  доведён до паритета с левым (фон, нечётные строки, разделитель), а
  колоночная виртуализация научена монтировать только что закреплённый столбец
  сразу (см. ниже). См. требования CP20–CP22.

  - [ADR 0009](0009-test-coverage-visual-and-performance.md) — покрытие

## Контекст

Потребителям нужно удерживать значимые столбцы (идентификатор строки, статус,
столбец действий) в поле зрения при горизонтальной прокрутке широкого грида.
TanStack Table v9 несёт готовую модель `columnPinning` (`column.pin`,
`column.getIsPinned`, `column.getStart('start')`, `column.getAfter('end')`,
`getIsLastColumn`), но она про **состояние** (стороны `start`/`end`), а не про
рендер: sticky-раскладку,
affordance закрепления в шапке и приоритет сервисных колонок надо построить
поверх.

Этот ADR — единый источник истины по закреплению столбцов в Tessera. Он фиксирует
и **решение** (что закрепление строим на штатной модели TanStack, а не на своей),
и **как** оно реализовано плагином `columnPinning`: активацию, кнопку-affordance
в шапке, sticky-рендер ячеек, авто-закрепление сервисных колонок и flow
переключения, — плюс таблицу требований (CP1–CP16) со ссылками на тесты.

## Решение

### Опора на штатную модель TanStack

Закрепление опирается на встроенную фичу `columnPinning` TanStack Table
([ADR 0004](0004-core-on-tanstack-table.md)). Плагин не хранит собственную карту
закрепления — он читает `column.getIsPinned()` / `column.getStart('start')` /
`column.getAfter('end')` и вызывает `column.pin(...)`. Состояние возвращается
потребителю через штатный контракт `columnPinning` / `onColumnPinningChange`.

### Форма плагина

`columnPinning` (`src/lib/plugins/columnPinning/registry.ts`) — фабрика записи
`TesseraFeatureEntry`; поведение даёт встроенная `columnPinningFeature`
(состояние `{ start, end }`). Она делает что-либо только когда плагин подключён
(опция **`enableColumnPinning`**, по умолчанию `false`). В v9 нет per-column
`canPin`, а обёртка `createColumn` и `keepFeatureWhenDisabled` убраны —
**гранулярность** закрепления под вложенной шапкой перенесена в предикат `visible`
пин-дескриптора (`pinHeaderAction`):

```ts
// pinHeaderAction.visible — можно ли закрепить эту единицу заголовка
visible: ({ column, table }) => {
  if (!column.getCanPin()) return false
  // Плоская шапка — штатно.
  if (table.getHeaderGroups().length === 1) return true
  // Reorder-out (opt-in `enableLeafPinning`) — закрепляется любая единица.
  if (table.options.enableLeafPinning) return true
  // Иначе вложенная шапка — только группа верхнего уровня целиком.
  return column.depth === 0
}
```

**По умолчанию** под вложенной шапкой закрепляется **только группа верхнего
уровня** (`depth === 0`) **целиком**: TanStack при `column.pin(...)` группы
закрепляет все её листовые колонки (`getLeafColumns()`), а `getIsPinned`/
`getCanPin` группы агрегируют по листьям — групповой пиннинг поддержан нативно.
Отдельный лист под группой в этом режиме закрепить нельзя, даже если у него
`enablePinning`: так закреплённая зона совпадает с границами группы и не рвёт
спанящую шапку. Явную попытку (лист с `enablePinning: true`) плагин один раз
логирует ([ADR 0022](0022-plugin-compatibility-contract.md)); дефолтный
`enablePinning` просьбой не считается, чтобы не спамить.

Рендер (sticky) для групповой шапки считает offset по **листьям** колонки
заголовка (`HeadCell`): у спанящей шапки `header.column` — не лист, поэтому
`getStart('start')`/`getAfter('end')`/`getIsLastColumn('start')` берутся с первого
и последнего листа. Для листовой шапки `getLeafColumns()` = `[сама колонка]`, так
что плоский путь не меняется. Виртуализация столбцов в grid-layout выключена, так
что кастомный range-extractor (как во `flex`) для этого не нужен.

### Reorder-out: закрепление листьев и вложенных групп (`enableLeafPinning`)

Опциональный режим (opt-in через `columnPinning({ leafPinning: true })` →
`table.options.enableLeafPinning`) снимает ограничение «только группа верхнего
уровня» и позволяет закрепить под вложенной шапкой **любую единицу** — отдельный
лист, промежуточную или верхнюю группу. Модель — **reorder-out** (как в AG Grid):

- **Механика (симметрична для обеих сторон).** Закрепление всегда работает по
  **листьям цели**. При левом пине их id уходят в **начало** `columnPinning.start`,
  при правом — в **начало** `columnPinning.end`, и `columnOrder`
  переупорядочивается так, что закреплённые листья встают к нужному краю (левые —
  сразу за ведущим сервисным блоком, правые — сразу перед замыкающим `rowActions`),
  остальные — в естественном порядке определения. Тогда штатные
  `getVisibleLeafColumns()` и `getHeaderGroups()` сами ставят листья у края, а
  `buildHeaderGroups` (группирует по **смежным прогонам** одного родителя) **режет**
  спанящую шапку каждого родителя на сегменты: закреплённый у края + остаток в
  центре. Существующий sticky-путь замораживает крайний блок. 3-регионный рендер не
  понадобился — весь текущий поток переиспользован. Сторону задаёт `pinSides` того
  же дескриптора, что и для плоской шапки: `both` — поповер выбора, одна сторона —
  прямой тумблер.
- **Почему `columnOrder` сеется по листьям.** Ядро сеет начальный `columnOrder` на
  уровне **листьев** (а не top-level), иначе reset-эффект `useColumnOrderState`
  (сверяет длину с начальной) сбрасывал бы перестановку. Для плоской таблицы листья
  == top-level, поэтому порядок и его длина не меняются.
- **Естественный порядок — из дерева.** При откреплении порядок восстанавливается
  из обхода дерева `getAllColumns()` (`.columns`), а **не** из `getAllLeafColumns()`
  — последний уже применяет `columnOrder` и не вернул бы исходный порядок.
- **Аффорданс и активность — по сегменту.** Кнопка (и её активное состояние, и
  переключение) считается по листьям **этой ячейки-сегмента** (`header.getLeafHeaders()`),
  а не по колонке-группе. Иначе после разреза `column.getIsPinned()` агрегировал бы
  по всем листьям, и сегмент над **откреплённым** листом остался бы «активным».
  Переключение сегмента пинит/открепляет ровно его листья (через `setColumnPinning`,
  не `column.pin`, который тронул бы все листья группы).
- **Гранулярность.** Кнопка — на каждом закрепляемом заголовке: лист, промежуточная
  и верхняя группа. Частичный анпин листа из закреплённой группы законен: группа
  корректно **разрезается**, а её сегмент-призрак гаснет.

- **Стык с сервисными столбцами.** Reorder уважает авто-закрепление: ведущие
  сервисные столбцы (`rowSelection`/`rowExpanding`/`rowDragging`) держат левый край,
  замыкающий (`rowActions`) — правый. Пользовательские пиннутые листья вставляются
  **между** сервисными: левые — **после** ведущего блока, правые — **перед**
  замыкающим `rowActions` (LP10), а не снаружи них. Сервисные id в стор пиннинга не
  пишутся — ядро их срезает (`handleColumnPinningChange`, `mergeServiceColumnPinning`),
  так что «протечки» нет и логика `when:'with-user'` (release ведущих при откреплении
  последнего пользовательского пина) сохраняется.

Ограничения режима (осознанные): подпись группы **дублируется** над закреплённым
сегментом (неотъемлемо для reorder-out); лист/группа визуально **покидают** своё
место. Стороны — обе (влево и вправо), как и для плоской шапки.

UI-affordance объявляется **дескриптором** `slotActions` (`pinHeaderAction`,
[ADR 0024](0024-slot-action-descriptor-and-menu.md)) в `rightHeaderSlot` (`order: 0`)
— в правой части каждой ячейки заголовка; ядро подаёт его инлайн-кнопкой (`PinButton`)
или строкой кебаб-меню:

```ts
slotActions: [pinHeaderAction]
```

### Двустороннее закрепление в UI (`pinSides`)

Кнопка закрепляет столбец **и влево, и вправо**. Какие стороны предлагать —
решает `columnDef.meta.pinSides` (`'both' | 'start' | 'end'`, по умолчанию
`'both'`); ограничение касается только affordance, сама модель TanStack
поддерживает обе стороны независимо. Поле типизировано аугментацией
`ColumnMeta` (`plugins/columnPinning/types.ts`): физические `'left'`/`'right'`
или опечатка — ошибка типов, а не молчаливый откат к `start`.

- **`both`** — инлайн-клик неоднозначен, поэтому кнопка открывает **мини-меню-
  поповер** с пунктами «Закрепить слева / справа» (активная сторона отмечена).
  Технически это флаг дескриптора `SlotAction.inlineAsMenu`: ядро рисует инлайн-
  действие не кнопкой-`onSelect`, а поповером его `menuItems` (общий с кебабом
  `ActionMenuPopup`). Повторный выбор той же стороны — открепляет; выбор другой —
  переносит.
- **`start` / `end`** — вариант один, поповер не нужен: кнопка работает прямым
  **тумблером** этой стороны (`side ↔ false`, как было для левого пиннинга).

Подпись/иконка/активность считаются по **стороне сегмента**
(`getSegmentPinnedSide`: все листья сегмента на одной стороне → эта сторона,
иначе `false`). `cellPinningParams` и раньше целиком покрывал правый край
(системно он использовался для авто-закреплённого справа `rowActions`, см.
[Сервисные столбцы](#сервисные-столбцы-авто-закрепление)) — двусторонний UI
переиспользует этот путь без переделки расчёта.

### Паритет рендера правого края

Правозакреплённый **пользовательский** столбец доведён до визуального паритета с
левым: у него появился фон (`--tsr-comp-cell-pinned-right-bg`) и вариант нечётной
строки (`data-cell-odd-right-pinned` / `--tsr-comp-cell-odd-pinned-right-bg`), а
**первый** (левый в правом блоке) закреплённый столбец несёт разделитель слева
(`data-cell-first-right-pinned` → `border-left`) — зеркало `data-cell-last-left-pinned`.

Служебная колонка действий (`rowActions`) авто-закреплена справа всегда, поэтому
её подложка **условна**: пока пользовательских правых пинов нет — она без фона (как
было до двустороннего UI), а как только появляется хотя бы один пользовательский
right-pin, действия входят в правозакреплённый блок и получают ту же подложку.
Условие выражено через `data-cell-first-right-pinned`: `rowActions` всегда самая
правая, значит «первой справа» она бывает только когда одна (пинов нет) — тогда фон
исключён; при появлении пользовательского пина она перестаёт быть первой справа и
фон включается (правила `[data-actions-column-cell='true']…:not([data-cell-first-right-pinned='true'])`).
Пользовательский right-pin встаёт **левее** `rowActions` (порядок
`[...userRight, ...service]` в `mergeServiceColumnPinning`), поэтому разделитель
правого блока ложится на его левую границу, а сама `rowActions` остаётся замыкающей.
Разделитель у `rowActions` не рисуется никогда (`:not([data-actions-column-cell='true'])`).
Заголовок `rowActions` по умолчанию (действия единственные справа) позиционируется
флексом — `position: sticky` там сломал бы раскладку (регрессия `service-columns`).
Но при наличии пользовательского правого пина заголовок действий становится
`sticky` у правого края (с `flex-grow: 0`, отменяющим заполняющее флекс-правило),
получая фон и выравниваясь со своим телом; контента у него нет (`header: undefined`).

### Виртуализация: монтирование только что закреплённого столбца

Колоночная виртуализация (`useColumnVirtualizer`) держит закреплённые к краям
столбцы в окне через `rangeExtractor`. react-virtual мемоизирует `getIndexes` по
паре `[range, rangeExtractor]`: при закреплении `range` (от скролла) не меняется, а
ссылка на extractor была стабильна (`useCallback([table])`) — поэтому только что
закреплённый **справа** столбец не попадал в окно до следующего скролла (левый
«работал» лишь потому, что и так был у левого края). Починка: `columnPinning` в
зависимостях `useCallback` — при закреплении меняется идентичность extractor,
react-virtual сбрасывает кэш и пере-считает окно сразу, монтируя пиннутый столбец
sticky у нужного края без скролла.

**Порядок индексов виртуализатора — порядок отображения.** Ячейки строки
(`row.getVisibleCells()`) и заголовки упорядочены start-закреплённые → центр →
end-закреплённые, и `BodyRowCells`/`HeadRow` адресуют их по `virtualColumn.index`.
Поэтому оценки размеров (`estimateSize`) и ключи (`getItemKey`) виртуализатор
берёт из того же порядка (`core/displayColumns.ts`), а не из натурального
`getVisibleLeafColumns()`: иначе ширина колонки, закреплённой справа, ложится в
слот её «натуральной» позиции — соседи в центре расходятся зазором или
нахлёстом. `estimateSize` не входит в мемо-зависимости react-virtual, поэтому при
смене порядка отображения (закрепление/перестановка) кэш размеров сбрасывается
явно (`virtualizer.measure()`).

### Affordance в шапке

Кнопку описывает **дескриптор** `pinHeaderAction` (`pinHeaderAction.tsx`, ADR 0024) —
данными, а не опаковым компонентом. `visible` (см. выше) решает, показывать ли её;
`active`/`label` берут `getSegmentPinnedSide`. Ядро подаёт дескриптор **инлайн** —
иконка-кнопка `PinButton` (при `pinSides: 'both'` — поповер выбора стороны через
`inlineAsMenu`) — либо строкой **кебаб-меню** (`menuItems`); `onSelect` тумблит сторону:

```ts
onSelect: ctx => {
  const side = getPinSides(ctx.column) === 'end' ? 'end' : 'start'
  togglePin(ctx, side) // column.pin(...) или reorder-out по листьям сегмента
}
```

`PinButton` (`PinButton.tsx`):

- иконка `pin` (по умолчанию lucide `Pin`, переопределяема через
  `<DataGrid icons={{ pin }} />`) — **16×16**;
- в закреплённом состоянии иконка **повёрнута на −45°** (`PinButton.module.css`:
  `.pinned svg { rotate: -45deg }`) и красится в активный цвет
  (`--tsr-comp-control-active-color`), `data-button-active` = `true`;
- тултип — `pin` / `unpin` из локализации (по умолчанию `Pin column` /
  `Unpin column`);
- **видимость только при наведении** — кнопка присутствует в DOM всегда, но
  скрыта `opacity: 0` до наведения на ячейку заголовка через общую конвенцию
  `cell__button--hidden` (`grid/cellControls/buttonVisibility.css`).

### Sticky-рендер ячеек

Позиционирование закреплённых ячеек считает `useCellPinningParams`
(`cellPinningParams.ts`) из штатных методов TanStack. И `HeadCell`, и `BodyCell`
читают его и превращают в inline-стиль + data-атрибуты:

- **offset:** `left = column.getStart('start')` для левого края,
  `right = column.getAfter('end')` для правого — накопительное смещение с
  учётом ширин соседних закреплённых столбцов;
- **sticky-слой:** CSS по `data-cell-pinned` даёт `position: sticky`,
  `z-index: var(--tsr-comp-z-index-pinned)`, фон
  (`--tsr-comp-cell-pinned-left-bg`, для нечётных строк —
  `--tsr-comp-cell-odd-pinned-left-bg`), чтобы прокручиваемый контент не
  просвечивал сквозь закреплённую ячейку;
- **разделитель:** последний закреплённый слева столбец
  (`data-cell-last-left-pinned`, `column.getIsLastColumn('start')`) получает
  правую границу `--tsr-comp-cell-pinned-border-color`; правый край
  зеркально (`isFirstRightPinnedColumn` / `isAloneRightPinnedColumn`
  выравнивают контент по правому краю).

data-атрибуты (`data-cell-pinned`, `data-cell-last-left-pinned`,
`data-cell-odd-left-pinned`, `data-cell-first-right-pinned`,
`data-cell-last-right-pinned`, `data-cell-alone-right-pinned`) — контракт между
расчётом и CSS; на них же опираются визуальные тесты.

### Сервисные столбцы: авто-закрепление

Сервисные (action-) столбцы плагинов закрепляются **автоматически**, помимо
пользовательских кликов. `useColumnPinningInitialState`
(`core/createState.ts`) вычисляет их набор: **слева** —
expander (`rowExpanding`), selection (`rowSelection`), drag-ручка
(`rowDragging`); **справа** — столбец действий строки (`rowActions`, сам плагин —
[ADR 0025](0025-row-actions.md)).

Как этот набор применяется, решает `mergedColumnPinning` в `useCreateState`
(асимметрично, намеренно):

- **столбец действий (справа)** закрепляется **всегда** — даже когда
  пользователь ничего не пинил;
- **ведущие сервисные столбцы (слева)** подмешиваются в закрепление **только
  когда пользователь закрепил хотя бы один столбец влево** (или пришёл external
  left-пиннинг). Иначе они остаются обычными — незачем создавать закреплённую
  зону слева, пока в ней нет пользовательских столбцов; как только она
  появляется, сервисные столбцы «прилипают» к её началу, а не остаются левее
  прокручиваемыми.

Слияние идёт через `mergeColumnPinning` (dedupe левых/правых id через `Set`), а
`useColumnPinningState` пере-мёржит дефолт с начальным состоянием при его смене.
Это тот самый неоднородный слайс state, отмеченный в
[ADR 0010](0010-invert-core-plugins-registry.md).

### Точка расширения

`ColumnPinningPluginParams.onTogglePin(pinned: boolean)` — hook плагина,
вызываемый после переключения (дефолт — no-op). Позволяет потребителю
среагировать на закрепление/открепление (аналитика, серверная персистенция),
не перехватывая сам контракт `onColumnPinningChange`.

## Последствия

- **+** Закрепление опирается на штатную, проверенную модель TanStack — свой
  «источник истины» по состоянию не заводится.
- **+** Sticky-раскладка выражена data-атрибутами + CSS-переменными: тема и
  границы переопределяемы, визуальные тесты цепляются за атрибуты.
- **+** Сервисные столбцы закрепляются сами — пользователю не надо вручную
  фиксировать selection/expander/действия.
- **+** UI закрепляет и влево, и вправо (`pinSides`); правый край доведён до
  визуального паритета с левым, а виртуализация монтирует пиннутый столбец сразу.
- **+** Многоуровневые заголовки закрепление **поддерживают**: по умолчанию — группа
  верхнего уровня целиком; опционально (`enableLeafPinning`, reorder-out) — любая
  единица (лист / промежуточная / верхняя группа), закреплённые листья уходят влево
  блоком, спанящие шапки родителей режутся. Перетаскивание столбцов под вложенной
  шапкой при этом по-прежнему выключено ([ADR 0006](0006-dnd-with-dnd-kit.md),
  [ADR 0022](0022-plugin-compatibility-contract.md)) — потребности нет.
- **+** Reorder-out корректно уживается с сервисными столбцами: ведущие держат
  левый край, `rowActions` — правый, пользовательские пины встают после ведущего
  блока; сервисные id не протекают в стор (LP7/LP8).
- **−** Режим reorder-out дублирует подпись группы над закреплённым сегментом и
  визуально «выносит» единицу из её места (неотъемлемо для reorder-out).
- **−** При `pinSides: 'both'` быстрый пин требует двух кликов (открыть поповер →
  выбрать сторону) — плата за явный выбор стороны; одностороннему столбцу задают
  `pinSides` и получают прямой тумблер.
