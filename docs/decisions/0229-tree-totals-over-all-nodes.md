## Контекст

Итог колонки в дереве складывает только верхний уровень (ADR 0184, §3): обход всех уровней
посчитал бы детей дважды, если значение родителя — свод его детей. Но родитель бывает и своей
записью: у задачи свои часы, у подзадач — свои; у отдела свои продажи, а люди в нём собраны не
по признаку продаж. Тогда верный итог — сумма всех строк, и встроенного способа для него нет:
приложение пишет свою функцию `{ aggregate }`, которая спускается по `subRows`. Опция TanStack
`maxAggregationDepth` не помогает: она выбирает один уровень, а не «до уровня».

### Как это сделано у других (проверено 2026-11-15)

- **DevExpress** — единственный с переключателем: WinForms `AllNodesSummary` у колонки (по
  умолчанию только корни), ASP.NET `Recursive` у элемента итога (по умолчанию все узлы), WPF —
  `AllowRecursiveNodeSummaryCalculation` на грид и `IsRecursive` на элемент. Ограничения глубины
  нет.
- **AG Grid, MUI X** — значения родителя нет: агрегат строки-группы вытесняет данные строки,
  родитель всегда свод.
- **Kendo TreeList** — `sum` по поддереву вместе с родителем, выбора нет.
- **Ленивые дети.** DevExpress Blazor: загрузка по требованию и итоги несовместимы. MUI X и AG
  Grid: итог ленивого дерева считает сервер (`aggregateRow`, `grandTotalData`). Syncfusion молча
  суммирует полученные строки.

## Решение

### 1. Режим колонки

```ts
{ accessorKey: 'amount', aggregationFn: 'sum', aggregationScope: 'all' }
useCreateTable({ defaultColumn: { aggregationScope: 'all' } })
```

- `aggregationScope: 'top'` — прежнее поведение и умолчание: верхний уровень, а с
  `maxAggregationDepth` — фронт на его глубине.
- `aggregationScope: 'all'` — все строки дерева: каждая строка и все её потомки. Свёрнутые ветки
  входят: итог — по данным, а не по раскрытию. `maxAggregationDepth` в этом режиме не действует.
- Умолчание на всю таблицу — `defaultColumn.aggregationScope`; поле колонки главнее. Аргумент
  плагина для этого не подходит: значения строк-групп считает модель группировки, а собственную
  опцию чужого плагина она не читает (ADR 0163, LB5).
- Ограничения глубины нет: его нет ни у кого на рынке, а «до уровня N» задаёт своя функция.

### 2. Что получает функция агрегации

В режиме `'all'` функция получает плоский список всех строк: `sum`, `count`, `mean`, `min`,
`max`, `median`, `unique` и `extent` работают без изменений. Своя функция `{ aggregate }` в этом
режиме не спускается по `subRows` сама — иначе посчитает потомков дважды.

### 3. Поиск и фильтр

Итог — по строкам после отбора. Родитель, оставшийся в таблице как предок найденной строки
(`filterFromLeafRows`), входит в итог: итог — сумма строк, которые человек видит.

### 4. Строки-группы

При клиентской группировке поверх дерева значение строки-группы в колонке `'all'` складывает
строки группы со всеми их потомками. Сумма значений групп совпадает с итогом в футере.

### 5. Ленивое дерево

Пока часть веток не загружена, сумма загруженных строк выглядела бы настоящим итогом (как в
§5 ADR 0184). Поэтому в таблице с `loadChildren` колонка `'all'` итог на клиенте не считает:
ячейка футера пустая, значения строк-групп тоже, в разработке — предупреждение раз на колонку.
Решение — по настройке, а не по ходу загрузки: иначе ячейка была бы пустой, пока грузится
последняя ветка, и внезапно получала бы число. Колонки `'top'` считаются, как раньше: корни
загружены целиком.

### 6. Итог от приложения

```ts
columnTotals({ totals: { amount: 48_000 } })
```

Аргумент `totals` — итоги колонок, которые знает приложение (обычно сервер). Плагин показывает
их вместо своего подсчёта: в ленивом дереве, при странице с сервера, в ленте и на полных данных.
Ячейка рисуется по типу колонки, как свой итог, — свой `footer` не нужен. Аргумент живой (ADR
0039): новое значение перерисовывает футер. В серверной модели строк главнее `totals` ответа.

### 7. Серверная модель строк

Итог и значения строк-групп считает сервер. Запрос `getRows` и запрос серверной выгрузки несут
`aggregationScopes` — колонка → `'all'` для колонок в этом режиме (рядом с `aggregations`).
Новые колонки грид сверяет с запросом: сменился агрегат или его режим — новая выборка с начала
списка, как при смене сортировки; те же агрегаты — выборка прежняя. До этого ADR новые колонки
выборку не начинали, и смена `aggregationFn` доходила до сервера только со следующим запросом.

```ts
interface ServerRowsRequest {
  // …прежние поля
  /** Колонки с `aggregationScope: 'all'`: итог и агрегаты групп — по всем узлам дерева. */
  aggregationScopes: Record<string, 'all'>
}
```

## Границы

- Ограничение глубины («все уровни, но не глубже N») — нет, см. §1.
- Частичный итог ленивого дерева с пометкой «неполный» — нет: образца на рынке нет, а «всё
  загружено» в большом дереве почти не наступает.
- Сумма поддерева в ячейке строки-родителя — нет: ячейка родителя показывает его значение,
  `aggregatedCell` TanStack грид не рисует (ADR 0144, §2).
- Итоги групп (`groupTotalRow`) — вне объёма, как в ADR 0184.

## Отвергнутые альтернативы

- **Только своя функция `{ aggregate }`** — частый случай требует кода приложения, а значения
  строк-групп и запрос сервера о нём не знают.
- **Значение `maxAggregationDepth` «до уровня»** — одно поле получило бы два смысла.
- **Аргумент `columnTotals({ aggregationScope })` умолчанием таблицы** — модель группировки его не
  видит: значения групп разошлись бы с итогом.
- **Растущая сумма в ленивом дереве** — ложный итог, от которого защищает §5 ADR 0184.

## Последствия

- **+** Дерево со своими значениями родителей получает верный итог одной настройкой колонки, в
  футере, в строках-группах и на сервере.
- **+** Итог, который знает сервер, показывается без своего `footer`.
- **−** Новое поле колонки и поле запроса серверной модели: серверу нужно поддержать
  `aggregationScopes`, иначе итог будет по верхнему уровню.
- **−** Итог `'all'` обходит все строки модели: обход один на модель и кэшируется.
