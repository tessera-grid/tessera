## Контекст

Четыре плагина добавляют служебную колонку: `rowSelection` (чекбоксы), `rowExpanding`
(тоггл раскрытия), `rowDragging` (ручка), `rowActions` (кебаб действий). Колонка
вклеивается при сборке колонок (`injectServiceColumns`) один раз и от данных не
зависит: пока плагин подключён, колонка есть.

Для двух из них это даёт пустую полосу:

- `rowExpanding` в плоских данных — ни одна строка не раскрываема, колонка шириной с
  кнопку пустует;
- `rowActions` без единого действия — колонка пуста, плагин инертен с причиной
  `'noActions'` и предупреждением в dev.

Решать это в каждом плагине по отдельности — четыре реализации одного и того же
(расчёт, скрытие, навигация, закрепление, тесты). Нужен один механизм ядра, а условие
— объявление плагина.

Ограничения, которые задают форму решения:

- **Смена идентичности `columns` перестраивает модель целиком** (L1). Колонку нельзя
  добавлять и убирать в наборе колонок по данным.
- **Колонка не должна мигать.** Если условие зависит от вида (фильтр, поиск, сортировка,
  страница), колонка появлялась бы и исчезала при наборе в поиске или листании.
- `columnVisibilityFeature` в ядре есть всегда (`buildTesseraFeatures`), независимо от
  плагина `columnVisibility`.

## Решение

### 1. Условие объявляет плагин (SC1, SC8)

Объявление служебной колонки в `definePlugin` получает необязательное поле
(`core/servicePresence.ts`):

```ts
column: {
  // …id, make, side, order, pin
  /** Нужна ли колонка сейчас; без поля — нужна всегда. */
  presence?: (
    table: PresenceTable | null, // экземпляр с текущими данными; null — ещё нет
    context: NarrowContext, // текущая свёртка набора: опции и действия слотов
    opts: TOptions, // аргументы фабрики
  ) => boolean | undefined // undefined — без таблицы не посчитать
}
```

Поле живёт в объявлении плагина, а не в ядровом `ServiceColumn`: условию нужны
аргументы фабрики (`maxDepth`), а набор служебных колонок от аргументов не зависит.
`context` нужен потому, что опции `table` отстают на рендер от свёртки набора.

Колонка без `presence` показывается всегда — поведение `rowSelection` и `rowDragging`
не меняется. У плагина с `presence` появляется опция фабрики
`column?: 'auto' | 'always'` (по умолчанию `'auto'`): `'always'` показывает колонку
независимо от условия — для серверного режима, где каждая страница приходит новым
`data`. Своего условия приложение не задаёт: скрыть колонку совсем можно, не подключая
плагин или через срез видимости.

### 2. Условие смотрит на данные, а не на вид (SC2)

`presence` читает только исходные строки (`table.getCoreRowModel()`), аргументы плагина
и зарегистрированные действия. Фильтр, поиск, сортировка и пагинация на результат не
влияют: колонка меняется только с новым `data`. Временная инертность плагина колонку
тоже не убирает — при сортировке, фильтре или группировке прячутся кнопки в колонке,
как сейчас (ручки `rowDragging`, чекбоксы при группировке), а раскладка не прыгает.

Группировка у `rowExpanding` (§4) тоже не вид: колонка нужна, когда подключён плагин
`rowGrouping` (группы раскрываются её тогглом), а не когда группировка активна — иначе
колонка прыгала бы при группировке и разгруппировке.

### 3. Скрытие — эффективное состояние видимости (SC3–SC7, SC9)

Колонка остаётся в модели. Ядро сужает срез `columnVisibility` в эффективном состоянии
([ADR 0039](0039-reactive-plugin-arguments.md), `narrow`): колонка, чей `presence`
ложен, получает `false`. Отсюда:

- идентичность `columns` не меняется, модель не перестраивается; раскрытие, выбор и
  ширины переживают появление и исчезновение колонки;
- сохранённый срез не переписывается: контролируемый потребитель не получает
  `onColumnVisibilityChange`, пользовательская видимость других колонок сохраняется;
- все читатели видимых колонок (шапка, тело, `aria-colcount`/`aria-colindex`,
  клавиатурная навигация, sticky-смещения, заполнитель справа) видят колонку скрытой
  штатно. Экспорт и меню «Колонки» служебные колонки исключают и сейчас;
- ведущая колонка с `pin.when: 'with-user'` после появления присоединяется к
  закреплённому блоку, как сразу смонтированная.

Расчёт `presence` идёт при смене `data`, аргументов плагина или набора действий, а не
на каждый рендер и не при прокрутке; проход по корням останавливается на первом
подходящем. При монтировании и смене `data` условию со строками нужна таблица — слой
эффективного состояния досчитывает его повторной отрисовкой до кадра (как прочие
сужения со строками).

**Детали слоя эффективного состояния.** У плагина с `presence` сужение
`columnVisibility` есть всегда — в режиме `'always'` и у выключенного плагина
тождественное: иначе срез ушёл бы из-под сужения, и TanStack держал бы последнее
суженное значение. Срез `columnVisibility` берёт начальное значение `{}` с первого
рендера, и колбэк потребителя без контролируемого значения больше не теряет изменение —
ядро хранит срез и тогда.

### 4. Условия встроенных плагинов (RE14–RE16, RA3)

| Колонка        | `presence`                                                                                           | Опция `column` |
| -------------- | ---------------------------------------------------------------------------------------------------- | -------------- |
| `rowExpanding` | Хоть один корень исходных данных имеет детей (при `maxDepth ≥ 1`) или подключён плагин `rowGrouping` | есть           |
| `rowActions`   | Хоть один плагин добавил действие строки (то же условие, что `'noActions'`)                          | есть           |
| `rowSelection` | — (всегда): выбор — режим грида, в шапке «выбрать всё»                                               | нет            |
| `rowDragging`  | — (всегда): колонка означает, что строки можно переставлять                                          | нет            |

## Границы

- **Ленивые дети не поддержаны.** Строка раскрываема только при `subRows.length > 0`;
  раскрыть строку без детей, чтобы догрузить их в `onExpandRow`, нельзя. На сервере с
  ленивыми детьми — `column: 'always'`, сама догрузка — отдельная потребность
  (roadmap, «Известные проблемы»).
- **Условие приложения** (`column: (table) => boolean`) отвергнуто: функция легко
  начинает зависеть от вида и возвращает мигание. Добавится отдельной потребностью.
- Колонки `rowSelection` и `rowDragging` не меняются; механизм позволит добавить им
  условие одной строкой, если оно появится.

## Отвергнутые альтернативы

- **Добавлять и убирать колонку в наборе колонок.** Меняет идентичность `columns` —
  полная перестройка модели при каждом переключении.
- **Встроенный `getCanSomeRowsExpand()` TanStack.** Смотрит строки после фильтра —
  колонка мигала бы при поиске.
- **Условие в каждом плагине.** Четыре реализации скрытия, навигации и закрепления.
- **Убирать колонку при инертности плагина.** Раскладка прыгала бы при каждом клике по
  сортировке.

## Последствия

- **+** Пустых служебных колонок нет по умолчанию; поведение одно для всех плагинов.
- **+** Новая служебная колонка получает показ по условию объявлением `presence`.
- **−** Плоские данные и дерево на разных серверных страницах показывают колонку
  раскрытия по-разному — для этого `column: 'always'`.
- **−** Повторная отрисовка до кадра при монтировании и смене `data`, когда условию
  нужны строки, — перф-требование SC10.
- **Публичный API:** новая опция `column` у `rowExpanding` и `rowActions`; поле
  `presence` в объявлении колонки `definePlugin`. Ломающих изменений нет, но
  поведение по умолчанию меняется: колонки раскрытия и действий без надобности больше
  не рисуются.
