## Контекст

Документации для потребителя нет. Её роль играет `README.md` — 1520 строк на русском:
руководство по колонкам, данным, состоянию, плагинам и три гайда по своим плагинам.
`docs/architecture/` и ADR пишутся для контрибьюторов: они объясняют, как устроено ядро,
а не как подключить сортировку. Roadmap называет это главным пробелом «продуктовости»:
без документации библиотеку не начинают использовать.

Материал для сайта уже есть: 22 плагина с публичными типами в `/plugins`, UI-кит в `/ui`,
54 файла историй в тех же группах, что и фичи (Columns, Rows, Cells, Data, Panels,
Theming, UI), и CI с выпуском по тегу (ADR 0103). Песочниц на первом этапе не будет.

### Как это сделано у других

- **AG Grid** — свой движок. Getting Started, затем разделы по сущностям (Columns, Rows,
  Cells, Selection, Filtering…), Theming, API: ручные таблицы Grid Options, Grid API,
  Events. Живой пример на каждой странице.
- **MUI X Data Grid** — свой движок на Next.js. Overview, Quickstart, страница на фичу,
  Advanced (server-side, tree data), Recipes; API (props, `apiRef`, селекторы)
  **генерируется из типов**. Живые демо с «Edit in CodeSandbox».
- **TanStack Table** — markdown в репозитории, свой сайт. Core Guides (Data, Column Defs,
  Row Models…), Feature Guides, API по фичам, Examples.
- **Material React Table** — Next.js. Guides по фичам и таблицы API с поиском: table
  options, column options, state, instance.
- **react-data-grid, Glide Data Grid** — README и Storybook на GitHub Pages; связного
  текста, поиска и API-справочника нет.

Общий шаблон у сильных библиотек: начало работы → концепции → страница на фичу по единому
шаблону → кастомизация → API, сгенерированный из типов → ресурсы.

## Решение

### 1. Движок и место

Сайт — **Starlight** (Astro) в папке `website/` со своим `package.json`: зависимости сайта
не попадают в библиотеку, её сборка и тесты от сайта не зависят. Starlight работает на
Vite, как сама библиотека, собирает статику, из коробки даёт оффлайн-поиск Pagefind,
локали, светлую и тёмную тему. React-острова позволят позже встроить живой `DataGrid`
без смены движка.

Адрес — страница проекта `tessera-grid.github.io/tessera`, base `/tessera/`. Свой домен
подключается позже файлом `CNAME` без переделок. Логотип, фавикон и акцентный цвет сайта —
из `brand/`.

### 2. Языки

Две локали: английская в корне, русская — в `/ru/`. **Источник — английский**, русский —
перевод и может отставать:

- нет русской страницы — Starlight показывает английскую с пометкой «перевода пока нет»;
- у пары страниц во frontmatter `revision` — целое число, его поднимают при правке
  английской по существу. Русская с меньшим `revision` показывает плашку «перевод
  устарел», проверка при этом не падает;
- проверка падает, если у русской страницы нет английской пары или её `revision` больше
  английского: значит, правили только перевод.

`README.md` — короткая английская витрина в стиле TanStack: логотип, назначение, установка,
пример на 15 строк, ссылки на сайт и Storybook. Рядом — `README.ru.md` с тем же на
русском. Руководство из README переезжает на сайт целиком, двух копий не остаётся.

### 4. Шаблон страницы фичи

Каждая страница фичи — одни и те же разделы в одном порядке, как у MUI и AG Grid:

1. **Overview** — что делает, картинка;
2. **Usage** — как включить: фабрика плагина в `plugins`;
3. **Options** — аргументы фабрики со ссылками в API;
4. **Behavior & keyboard** — поведение мышью, клавиатурой и касанием;
5. **Server-side** — что сообщает колбэк и что делает приложение;
6. **Combinations** — сочетания с другими плагинами (ADR 0022);
7. **Localization & theming** — ключи подписей и CSS-переменные фичи;
8. **API** — ссылки на справочник и истории.

Раздел, которого у фичи нет, объявляется во frontmatter с причиной
(`notApplicable: { serverSide: 'Client-side state only' }`) — он не пропадает молча.

### 5. API-справочник и справочные списки

Справочник генерируется из публичных деклараций `.`, `/plugins` и `/ui` при сборке сайта
(TypeDoc через `starlight-typedoc`) и в git не хранится. Описания берутся из JSDoc типов;
предупреждение TypeDoc — битая ссылка, тип без экспорта — роняет сборку. Сайт собирается
в `ci.yml` на каждый пуш, поэтому сломанный справочник виден до выпуска.

Списки CSS-переменных, ключей `localization` и `icons` тоже генерируются из кода. Имя
переменной или ключа, упомянутое в тексте страницы, обязано существовать в коде.

### 6. Код, картинки, Storybook

- **Код** живёт в `website/snippets/*.tsx` и вставляется в страницы `.mdx` импортом
  (`?raw` и компонент `Code` Starlight). Сниппеты проходят `typecheck` против исходников
  библиотеки: пример, который не компилируется, не доходит до сайта. Код общий для обеих
  локалей, переводится только текст. Блоков `tsx` прямо в страницах нет.
- **Картинки** снимаются из историй скриптом `docs:shots` (Playwright по собранному
  Storybook) в светлой и тёмной теме и вставляются через `<picture>`. В git они не
  хранятся: скрипт гоняется в сборке перед публикацией.
- **Storybook** собирается публичной сборкой `build-storybook:public` — без песочниц
  `*.dev` и историй только для снимков `*.vr` (ADR 0117 §8) — и публикуется рядом, в
  `/tessera/storybook/`. Ссылка «Open in Storybook» на странице — по id истории; id обязан
  существовать в этой сборке.

### 7. Публикация

Сайт и Storybook публикуются в GitHub Pages задачей `release.yml` после гейта выпуска
(ADR 0103) — документация совпадает с выпущенной версией и не описывает невыпущенное.
Есть и ручной запуск. Версия на сайте берётся из `package.json`. Пока репозиторий
приватный, Pages работает только на платном плане GitHub; на бесплатном деплой заработает
после открытия.

Команды в корне: `docs:dev` (живой сайт), `docs:build` (сайт со справочником и
Storybook), `docs:shots` (картинки). В барьер AGENTS.md `docs:build` входит при правках
`website/` и публичных типов; в CI — всегда.

### 8. Доступность сайта

Собранные страницы проходят axe с `color-contrast` в обеих темах. Библиотека с WCAG 2.2 AA
и недоступной документацией подрывает доверие к заявлению; риск — в своих цветах поверх
темы Starlight.

## Границы

- Песочницы (StackBlitz, CodeSandbox) и живые демо в странице — следующий ADR.
- Версии документации — после 1.0.
- Algolia DocSearch — после открытия репозитория, если Pagefind не хватит.
- Свой домен, блог, отдельный дизайн главной сверх hero-блока Starlight.
- Перевод `docs/architecture` и ADR.

## Отвергнутые альтернативы

- **Docusaurus** — React-нативный, с версиями из коробки, но второй сборщик
  (webpack/rspack) рядом с Vite и тяжелее; поиск — через Algolia или плагин.
- **VitePress** — быстрый и простой, но на Vue: встроить React-демо позже неудобно.
- **Nextra, Fumadocs** — Next.js ради статики: лишний фреймворк и настройка static export.
- **Только Storybook (MDX)**, как у react-data-grid и Glide, — нет связного текста,
  поиска и навигации по разделам.
- **Русский как источник** — переводить пришлось бы на язык основной аудитории npm;
  английский-источник оставляет её с полной и свежей версией.
- **Ручные таблицы API** (AG Grid, Material React Table) — расходятся с типами; у нас
  типы — источник правды и уже несут JSDoc.
- **Публикация на каждый пуш** — сайт обещал бы невыпущенное.
- **Страница организации** `tessera-grid.github.io` — нужен отдельный репозиторий и деплой в
  него; у страницы проекта адрес тот же по сути и без второго репозитория.

## Последствия

- **+** Потребитель находит, как включить фичу, по одной ссылке, на своём языке, с поиском.
- **+** Справочник, сниппеты, ключи и ссылки на истории не расходятся с кодом: их проверяют
  сборка и стражи.
- **+** Каждая фича описана по одному шаблону — сравнимо от страницы к странице.
- **−** Фича дорожает на страницу на английском и её перевод; DC3 напоминает об отставании,
  но не блокирует.
- **−** Около 45 страниц на первом проходе; руководство из README переписывается под
  шаблон, а не переносится как есть.
- **−** Пять новых dev-зависимостей в `website/`: `astro`, `@astrojs/starlight`,
  `starlight-typedoc`, `typedoc`, `typedoc-plugin-markdown`.
- **−** Сборка сайта со справочником и Storybook добавляет минуты в CI.
