# 0139 — Сохранённая строка правки и тип данных колонки

- **Статус:** Принято (решения — по итогам прожарки 2026-10-26)
- **Дата:** 2026-10-26
- **Изменяет:**
  - [ADR 0138](0138-server-side-row-model.md) — §7 и SD24: успех правки ячейки обновляет
    кэш серверной модели строкой из ответа `onCellEdit` или разобранным значением по
    этому ADR, а не строкой редактора по `accessorKey`.
  - [ADR 0041](0041-async-business-callbacks.md) — §2: `onCellEdit` может вернуть
    сохранённую строку — сразу или промисом.
- **Связано:**
  - [ADR 0040](0040-action-sessions.md) — сессия правки и её итог.
  - [ADR 0045](0045-filtering.md) — тип фильтра колонки остаётся настройкой фильтра; связь
    фильтра с `dataType` — вне объёма.

## Контекст

В серверной модели строк данных у приложения нет: строки держит кэш блоков грида
(ADR 0138). Успех правки писал в кэш значение редактора по `accessorKey` колонки. Это
догадка с тремя краями:

- редактор отдаёт текст, и числовое поле получает строку `"42"` — свой рендер ячейки
  вроде `price.toFixed(2)` падает, выгрузка получает текст;
- колонка с `accessorFn` не пишется вовсе, а грид молчит;
- вложенный путь `a.b` пишется плоским ключом.

Поля, которые посчитал сервер (округление, `updatedAt`), в кэш не попадают — до
`refreshRows` ячейка показывает введённое, а не сохранённое.

### Как у других

| Библиотека | Источник истины после правки                                                                                                                                                                                                                                                                                                                              |
| ---------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| AG Grid    | Тип данных колонки `cellDataType` (`text`, `number`, `boolean`, `date`/`dateTime` — объекты `Date`, `dateString`/`dateTimeString` — строки ISO, свои типы). От типа — разбор ввода `valueParser`, формат, редактор и фильтр. В клиентской модели тип выводится из данных, в SSRM — только явно. Пишет `field` (путь с точками — вглубь) или `valueSetter` |
| MUI X      | `processRowUpdate(newRow, oldRow)` возвращает строку — грид хранит её; значение до этого разбирают `valueParser` и `valueSetter` колонки, тип колонки `type: 'number'` разбирает число                                                                                                                                                                    |

## Решение

### 1. Сохранённая строка из ответа

`onCellEdit` может вернуть сохранённую строку — сразу или промисом:
`(commit) => TData | void | Promise<TData | void>`. Строка — объект с тем же id, что у
правленой строки: по `getRowId` таблицы, без него — по полю `id`. Другой ответ (например,
`Response` от `fetch`) строкой не считается. В серверной модели строк она
заменяет строку в кэше (`setRowData`), перерисовывается только эта строка. Это главный
путь: сервер знает итог точнее грида — посчитанные поля, округление, типы.

### 2. Тип данных колонки и разбор ввода

Когда строки в ответе нет, значение для записи разбирается из текста редактора:

- `parseValue(text, row)` колонки — свой разбор, главнее всего (аналог `valueParser`);
- иначе по `dataType` колонки: `'number'` — число; `'boolean'` —
  `true`/`false` без учёта регистра; `'date'` — объект `Date`; `'dateString'` — строка
  `YYYY-MM-DD`; `'text'` — как есть; пустое поле у всех типов, кроме `'text'`, — `null`;
- без `dataType` тип выводится из прежнего значения самой ячейки: число, булево или
  `Date`. Строка или пусто — `'text'`. В серверной модели прежнее значение лежит в кэше,
  поэтому вывод работает и там, в отличие от вывода AG Grid по колонке.

`dataType` и `parseValue` — поля колонки ядра, а не плагина фильтров: тип значения
нужен правке независимо от того, подключены ли фильтры.

### 3. Запись в кэш

- Вложенный путь `accessorKey` (`a.b`) пишется вглубь, остальные поля строки не
  меняются.
- Колонка с `accessorFn` — писать некуда; значение, которое не разбирается (`"abc"` в
  числовой колонке, `"maybe"` в булевой), — тоже не пишется. Кэш не меняется, в консоли
  браузера — совет вернуть строку из `onCellEdit` или задать `dataType`/`parseValue`.

### 4. Клиентский режим

Данными владеет приложение (ADR 0041): ни возвращённая строка, ни разобранное значение
никуда не пишутся. Приложение обновляет `data` само.

## Границы

- Формат показа по `dataType`, фильтр и выгрузка по умолчанию от `dataType`, свои типы
  (`dataTypeDefinitions`) — отдельным ADR.
- Разобранное значение в `commit` для клиентского режима — по запросу отдельным
  требованием.
- Своя запись значения (`valueSetter`) — нет: путь `accessorKey` и строка из ответа
  покрывают запись.

## Отвергнутые альтернативы

- **Значение редактора по `accessorKey` как есть** (прежнее поведение). Текст в числовом
  поле ломает рендер и выгрузку, `accessorFn` молчит.
- **Тип по фильтру колонки.** Связывает правку с настройкой фильтра; вид хранения даты
  из типа фильтра не понять.
- **Ничего не писать без строки из ответа.** Правка на глазах откатывается к прежнему
  значению кэша.
- **Только `setRowData` приложения.** Приложение, которое забыло вызов, видит тот же
  откат.

## Последствия

- **+** Кэш серверной модели после правки совпадает с сервером, когда приложение
  возвращает строку; без неё — значение верного типа.
- **+** `dataType` — основа для формата, фильтра и выгрузки по типу в следующих ADR.
- **−** Вывод типа из значения ячейки — догадка: пустая ячейка числовой колонки без
  `dataType` получит строку.
- **Публичный API:** поля колонки `dataType` (`'text' | 'number' | 'boolean' | 'date' |
'dateString'`) и `parseValue(text, row)`; тип `onCellEdit` расширен до
  `TData | void | Promise<TData | void>` — не ломающее изменение.
