# 0181 — Id новой строки задаёт таблица

- **Статус:** Принято (решения — по итогам прожарки 2026-11-04)
- **Дата:** 2026-11-04
- **Слой:** плагин `cellEditing` — id новой строки, слой строк до сохранения и разбор ответа
  пакета; утилита `util/randomId`. Плагин `serverRowModel` — приход строки транзакцией без вспышки,
  когда строка уже стояла на экране. Ядро — активная ячейка держит строку по `id`
  (`keyboardNavigation/followActiveCell`): это слежение за списком, оно уже в ядре.
- **Изменяет:**
  - [ADR 0178](0178-drafts.md) §7 — новая строка получает постоянный id сразу (прежде —
    временный `tsr-new-row:…`); сохранённая строка под этим id — та же строка; в серверной модели
    черновик новой строки держится до записи строки в кэш.
  - [ADR 0157](0157-ssrm-row-transactions.md) §4 — строка, добавленная транзакцией, не вспыхивает
    «пришла» и не объявляется, если она уже стояла на экране.
  - [ADR 0157](0157-ssrm-row-transactions.md) §3 — активная ячейка держит свою строку по `id`:
    журнал вставок не видит строк слоя поверх источника, и без этого новая строка, легшая в кэш
    под тем же `id`, сдвигала бы ячейку на строку ниже; строки по `id` нет — сдвиг по журналу.
- **Связано:**
  - [ADR 0107](0107-row-motion.md) — движение строк по `id`.
  - [ADR 0139](0139-saved-row-and-column-data-type.md) — сохранённая строка из ответа.

## Контекст

Новая строка до сохранения жила под временным id (`tsr-new-row:…`, ADR 0178, §7). Сервер
создавал запись в базе со своим ключом, и сохранённая строка приходила под другим id. Для грида
это другая строка: движение строк гасило временную и проявляло сохранённую, а состояние по id —
выбор, фокус, подсветки — оставалось у временной. Передача состояния со старого id на новый
требовала бы всем срезам помнить пару id и ломалась на порядке событий: приложение пишет строку в
`data` раньше, чем грид разбирает ответ, — на кадр видны обе строки, затем сохранённая «выезжает
снизу».

Как у других: в MUI X Data Grid id новой строки создаёт клиент (`randomId()`) и сохраняет как
есть; в AG Grid id даёт приложение и он не должен меняться; в DHTMLX и TreeGrid сервер возвращает
новый id, и сетка переименовывает строку. Современные приложения обычно создают UUID на клиенте, и
сервер принимает его ключом записи — переименования нет вовсе.

## Решение

### 1. Id выдаёт таблица

`addRow` выдаёт новой строке уникальный постоянный id — UUID (`crypto.randomUUID`, без HTTPS — из
`crypto.getRandomValues`). Этот id — `rowId` вставки в пакете `onCommitEdits`; приложение и сервер
сохраняют строку под ним. Новую строку отличает её черновик `rowInsert`, а не вид id.

**Рекомендация приложению:** id строки не менять — сохранять новую строку под id, который выдала
таблица, и возвращать в ответе `saved` строку с тем же id. Ключ базы, если он свой, — отдельным
полем строки. Строка под другим id для таблицы — другая строка; в разработке — предупреждение.

### 2. Сохранённая строка — та же строка

- **Клиентский режим.** Приложение вставляет сохранённую строку в `data` под тем же id. Пока
  черновик есть, а строка с этим id уже в `data`, слой новую строку не рисует: в таблице одна строка
  — в том числе когда приложение отрисовало `data` раньше, чем грид разобрал ответ.
- **Серверная модель.** Строка ложится в кэш транзакцией после кадра (ADR 0157). Черновик новой
  строки держится до записи, затем снимается: строка не пропадает между ответом и записью. Её
  приход не вспыхивает «пришла» и не объявляется — строка уже стояла на экране.

Состояние по id — выбор, подсветки, вспышка «принято» — остаётся у строки само: id тот же.
Активная ячейка держится за индекс; в серверной модели она теперь держит свою строку по `id`, а
сдвиг по журналу — только когда строки по `id` нет.
Движение строк (ADR 0107) видит ту же строку на том же месте — ни призрака, ни проявления.

## Границы

- **Сервер со своим ключом** — приложение хранит ключ базы отдельным полем строки, id строки —
  выданный таблицей. Переименования строки нет.
- **Свой id новой строки от приложения** — нет: источник id новой строки — таблица.

## Отвергнутые альтернативы

- **Переименование строки по ответу**: пара «временный → постоянный», перенос состояния ядра и
  плагинов отдельным полем контракта плагина, ожидание строки в `data`. Каждый срез обязан помнить
  про старый и новый id, а порядок «приложение пишет `data` раньше разбора ответа» даёт кадр с двумя
  строками (решение автора 2026-11-04).
- **Только движение строк** — лечит один симптом: состояние по id остаётся у временной строки.
- **Эвристика «ушла одна, пришла другая на том же месте»** — угадывание.

## Последствия

- **+** Новая строка до и после сохранения — одна строка: место, выбор, фокус и подсветки остаются
  без кода переноса.
- **+** Порядок «`data` раньше разбора ответа» безопасен.
- **−** Приложение, чей сервер выдаёт ключи, хранит ключ базы отдельным полем.

## Внедрение

- **Этап 1** (NI1–NI5; S1): id новой строки — `util/randomId` в `addRow`; слой строк до сохранения
  не рисует новую строку, чей id уже в данных; черновик новой строки серверной модели — до записи в
  кэш; без вспышки прихода уже видимой строки в `serverRowModel`; предупреждение о смене id.
