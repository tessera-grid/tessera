# 0103 — CI и выпуск версий

- **Статус:** Принято (решения — по итогам прожарки 2026-10-13)

## Контекст

Барьер (AGENTS.md §4) гоняется только локально: на Windows, руками, по просьбе. Полный
прогон — около 20 минут, из них `npm test` — около 15. Ничто не мешает закоммитить
красное, а снимки каталога состояний (ADR 0093) и регрессия перфа на PR (ADR 0099) ждут
CI с первых дней.

Репозиторий на GitHub приватный: Actions даёт 2000 минут в месяц, на двухъядерном
раннере полный барьер займёт 30–45 минут. Открытие репозитория и публикация в npm — после
английского README и смены git-процесса; этот этап их не включает.

Выпуска версий нет совсем: `package.json` — `0.0.1` без лицензии и ссылки на
репозиторий, тегов и CHANGELOG нет. Автор хочет сам решать, когда выходит версия, и сам
решать, что в CHANGELOG, — одной командой, руками или через агента.

### Как это сделано у других

- **TanStack** — версия на каждый влитый в `main` коммит с `feat`/`fix`: скрипт CI выводит
  её из Conventional Commits и публикует.
- **MUI, Base UI** — выпуск примерно раз в неделю: дежурный запускает его, CHANGELOG
  собирается из PR и правится руками.
- **Radix, dnd-kit** — Changesets: описание к каждой правке, «PR релиза» копит их; влили —
  CI публикует.
- **React, React Aria** — плюс канал `canary`/`nightly` на каждый коммит.

Везде публикует CI, а тяжёлые проверки — гейт перед публикацией. Различается, кто
нажимает «выпустить».

## Решение

### 1. Барьер на каждый пуш

Workflow `ci.yml` на пуш в `master` и на `pull_request` гоняет весь барьер: формат, линт,
типы, сверка требований, `npm test` (со счётчиками работы, PF20), сборка, tree-shaking,
инварианты темы, порог браузеров, `test:browsers`. Пока работа идёт на `master`, триггер
PR не срабатывает; после перехода на ветки — заработает без правок.

`npm test` делится на шарды (`vitest --shard`): несколько раннеров параллельно, минуты те
же, время по часам короче. Скриншоты и логи упавшего шарда — архивом прогона. Новый пуш
в ту же ветку отменяет идущий прогон. Окружение — как у разработчика: Node из `.nvmrc`,
`npm ci` по lockfile, браузеры Playwright из кэша.

### 2. Перф

`perf:compare` (ADR 0099) — ручной запуск с ревизией и набором кейсов; отчёт и дашборд —
архивом. Задачи на PR (`PR_CASES` против базы PR) и ночная (против последнего тега; пока —
`PR_CASES`: всю матрицу `perf:compare` брать не умеет, PF21 ждёт этого) лежат в том же workflow с условием «репозиторий публичный»: в приватном они не
тратят минуты, после открытия включаются сами.

### 3. Снимки — Chromatic

На пуш в `master` и на PR CI собирает Storybook и отдаёт его `chromatic` с TurboSnap
(ADR 0093, §6). Токен — секрет `CHROMATIC_PROJECT_TOKEN`; без него шаг падает с понятной
ошибкой, остальной барьер это не задевает.

### 4. Шаги перед публикацией

`test:engines`, `test:react18` и `check:package` идут раз в неделю при новых коммитах,
обязательным гейтом выпуска и по кнопке. Неделя — чтобы регрессию в Firefox, WebKit или
React 18 увидеть не в день выпуска.

### 5. Выпуск — одна команда

Автор решает, когда выходит версия; агент может подготовить черновик и выпустить по
просьбе.

- **`npm run release:draft -- [patch|minor|major]`** вписывает в `CHANGELOG.md` раздел
  следующей версии и ничего не коммитит. Раздел собирается из Conventional Commits с
  прошлого тега: «Breaking changes» (`!` или `BREAKING CHANGE`), «Features» (`feat`),
  «Fixes» (`fix`), «Performance» (`perf`); `chore`, `test`, `docs`, `refactor`, `style`,
  `build`, `ci` скрыты. Агент переводит его на английский, автор правит.
- **`npm run release -- [patch|minor|major]`** выпускает. Отказывает, если рабочая копия
  грязная (подготовленный `CHANGELOG.md` — не грязь), ветка не `master`, есть расхождение с `origin` или CI на HEAD не зелёный. Без
  уровня предлагает его по коммитам и показывает, какие коммиты его определили. Готовый
  раздел следующей версии берёт как есть; если раздела нет — собирает черновик и
  открывает его в редакторе git. Затем просит подтверждения (`--yes` — без вопроса, для
  агента после согласия автора), поднимает версию в `package.json` и lockfile, делает
  коммит `chore(release): vX.Y.Z` и тег `vX.Y.Z`, пушит.
- **Уровень по SemVer.** До 1.0 ломающее изменение поднимает minor, остальное — patch:
  `^0.1.0` у потребителя разрешает только `0.1.x`. С 1.0 — ломающее major, `feat` minor,
  остальное patch. 1.0 — решение автора («API устоялся»), его не выводят из коммитов.
- **Пуш тега** запускает `release.yml`: гейт (барьер и шаги перед публикацией) и черновик
  GitHub Release с текстом раздела. Публикации в npm на этом этапе нет — она добавится в
  тот же workflow при открытии.

Инструкция — `docs/releasing.md`.

### 6. Лицензия и метаданные пакета

`LICENSE` — MIT, как у TanStack, MUI X Community, AG Grid Community, dnd-kit и Base UI.
В `package.json` — `license`, `repository`, `homepage`, `bugs`, `engines`; publint в
`check:package` проверяет поля.

### 7. Язык

`CHANGELOG.md` — на английском: его читают потребители на GitHub и npm. Это исключение
из правила «все `.md` — на русском» (AGENTS.md); README и правило языка в целом —
отдельный ADR вместе с английским README.

## Границы

- Открытие репозитория, публикация в npm, английский README, переход на рабочие ветки —
  следующий этап.
- Каналы `canary`/`nightly` — после открытия, если понадобятся.
- Свой раннер — нет железа.

## Отвергнутые альтернативы

- **release-please** — сам держит PR релиза и сам пишет CHANGELOG из коммитов; автор хочет
  решать и то, и другое.
- **Changesets** — описание к каждой правке и новая зависимость; Conventional Commits уже
  несут ту же информацию.
- **Версия на каждый коммит** (TanStack) — до 1.0 с ломающими изменениями потребители
  получали бы их без выбора.
- **Шаги перед публикацией на каждый пуш** — около 35 минут сверху к прогону; в
  приватном репозитории это половина бюджета.
- **Полный барьер только по ночам** — регрессия видна на следующий день.

## Последствия

- **+** Красный коммит виден сразу, на том же окружении для всех.
- **+** Выпуск — одна команда, CHANGELOG пишет человек, публикует CI.
- **+** Снимки каталога сравниваются на каждый пуш.
- **−** Барьер подбирался на Windows: первые прогоны на Linux почти наверняка дадут
  красные визуальные и тайминговые тесты — их починка входит в этап.
- **−** Бюджет 2000 минут в месяц: около 50 прогонов; пушим пачками коммитов.
- **−** Chromatic принимает изменения вида человеком в веб-интерфейсе.
