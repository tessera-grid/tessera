# 0026 — Миграция на TanStack Table v9

- **Статус:** Принято
- **Дата:** 2026-09-13

## Контекст

[ADR 0004](0004-core-on-tanstack-table.md) поставил ядро на TanStack Table v8. Его
архитектурное ограничение: любое изменение состояния или данных пересчитывает **всю**
модель таблицы. [ADR 0007](0007-reactivity-pubsub.md) (собственный Pub-Sub) смягчает
последствия на уровне React-ре-рендеров, но саму пересборку модели не устраняет.
[roadmap](../roadmap.md) держит миграцию на v9 в статусе «на рассмотрении».

Проведён RnD и спайк (ветка `feat/tanstack-v9`, [docs/research/](../research/),
`spike/tanstack-v9/`). Собраны два входа для решения.

> Спайк удалён после завершения миграции; последний коммит, где он есть, —
> `bbc7bb5` (`git show bbc7bb5:spike/tanstack-v9/README.md`).

### Вход 1 — v8-базлайн производительности (доказательство проблемы)

`npm run perf`, Chromium, throttle CPU 4×. Полный снимок —
`spike/tanstack-v9/perf-baseline-v8.json` в коммите `bbc7bb5` (снят 2026-09-12).

| Сценарий (размер / плагины) | Render, longest (бюджет 1000 мс) | Scroll Y p95 (бюджет 16.67 мс) | Scroll X p95              |
| --------------------------- | -------------------------------- | ------------------------------ | ------------------------- |
| 30×500 / нет                | 173 мс ✅                        | 17.8 мс                        | 47.1 мс                   |
| 1000×1000 / нет             | 359 мс ✅                        | 41.7 мс                        | 101.5 мс                  |
| 30×500 / все                | 660 мс ✅                        | 95.4 мс                        | 155.1 мс                  |
| 1000×1000 / все             | **2876 мс ❌**                   | 178.7 мс                       | **396.9 мс** (TBT 13.2 с) |

Итого: 3/12 метрик в бюджете, остальное — признанные shortfall'ы (`knownShortfall`,
[ADR 0009](0009-test-coverage-visual-and-performance.md)). Стоимость **резко** растёт
с числом плагинов и объёмом данных — сигнатура пересчёта всей модели. Именно этот край
и целевой для v9.

### Вход 2 — спайк на реальном v9 (доказательство решения)

`@tanstack/react-table@9.2.4` (алиас `@tanstack/table-v9`, сосуществует с v8). Все пять
открытых вопросов [плана](../research/tanstack-table-v9-migration-plan.md) закрыты, см.
`spike/tanstack-v9/README.md` (коммит `bbc7bb5`):

- **Реактивность / снос Pub-Sub — подтверждено запускаемым тестом (3/3).** Состояние v9
  живёт в TanStack Store; `table.atoms.<slice>` слайс-адресуемо (незатронутый срез
  сохраняет референсную идентичность). `useSelector(table.atoms.X)` даёт ровно ту
  гранулярность, ради которой написан `src/lib/core/subscribeStore/` → его можно удалить.
- **Плагинная модель** переносима: v8 `TableFeature` (`create*`) → v9
  (`assign*Prototype`/`constructTableAPIs`/`getDefaultTableOptions`); подтверждено портом
  среза `commonPlugin`.
- **Рендер** — нативный `FlexRender` заменяет самописный `render`→`columnDef` (Q1).
- **Presence-based** композиция ложится на `tableFeatures()` с компромиссом по типам (Q2).
- **`keepFeatureWhenDisabled`** скорее не нужен (Q4).
- **Дженерики** — `TFeatures` ведущий; `hooks`/`slots` едут как опции фичи, а не глобальные
  дженерики (Q5). `createColumnHelper<typeof features, T>()` компилируется; основной
  typecheck репозитория при установленном v9 не сломан.

Блокеров, делающих миграцию невозможной, не обнаружено.

## Решение

**Мигрировать ядро Tessera на TanStack Table v9** — поэтапно, по
[плану миграции](../research/tanstack-table-v9-migration-plan.md) (фазы A–G), с главным
архитектурным следствием: **удалить собственный Pub-Sub** ([ADR 0007](0007-reactivity-pubsub.md)
переходит в отменённый статус, заменяясь штатным store v9).

Условие go/no-go: миграция считается успешной, только если постмиграционный
`npm run perf` **не хуже** зафиксированного v8-базлайна (Вход 1) по каждой метрике, а в
сценариях «все плагины»/большой объём — ощутимо лучше (иначе ключевой мотив не
подтверждён и решение пересматривается).

Дисциплина исполнения (из плана): parity-тесты [ADR 0010](0010-invert-core-plugins-registry.md)
и покрытие [ADR 0009](0009-test-coverage-visual-and-performance.md) держатся зелёными
пофазно; переименования (`start/end`, `sortFn`, sizing/resizing split) — точечным
аудитом; дистрибутив (ESM-only) — отдельным решением внутри фазы F.

## Последствия

- **+** Снимается корневое перф-ограничение v8; собственный Pub-Sub и часть
  мемоизационных костылей в `useCreateTable` удаляются — меньше нашего кода.
- **+** Гранулярные подписки, tree-shaking фич, переписанные devtools — из коробки.
- **+** Снимается «известная проблема» roadmap «Pub-Sub на масштабе».
- **−** Major-переписывание ядра (недели): самое дорогое — типовой слой (`TFeatures`) и
  `commonPlugin`; дерево не зелёное до конца блока фаз A–C.
- **−** Ломающие изменения API для потребителей (пиннинг `start/end`, ESM-only,
  дженерик `TFeatures`) — вероятен мажорный релиз Tessera.
- **Отменяет** [ADR 0007](0007-reactivity-pubsub.md) после завершения фазы D (до тех пор
  Pub-Sub жив). Ссылается на [ADR 0004](0004-core-on-tanstack-table.md) (v8) как
  предшественника.
- **Пересмотр:** статус → «Принято» только после постмиграционного перф-замера,
  подтверждающего условие go/no-go; иначе → «Отклонено» с фиксацией причин.

## Требования

- **V9-1.** Постмиграционный `npm run perf` не хуже v8-базлайна по каждой метрике.
- **V9-2.** Собственный Pub-Sub (`src/lib/core/subscribeStore/`) удалён; реактивность —
  на `table.atoms`/`table.store`.
- **V9-3.** Все существующие требования плагинов (ADR 0011–0025) остаются покрытыми
  зелёными тестами после миграции их плагинов.
