## Контекст

В серверном режиме (`server: true`) грид не сортирует, не фильтрует и не режет строки:
он меняет срез состояния и сообщает о нём колбэком — `onToggleColumnSort`,
`onFilterChange`, `onSearchChange`, `onPageChange`. Колбэки возвращают `void`, их
результат игнорируется (ADR 0041, §1). Остальное приложение делает само:

1. **Отсекает устаревшие ответы** — номер запроса или свой `AbortController`.
2. **Показывает ожидание** — проп `loading: 'refresh'` (ADR 0094). Свечение общее:
   пользователь не видит, какое действие ждёт ответа.
3. **Показывает отказ** — `loadError` и `onRetry` (ADR 0096).
4. **Откатывает состояние** — через контролируемый `state`. Без этого после отказа
   стрелка сортировки, номер страницы и фильтр показывают то, чего в данных нет.

Демо серверной пагинации пишет пункты 1–2 вручную, а отказ не обрабатывает вовсе.
ADR 0094 отнёс индикатор у причины к асинхронным колбэкам, ADR 0096 — подключение
серверных плагинов к плашке оставил приложению. Образец готов: правка ячейки (ADR 0041),
перенос строк и колонок (ADR 0112, 0114) ведут промисом ожидание у причины и отказ.

Как в других гридах:

| -------------- | -------------------------------------------- | --------------------------------------------------------------------------- | ----------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------- |

## Решение

### 1. Промис от колбэков серверного режима (SA1)

В серверном режиме колбэки могут вернуть промис:

```ts
interface ServerActionContext {
  signal: AbortSignal
}
type ServerActionResult = void | PromiseLike<unknown>

// columnSorting
onToggleColumnSort: (
  id: string,
  direction: SortDirection | false,
  context: ServerActionContext,
) => ServerActionResult
// columnFiltering
onFilterChange: (filters: ColumnFilterEntry[], context: ServerActionContext) =>
  ServerActionResult
// quickSearch
onSearchChange: (
  search: string,
  scope: SearchScope,
  context: ServerActionContext,
) => ServerActionResult
// pagination
onPageChange: (
  pageIndex: number,
  pageSize: number,
  context: ServerActionContext,
) => ServerActionResult
```

- Промис — запрос данных под новое состояние. Приложение заменяет `data` до выполнения
  промиса — как при правке ячейки (ADR 0041, §2), иначе под подтверждённым состоянием
  мелькнут прежние строки.
- Синхронный результат — успех сразу, как сейчас.
- В клиентском режиме результат игнорируется: вид грид уже посчитал сам, ждать нечего.
- Когда колбэк зовётся, не меняется: фильтр и поиск — после дебаунса (ADR 0045, §10),
  программная смена среза колбэк не зовёт (PG6) и ожидания не начинает.

### 2. Один запрос, замена и подтверждённое состояние (SA2–SA3)

Сортировка, фильтры, поиск и страница вместе задают один серверный запрос: приложение
перезапрашивает данные со всеми четырьмя. Поэтому ожидание у грида одно.

- **`signal`** прерывается следующей сменой любого из четырёх срезов и размонтированием.
  Итог прерванного вызова игнорируется: ни ожидания, ни отказа, ни отката. Пользователям
  TanStack Query `signal` не нужен — запрос отменяет смена ключа; остальным он заменяет
  номер запроса.
- **Замена.** Действие во время ожидания не блокируется: контролы живые (ADR 0094, §2).
  Новое действие прерывает прежнее и становится ожидающим.
- **Подтверждённое состояние** — сортировка и страница перед первым действием цепочки
  ожидания: в покое срезы подтверждены, в том числе программная смена приложения.
  Успех цепочки подтверждает текущие значения. Откат идёт к подтверждённому состоянию, а
  не к значению перед последним действием: «сортировка A → страница 3 → отказ»
  возвращает и сортировку, и страницу.

### 3. Ожидание у причины и свечение (SA4–SA6)

- **Причина** — контрол, начавший действие: кнопка сортировки колонки (сортировка из
  кебаба — сам кебаб, ADR 0078; с клавиатуры — кнопка сортировки заголовка), нажатый
  контрол пагинатора (страница, «вперёд/назад», размер страницы), кнопка фильтра
  колонки. Пока промис не выполнен, причина горит светом ожидания ADR 0095 и помечена
  `aria-busy`. Замена гасит свет прежней причины. Поле быстрого поиска своего света не
  несёт: ожидание поиска — свечение под шапкой (решение 2026-10-15).
- **Свечение обновления.** Пока промис не выполнен, грид сам включает свечение под шапкой
  (ADR 0094) с задержкой и минимумом показа из `refreshOptions` — проп `loading` не нужен.
  Проп `loading: 'refresh'` приложения складывается с ним: свечение горит, пока ждёт любой
  из двух. Скелет `loading: 'initial'` главнее, как прежде.
- Ожидание живёт в срезе ядра, а не в компоненте причины: колонка или строка, ушедшая из
  окна виртуализации и вернувшаяся, снова горит.

### 4. Отказ: откат кликов, черновик полей (SA7–SA10)

- **Клики откатываются.** Сортировка и страница с её размером возвращаются к
  подтверждённому состоянию — вместе со сбросом страницы, который вызвала сортировка.
  Откат идёт через `setSorting` / `setPagination`, то есть и через `onSortingChange` /
  `onPaginationChange` контролируемого состояния. Колбэки действий откат не зовёт: это не
  действие пользователя и не новый запрос (как PG6). Суженная сортировка (ADR 0039,
  `multiSort`) доходит до TanStack рендером, и клиентская пагинация сбрасывает страницу
  тогда же — страница возвращается после этого сброса.
- **Поля остаются черновиком.** Текст поиска и значения фильтра не откатываются —
  введённое не теряется, как черновик правки (ADR 0041). Следующая правка или повтор
  отправляют значения снова. Отметки отказа — §5.
- **`revertOnReject`** — у `columnSorting` и `pagination`, по умолчанию `true`, живой
  аргумент (ADR 0039), как у перетаскивания (ADR 0114, §4). `false` — сортировка и
  страница остаются новыми с меткой ошибки, как у полей: расхождение с данными
  допускается осознанно.

### 5. Видимость отказа (SA11–SA12)

- **Плашка ADR 0096.** Отказ показывает красный свет под шапкой и плашку с причиной: текст
  отказа по правилу AS10, иначе подпись отказавшего действия. «Повторить» повторяет
  отказавшее действие с теми же аргументами — откаченное применяется снова и снова ждёт.
  `loadError` приложения главнее: при нём плашка показывает ошибку приложения и его
  `onRetry`. Ошибку грида снимает успех следующего действия или «Закрыть».
- **У причины** — вспышка `errorFlash` (ADR 0055); отказ объявляется в live-области
  вместе с причиной.
- **Кнопка фильтра колонки** — как кнопка раскрытия строки (ADR 0055, ADR 0095): свет
  ожидания, при отказе — красный свет. Когда он гаснет, на кнопке колонок, чьи значения
  ушли в отказавший запрос, остаётся `ErrorDot` — как отметка отказа на кебабе
  (ADR 0078). В открытой панели фильтра такой колонки внизу, рядом с кнопкой сброса, —
  иконка ошибки с тултипом причины. Решение 2026-10-15.
  `aria-invalid` на кнопке ARIA не допускает: причина — описание кнопки.
- **Поле поиска** — без света, вспышки и отметок: ожидание поиска — свечение под шапкой,
  отказ — красный свет и плашка с причиной и «Повторить» (решение 2026-10-15).
- **Снятие отметки** кнопки фильтра — успех следующего действия или «Закрыть» плашки.
  Пока ждёт повтор или новая правка, вместо отметки — свет ожидания.

### 6. Клавиатура и сочетания (SA13–SA14)

- Сортировка `Enter` на заголовке и контролы пагинатора с клавиатуры ведут то же ожидание
  и откат; фокус остаётся на причине — с `keyboardNavigation` и без него.
- **Лента** (ADR 0081): промис сортировки, фильтра и поиска ведёт себя так же; свою
  загрузку лента отменяет прежним механизмом (IS7).

### 7. Реактивность (SA16)

Ожидание и отказ — срез ядра (модуль вне папок плагинов: им пользуются четыре плагина,
IV3). Подписаны на него причины, свечение и плашка; строки тела — нет. Подтверждённое
состояние рендер не читает и в срез не входит.

## Отвергнутые альтернативы

- **Единый загрузчик `dataSource.getRows`** (MUI X, AG Grid SSRM). Грид владел бы
  данными — это отвергнуто в ADR 0081; по сути это первый шаг SSRM, решение уровня
  «Server-Side Row Model» из roadmap.
- **Не откатывать** (MUI X, AG Grid). Контролы показывают состояние, которого нет в
  данных: стрелка сортировки врёт до следующего успешного запроса.
- **Откатывать и поля.** Введённый текст поиска и значения фильтра пропадают — их
  пришлось бы набирать заново.
- **Только вспышка и объявление** (как отказ переноса колонки, ADR 0114). Причина отказа
  данных не видна на экране.
- **Постоянная метка у кнопки сортировки** (как пункты меню, ADR 0078). Метка на
  заголовке каждой отказавшей колонки засоряет шапку; плашка показывает причину один раз.
- **Блокировать контролы на время ожидания.** Медленный сервер мешает работе; ADR 0094
  уже отверг модальную блокировку.
- **`signal` на каждый срез.** Запрос один — смена любого среза делает прежний ответ
  устаревшим.
- **Учитывать промис и в клиентском режиме.** Вид уже посчитан; ждать нечего.

## Границы

- Выбор строк, видимость, закрепление, ширина колонок и группировка — не здесь: это
  локальное состояние, сохранять настройки можно без ожидания ответа.
- `signal` у правки ячейки, раскрытия, переноса и пунктов меню — не здесь.
- Server-Side Row Model, кэш блоков, автоповтор, тосты — не входят.
- Серверная выгрузка (`onExport`) — отдельная задача. Выгрузка `view` во время ожидания
  берёт текущее, ещё не подтверждённое состояние.

## Последствия

- **+** Приложение не пишет номер запроса, флаг загрузки, ошибку и откат: промис и
  `signal` закрывают их.
- **+** Пользователь видит, какое действие ждёт ответа, и после отказа контролы не врут.
- **−** **Смена поведения.** `async`-обработчики, чей промис сейчас молча игнорируется,
  начнут показывать ожидание и откатывать состояние при отказе.
- **−** Плашка показывает ошибку из двух источников — правило приоритета (§5).
- **−** Приложение с контролируемым состоянием, которое само откатывает его при ошибке,
  получит откат грида повторно; ему — `revertOnReject: false`.
- **Публичный API:** результат четырёх колбэков — `void | PromiseLike<unknown>`, последним
  аргументом — `ServerActionContext` (`{ signal }`); опция `revertOnReject` у
  `columnSorting` и `pagination`; подписи отказа четырёх действий и объявление отказа (в
  CHANGELOG).

## План внедрения

1. **Этап 1 — контракт и откат.** Модуль ядра серверных действий: ожидающий запрос,
   `signal`, замена, подтверждённое состояние, откат сортировки и страницы через сеттеры
   таблицы, `revertOnReject`; промис и `{ signal }` в четырёх колбэках. Тесты SA1–SA3,
   SA7–SA8, SA10.
2. **Этап 2 — вид ожидания и отказа.** Свет у причины: кнопка сортировки и кебаб,
   контролы пагинатора, кнопка фильтра; свечение без пропа `loading`; отметка отказа
   кнопки фильтра; плашка ADR 0096 — примитив кита `Alert` — с ошибкой грида и повтором
   действия; вспышка и объявление; подписи локализации. Тесты SA4–SA6, SA9, SA11–SA13, SA18–SA20.
3. **Этап 3 — сочетания, доступность, перф, история.** Лента, axe и высокая
   контрастность, счётчики работы, серверная история с `play`. Тесты SA14–SA17.
4. **Документация.** ADR 0012, 0038, 0041, 0045, 0094, 0096 («Изменён»),
   `docs/architecture/reactivity.md` и `rendering.md`, AGENTS.md, README решений,
   roadmap, CHANGELOG.
