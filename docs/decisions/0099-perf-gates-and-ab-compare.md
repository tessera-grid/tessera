# 0099 — Перф-тесты: счётчики работы, сравнение вперемешку, RAIL как цель

- **Статус:** Принято (решения — по итогам прожарки 2026-10-12)

  «Перформанс-тесты»: абсолютные пороги RAIL и известные недостиги перестают быть
  гейтом.
- **Связано:**
  - [ADR 0004](0004-core-on-tanstack-table.md) — перф-матрица P1–P13.
  - [ADR 0043](0043-honest-test-coverage.md) — TQ1, TQ6: перф нового массового

## Контекст

Перф-кейсы проверяют абсолютные миллисекунды под замедлением процессора ×4: прокрутка —
p95 работы на кадр против 16,7 мс, отрисовка и взаимодействие — самая длинная задача.
Кейс, не укладывающийся в цель, помечен `knownShortfall` и гейтится регресс-потолком
`regressionCeiling` чуть выше замера.

2026-10-12 ревизия потолков сорвалась. P7 и P8 (быстрая прокрутка со всеми плагинами)
за одну сессию перешли с трёх зелёных прогонов из трёх к одному-двум красным на тех же
коммитах — до 2,5 потолка. Бисект сериями «коммит за коммитом» указал на невиновный
коммит; прогоны вперемешку (A, B, A, B) показали, что падают оба. Машина дрейфовала:
фоновые процессы, оверлеи, нагрев.

Причины в устройстве тестов:

1. **Абсолютный порог на общей машине.** Замедление ×4 масштабирует скорость, но не
   изолирует от фоновой нагрузки. Потолок, подобранный в хороший день, краснеет в
   плохой и пропускает реальное замедление на 20–30 % в хороший.
2. **Серии подряд.** Один повтор (`retry: 1`) убирает единичный выброс, но не сдвиг
   состояния машины между сериями.
3. **Две задачи в одном числе.** «Держим ли мы RAIL» — цель; «не стало ли медленнее» —
   регрессия. Сейчас обе решает одно абсолютное значение.

Устойчивый приём у нас уже есть: сравнения внутри одного прогона — RE50 (подсветка
против базы), GL13, TU13, AS14, CF12. Обе половины сравнения переживают один и тот же
шум.

Второй машины для замеров нет. CI будет бесплатным — общие раннеры GitHub Actions,
шумные.

### Как это сделано у других

- **Tachometer** (Lit, Polymer) — версии гоняются вперемешку, выборка добирается, пока
  доверительный интервал разницы не сузится; результат — «B медленнее A на 3–7 %», а
  не миллисекунды.
- **Lighthouse CI** — для замеров времени рекомендует выделенную машину и несколько
  прогонов с медианой; общие раннеры считает слишком шумными.
- **CodSpeed** — детерминированный режим считает инструкции, а не время; для Node, не
  для браузера; внешний сервис.
- **AG Grid, TanStack Virtual** — открытых перф-гейтов нет.

## Решение

Три уровня, у каждого своя задача и своё место.

### 1. Политика: время не гейтит матрицу

Кейс перф-матрицы пишет значение в дашборд рядом с целью RAIL со статусом «в цели» или
«вне цели» и не падает на абсолютном времени. Падает он только на невалидном замере:
прокрутки не было, режим быстрой или спокойной прокрутки не совпал, прогрев или
`verify` не подтвердили действие. `regressionCeiling` и `knownShortfall` удаляются из
кейсов и дашборда; `test.fails` у перф-кейсов не остаётся.

Сравнения внутри одного прогона («с режимом против базы») остаются гейтом — это тот же
A/B, только между режимами.

`npm run perf` остаётся командой дашборда без гейта по времени.

### 2. Счётчики работы — в `npm test` и CI на каждый push

Детерминированная защита: работа действия считается, а не меряется. Помощник
`measureWork(action)` возвращает:

- коммиты React и отрисованные компоненты — обходом дерева волокон коммита по флагу
  выполненной работы, без компонентов, отданных из кэша; на dev-сборке в StrictMode
  рендер двойной, коммит один — считаются коммиты и выполненная работа, а не вызовы
  рендера;
- созданные и удалённые DOM-узлы — `MutationObserver` на корне грида;
- `LayoutCount` и `RecalcStyleCount` — `Performance.getMetrics` CDP.

Бюджеты задаются через размер окна виртуализации («не больше видимых строк ×
видимых колонок»), а не магическими числами. Счётчики — у восьми ключевых сценариев
(PF4–PF11); остальное ловит сравнение вперемешку.

### 3. `perf:compare` — регрессия против базы вперемешку

`npm run perf:compare <ref> [--cases …]` сравнивает рабочую копию (B) с ревизией `ref`
(A):

- **Рабочее дерево.** `ref` поднимается рабочим деревом git во временном каталоге,
  зависимости — ссылкой на `node_modules` проекта, если lockfile совпадает. Если не
  совпадает — команда останавливается с подсказкой; флаг `--install` ставит
  зависимости `npm ci` в том дереве (зависимости проекта не меняются). Дерево
  удаляется по завершении, в том числе при ошибке; ссылка на `node_modules` снимается
  первой.
- **Вперемешку.** Раунд — по одному прогону кейса на каждой стороне, порядок внутри
  раунда чередуется (A, B, затем B, A). Минимум 5 раундов; кейс, чей вердикт не
  определён, добирает раунды до 15.
- **Метрика** — та же, что в матрице, с теми же проверками валидности: прокрутка — p95
  работы на кадр по каждой оси, отрисовка и взаимодействие — самая длинная задача;
  TBT — там, где кейс его пишет.
- **Вердикт** — по отношению медиан B/A с бутстреп-интервалом 95 % (фиксированное
  зерно): «регрессия», если нижняя граница выше 1,10; «улучшение», если верхняя ниже
  0,90; «без изменений», если интервал внутри [0,90; 1,10]; иначе «не определено».
  Ненулевой код выхода — только на регрессии.
- **Отчёт** — кейс, метрика, медианы A и B, отношение, интервал, вердикт: в консоли, в
  `performance-results/compare.json` и разделом дашборда.
- **Подмножество для PR** — `PR_CASES` в `performance/perf-cases.ts`: P2, P4, P7, P8
  (быстрая и спокойная прокрутка) и ключевые взаимодействия (I1, I3, I7, FL35, RE38),
  около 10–15 минут. Вся матрица — по ночам и по запросу.

Чувствительность и ложные тревоги проверяются самой командой: A против A на одной
ревизии — «без изменений»; подмешанная работа на стороне B (тестовый флаг) —
«регрессия».

### 4. Дашборд RAIL — цель и тренд

Дашборд показывает абсолютные значения против целей RAIL и тренд по истории прогонов
(`performance-results/history.json`, последние 50). Статусов «xfail» и «регресс» нет.
Абсолютные числа зависят от машины: на раннере CI они свои, тренд строится по прогонам
одной машины.

### 5. Где что гоняется

| Где                  | Что                                                                                |
| -------------------- | ---------------------------------------------------------------------------------- |
| Локально, `npm test` | Функциональные тесты, счётчики работы, сравнения внутри прогона                    |
| CI на каждый push    | Весь барьер, включая счётчики работы; замеров времени нет                          |
| CI на PR             | `perf:compare` против базы PR на `PR_CASES`                                        |
| CI по ночам          | `perf:compare` всей матрицы против прошлого релиза, дашборд и история              |
| Локально по запросу  | `npm run perf` (дашборд), `perf:compare` при оптимизации и подозрении на регрессию |
| Перед публикацией    | `test:engines`, `test:react18`, `check:package` (ADR 0084, ADR 0091)               |

## Границы

- Выделенная машина или свой раннер — нет железа; при появлении меняется только место
  ночного прогона.
- Утечки памяти (ADR 0092) — без изменений: они уже меряют наклон.
- Снимки экрана и Chromatic — ADR 0093, этап 6.
- Порог браузеров, движки, React 18 — без изменений.

## Отвергнутые альтернативы

- **Абсолютные пороги с потолками, подобранными точнее** — дрейф машины больше любого
  разумного запаса; потолок либо шумит, либо слеп.
- **Больше повторов (`retry: 3`)** — серии подряд не лечат сдвиг состояния машины.
- **Docker на этой машине** — те же ядра и фоновая нагрузка, плюс виртуальная машина
  WSL2; одинаковое окружение, но не тишина.
- **Абсолютные замеры на общих раннерах CI** — шум раннеров больше разницы, которую
  ищем.
- **Tachometer** — новая зависимость и свой формат бенчмарков; замер через CDP у нас
  есть, не хватает только чередования и статистики.
- **CodSpeed** — внешний сервис; детерминированный режим не для браузера.
- **Счётчики к каждому кейсу матрицы** — дублируют сравнение вперемешку; восемь
  ключевых путей покрывают основное.

## Последствия

- **+** Красный перф означает регрессию, а не плохой день машины.
- **+** CI на общих раннерах получает честную перф-защиту: счётчики — на push,
  сравнение — на PR и по ночам.
- **+** Бисект по перфу — одной командой, вперемешку.
- **−** Абсолютная цель RAIL больше не гейт: отставание видно в дашборде, но сборку не
  роняет.
- **−** Полное сравнение — 30–90 минут: только по ночам.
- **−** Счётчики на dev-сборке: работа dev-веток React в них не попадает, но и цены
  кадра они не говорят — это делает сравнение.
