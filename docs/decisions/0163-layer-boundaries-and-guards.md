# 0163 — Границы слоёв и стражи архитектуры

- **Статус:** Принято (решения — по итогам прожарки 2026-10-31)
- **Дата:** 2026-10-31
- **Слой:** инструменты разработки — `src/lib/__tests__`, `scripts`; правила слоёв — для всего
  `src/lib`.
- **Изменяет:**
  - [ADR 0010](0010-invert-core-plugins-registry.md), IV3 — код, общий у плагинов, живёт не
    «вне папок плагинов», а в слое `shared/`; ядро его не импортирует.
  - [ADR 0001](0001-spec-driven-development.md) — у ADR в шапке строка «Слой».
- **Связано:**
  - [Аудит архитектуры 2026-10-31](../research/architecture-audit-2026-10-31.md) — находки и
    порядок работ; этот ADR — его шаг 1.
  - [ADR 0043](0043-honest-test-coverage.md) — база расхождений, которая только сокращается.
  - [ADR 0138](0138-server-side-row-model.md), SD2 — страж с перечнем модулей и причиной.
  - [ADR 0106](0106-flag-and-predicate-naming.md) — стражи по публичным типам.
  - [ADR 0120](0120-model-and-interface-plugins.md), MP11 — интерфейс несёт свою модель.

## Контекст

Исходная архитектура: ядро самодостаточно и лёгкое, бизнес-логика — в плагинах, UI гибок и
независим. Аудит 2026-10-31 показал, что слои протекают, и ничто этого не ловит:

- ядро (18 тыс. строк) почти равно всем плагинам вместе (21,5 тыс.): правило IV3 выносит общий
  код плагинов «вне их папок», и по умолчанию он попадает в `core/`;
- грид статически импортирует перетаскивание строк и колонок — `DataGrid` без плагинов тянет
  их код, а `check:tree-shaking` проверяет только импорт плагина;
- ядро зависит от `ui`, `ui` — от ядра; плагины берут внутренности грида;
- ядро и грид читают собственные опции плагинов через касты `options as { … }` —
  переименование опции ломает их молча;
- поля колонки и опции таблицы добавляются без следа: список повторён в трёх типах, один
  плагин дополняет `ColumnMeta`, пространство приложения.

Каждое такое решение по отдельности выглядело разумным. Остановить рост можно только
стражами, которые видят границу и требуют причину у каждого исключения.

### Как у других

- **AG Grid** с v33 собирается из модулей (`ModuleRegistry.registerModules`): фича, не
  зарегистрированная приложением, не попадает в сборку; зависимости модулей объявлены явно.
- **TanStack Table v9** включает фичи `tableFeatures()` ради того же — неиспользуемые не
  попадают в сборку.
- **Инструменты** — `dependency-cruiser`, `eslint-plugin-boundaries`: правила слоёв поверх графа
  импортов.

## Решение

### 1. Слои и правила импортов

| Слой                | Что в нём                                                                             | Может импортировать                                                   |
| ------------------- | ------------------------------------------------------------------------------------- | --------------------------------------------------------------------- |
| `util/`             | листовые утилиты без знания о гриде: журнал, разбор CSS-времени, хуки React-окружения | ничего из `src/lib`                                                   |
| `ui/`               | примитивы кита                                                                        | `util`                                                                |
| `core/`             | сборка таблицы, контракт плагинов, реактивность, виртуализация                        | `util`                                                                |
| `grid/`             | рендер `DataGrid`                                                                     | `core`, `ui`, `util`                                                  |
| `shared/`           | код, общий у двух и более плагинов                                                    | `core`, `ui`, `util`                                                  |
| `plugins/<плагин>/` | плагин                                                                                | `core`, `ui`, `util`, `shared` и свои модели по цепочке `entry.model` |
| входы `src/*.ts`    | публичные точки входа                                                                 | всё                                                                   |

Ребро — относительный `import`, `export … from` или динамический `import()`; импорт только
типов — тоже ребро. Тесты, истории и их моки (`__tests__`, `stories`, `__mocks__`) в граф не
входят. Слои `util/` и `shared/` появляются с первым переносом в них (шаги 2–3 аудита); правила
действуют с первого дня.

- Вендор `src/vendor` (ADR 0143) — исходники пакета: его, как пакет, импортирует любой слой.
- `lib/types.ts` — типы TanStack с контрактом `commonFeature`: часть ядра.
- `plugins/index.ts` — вход `/plugins`, как `src/*.ts`.
- Интерфейс импортирует свои модели по цепочке `entry.model`, модель интерфейс — нет (MP11).

### 2. База исключений

Нынешние нарушения не чинятся этим ADR: они ложатся в базу стража, каждое — с причиной не
короче десяти знаков и номером находки аудита или ADR. Нарушение вне базы роняет страж; запись
базы, которой больше нет в коде, тоже роняет — база только сокращается, как у SD2 и
`requirements-baseline.json`. Базы стражей — один модуль, `src/lib/__tests__/architecture.baseline.ts`:
он же — рабочий список шагов 2–6 аудита.

### 3. Хозяин модуля ядра

Модуль `core/`, у которого все прямые импортёры вне ядра — плагины или `shared/` (ни ядро, ни
грид, ни `ui`, ни входы), — не ядро: его место в `shared/` или в плагине. Такой модуль роняет
страж, если его нет в базе. Модуль, который нужен самому ядру и открыт плагинам
(`servicePresence`, `scrollGridTo`), стоит в отдельном перечне «API ядра для плагинов» с
причиной ([ADR 0166](0166-shared-layer-utils-and-kit.md), §4); в обоих перечнях сразу его нет.

### 4. Сборка `DataGrid` без плагинов и её бюджет

`check:tree-shaking` собирает ещё одно приложение: `import { DataGrid, useCreateTable }` из
`dist` без плагинов, с теми же внешними зависимостями (`react`, `react-dom`, `@tanstack/*`,
`@dnd-kit/*`). В сборке нет модулей `dist/lib/plugins/*`, кроме базы с причиной (сейчас —
`rowDragging`, `columnDragging`, находка 2 аудита).

Размер этой сборки после gzip записан в `scripts/core-budget.json`. Рост больше чем на 1 %
роняет проверку: новое значение записывается осознанно, в ревью. Уменьшение больше чем на 1 %
печатает подсказку снизить запись.

### 5. Собственные опции плагинов

Ключи опций таблицы, которые выставляют встроенные плагины (записи `builtinPluginEntries()` —
без аргументов, выключенные и с типичными аргументами вроде `server: true`) и которых нет ни
среди опций стоковых фич TanStack, ни в `CommonOptions` ядра, читают только сам плагин и плагины
его цепочки `entry.model`. Обращение `options.<ключ>` к такому ключу в ядре, гриде, `shared/`
или чужом плагине — падение вне базы «файл: ключ». Стоковые ключи (`enableRowSelection`,
`manualFiltering`) страж не считает: они типизированы TanStack, а знание грида о присутствии
плагина разбирает шаг 7 аудита. Ключи `CommonOptions` — объявленные каналы ядра; их чтение
через каст ловит §7. Стоковые ключи берутся из записей карты фич, объявленных в
`@tanstack/*`: тип `TableOptions_All` включает и дополнения карты от Tessera.

### 6. Контракт колонки и записи плагина

- Свои поля описания колонки — поля, которые фичи Tessera добавляют в `ColumnDef_FeatureMap`, —
  не совпадают по имени ни с одним полем `ColumnDef` стоковых фич TanStack.
- Библиотека не дополняет `ColumnMeta`: это пространство приложения (база — `pinSides`,
  находка 14 аудита).
- Снимок контракта — перечень ключей с номером ADR у каждого: свои поля колонки, `CommonOptions`,
  поля публичной `TablePlugin` и внутренней `TesseraFeatureEntry` (ADR 0164). Ключ без строки
  снимка и строка без ключа роняют страж: новое поле
  контракта появляется только вместе с записью, откуда оно.

### 7. Опции без типа

`table.options` (и любое выражение `….options`) не приводится к `any`, к `unknown as …` и к
объектному литералу: опцию объявляют в `CommonOptions` или в карте фичи. База — файл и число
таких мест с причиной; рост числа в файле роняет страж, уменьшение требует снизить запись.

### 8. Слой в ADR и в прожарке

ADR с номером больше 0163 несёт в шапке строку `- **Слой:** …` — где живёт код решения и
почему не в плагине, если это не плагин. Шаблон прожарки (AGENTS.md §6, шаг 4) получает тот же
вопрос: в каком слое каждый новый модуль.

## Границы

- Этот ADR ставит стражи и базу; переносы кода — шаги 2–8 аудита отдельными ADR.
- Граф строится по относительным путям `src/lib`; импорты пакетов (`@tanstack/*`, `react`) не
  проверяются — их держат `vite.config.ts` и ADR 0003.
- Страж опций видит обращения `options.<ключ>`; чтение через деструктуризацию
  (`const { enableX } = table.options`) он не ловит — такие места переписываются по ходу шага 4
  аудита.

## Отвергнутые альтернативы

- **`no-restricted-imports` в ESLint по папкам** — базу с причиной правилом линтера не удержать
  без `eslint-disable` в каждом месте, а массовые отключения запрещены (AGENTS.md §4).
- **`dependency-cruiser`, `eslint-plugin-boundaries`** — новые зависимости; свой обход графа уже
  есть (SD2), а база в их форматах не связана с находками аудита.
- **Бюджет ядра в строках** — меряет текст, а не то, что получает приложение; бюджет сборки
  (§4) меряет байты.
- **Стоковые ключи в страже опций** — база втрое больше; решено на прожарке: шаг 7 аудита.
- **`plugins/_shared/`** вместо `shared/` — смешивает плагины и общий код в одном каталоге.

## Последствия

- Рост ядра и протечки слоёв видны в первом же прогоне `npm test` и `check:tree-shaking`.
- Модуль, нужный только плагинам, сразу ложится в `shared/`; новое поле колонки или опция ядра
  требует строки снимка с номером ADR.
- Каждый следующий шаг аудита виден как сокращение базы.
- Стражи снимка контракта идут через TS compiler API, как FN-стражи ADR 0106: до двух минут в
  проекте `unit`.

## Внедрение

**Этап 1 — стражи с базой нынешних нарушений** (2026-10-31).

- **Граф и правила** — `src/lib/__tests__/importGraph.ts` (модули, слои, рёбра) и
  `src/lib/__tests__/layerRules.ts` (нарушения каждого правила); типы TanStack и контракта для
  TS compiler API — `src/lib/__tests__/contractTypes.ts` через `publicTypes.ts`.
- **Стражи** — LB1, LB2, LB5, LB7, LB9, LB10 — модульный `layerBoundaries`; LB6, LB8 — модульный
  `contractSnapshot` со снимком `contract.snapshot.ts`; LB3–LB4 — `scripts/check-tree-shaking.mjs`
  с `scripts/core-budget.json`.
- **Базы** — `src/lib/__tests__/architecture.baseline.ts`: 43 ребра (LB1), 18 модулей ядра
  (LB2), 23 чтения чужих опций (LB5), одно дополнение `ColumnMeta` (LB7), 33 каста в 19 модулях
  (LB9); сборка `DataGrid` без плагинов тянет `rowDragging` и `columnDragging` (LB3).
- **Бюджет** — первый замер 211 850 байт gzip (668 КБ до gzip): грид 176 КБ, Base UI 173 КБ,
  ядро 152 КБ, вендор Virtual 43 КБ, `ui` 33 КБ, перетаскивание строк и колонок 21 КБ.
- **TQ1** — каждый страж показан падающим: без записи базы (LB1, LB2, LB5, LB7, LB3), с
  устаревшей записью (LB1, LB3), с числом кастов меньше настоящего (LB9), с порогом на ADR 0162
  без строки «Слой» (LB10), со стоковым именем `enablePinning` в поле колонки (LB6), без ключа
  снимка и с несуществующим ADR (LB8), с бюджетом 209 000 байт (LB4); бюджет 215 000 байт
  печатает подсказку снизить запись.
- **Документация** — правила слоёв в `docs/architecture/README.md`; карта репозитория, наборы и
  вопрос прожарки — в `AGENTS.md`.
