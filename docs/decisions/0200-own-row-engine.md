## Контекст

Цепочка моделей TanStack (исходная → фильтрация → группировка → сортировка → раскрытие →
страница) на любое изменение пересобирается по всем строкам. Свои фабрики в слотах моделей
(ADR 0064, 0067–0070, 0072, 0194, 0199) ускорили приход ленивых детей, смену `data` и сортировку
в разы, но держатся на поведении TanStack, которого его API не обещает: строка переживает смену
модели вместе с кэшами `_valuesCache` и `_groupingValuesCache`, словарь `rowsById` правится на
месте, `index`, `depth`, `parentId` и `subRows` уже собранных строк переписываются, автосбросы —
микрозадачи после пересчёта (перечень — [upstream-foundations.md](../architecture/upstream-foundations.md#движок-строк-поверх-tanstack)).
Почти всё, что мы трогаем, TanStack экспортирует (`constructRow`, `copyInstancePropertiesWithoutMemos`,
`expandRows`, `tableMemo`), а подчёркнутые поля объявлены в типах `Row`: риск не в закрытых
символах, а в неописанном поведении.

Peer `@tanstack/react-table: ^9` пускает к потребителю любую 9.x. На 2026-11-08 установлена
9.2.4, а `latest` — 9.3.1: между ними изменились больше 30 модулей `table-core`, среди них
`createCoreRowModel`, утилиты строк и модели фильтрации, группировки и сортировки. Сломанное
поведение даёт не ошибку сборки, а неверные строки.

### Что рассматривалось

| Вариант                                                                  | Итог                                                                                                                                                     |
| ------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------- |

| Б. Точная версия в `dependencies` и вход `/table` с API TanStack         | У приложения со своим TanStack — две копии; расширения Tessera через `declare module '@tanstack/react-table'` не доходят до его импортов; опора остаётся |
| В. `^9` и проверка версии в рантайме с откатом на стоковые модели        | Тихая потеря скорости; версию `table-core` надёжно не узнать                                                                                             |
| Г-а. Свои фабрики в тех же слотах на публичном контракте                 | Снимает опору, но оставляет два пути — клиентские модели TanStack и серверный движок                                                                     |
| **Г-б. Свой движок за источником строк для обоих режимов** (это решение) | Опора снята, клиентский и серверный режимы сходятся в одном движке, peer снова `^9`                                                                      |

### Как это сделано у других (2026-11-08)

- **AG Grid**, Client-Side Row Model — свои узлы строк и конвейер стадий (фильтр, группировка,
  агрегаты, сортировка, разворачивание в список); транзакции пересчитывают только изменённый путь
  (`ChangedPath`). Серверная модель — отдельный движок.
- **MUI X** — своё дерево строк (`rowsLookup`, `rowTree`); фильтр и сортировка выдают списки id;
  `updateRows` меняет строки без пересборки всего дерева.
- **Material React Table** — стоковые модели TanStack без своих фабрик; TanStack — зависимость с
  точной версией.
- **LyteNyte** — свой движок без зависимостей.

## Решение

### 1. Роль TanStack Table

TanStack — ядро колонок, шапки, состояния и фич: `ColumnDef` и модель колонок, группы заголовков,
видимость, порядок, закрепление, ширины, атомы состояния, композиция фич `tableFeatures()`,
объекты `Row`, `Cell`, `Column`, `Header` с API на прототипах, реестры `filterFns`, `sortFns` и
`aggregationFns`. Список строк, их порядок, видимость и место строит движок Tessera. Расширение
TanStack нашим API — по-прежнему `commonFeature` и `declare module '@tanstack/react-table'`
(ADR 0026): с возвратом к `^9` у приложения одна копия TanStack, и расширения видны в его
импортах.

**Критерий пересмотра.** Если после этапа 5 профили I4, PS8, P8 и P12–P13 покажут главной ценой
слой колонок или ячеек TanStack, он заменяется тем же приёмом — свой источник колонок за швом,
по частям — отдельным ADR.

### 2. Каркас движка

`core/rowEngine/` держит:

- **хранилище строк** — узлы по id с деревом данных. Два вида: в памяти (клиентский режим, из
  `data`) и блоки (серверная модель, ADR 0138). Хранилище одно на таблицу, закрытое и изменяемое (как у AG Grid): словарь id → строка меняется на месте, O(изменений), без копий и слоёв; удалённая строка уходит из памяти сразу. Списки строк — новые на каждую смену (копия массива дешёвая), опубликованные строки не меняются (§4). Пишет хранилище только движок;
- **конвейер стадий** в постоянном порядке: фильтр и поиск → группировка с агрегатами →
  сортировка → раскрытие → страница. Стадия получает узлы от предыдущей и набор изменений,
  отдаёт свои узлы и набор изменений для следующей;
- **пересчёт по пути изменения** (§7);
- **источник строк** (`RowSource`, ADR 0138, §2) — выход конвейера; `table.getRowSource()` в
  `commonFeature` отдаёт его.

Каркас не знает алгоритмов фильтра, группировки и сортировки: без стадий он отдаёт строки в
порядке данных.

Набор изменений (решение автора 2026-11-09, этап 5): смена `data` сравнивает прежний и новый
массивы данных — их держит приложение — и даёт список «добавлено, удалено, сдвинуто,
заменено»; транзакция и стадия переноса дают его сами, ответ ленивых детей — ветку. Стадия обновляет свой выход по набору и передаёт набор дальше; прежние объекты строк она берёт из набора (`previous`), а словарь прежнего входа не читает — он общий с хранилищем. Свои прежние списки и словарь своего выхода стадия читать может: их меняет только она. Поэтому словарь хранилища может меняться на месте, а неизменными остаются только снимки, отданные наружу (§6).

### 3. Стадии — в плагинах моделей

| Стадия                | Плагин модели          | Чем считает                                                                                         |
| --------------------- | ---------------------- | --------------------------------------------------------------------------------------------------- |
| Фильтр колонок        | `columnFilteringModel` | `filterFns` TanStack и функции колонок, типы данных (ADR 0172), подписи вариантов (ADR 0048)        |
| Поиск                 | `quickSearchModel`     | функция поиска колонки, показанный текст по типу (ADR 0172)                                         |
| Группировка, агрегаты | `rowGroupingModel`     | `aggregationFns` TanStack и функции колонок                                                         |
| Сортировка            | `columnSortingModel`   | `sortFns` TanStack, `sortUndefined`, `invertSorting`, `sortDescFirst`, подписи вариантов (ADR 0063) |
| Раскрытие             | `rowExpandingModel`    | срез `expanded`, модель дерева (ADR 0119), ленивые дети (ADR 0054)                                  |
| Страница              | `paginationModel`      | корни вместе с ветками (ADR 0038)                                                                   |

Плагин модели регистрирует стадию через свою запись `TesseraFeatureEntry` (ADR 0010, 0120);
стадий нет — их кода нет в сборке. Отдельного пакета не нужно: `dist` собран модулем на файл, и
`check:tree-shaking` проверяет, что плагин не тянет чужих модулей (IV3).

### 4. Строки

- Строка — `Row` TanStack из публичной `constructRow`. Создаётся один раз на объект данных;
  новая — только при новом объекте; новые колонки пересоздают таблицу, а с ней и строки.
- Поля строки пишет только движок и только при создании, до того как строку увидит кто-то
  ещё; у строки-группы — `groupingColumnId`, `groupingValue`, `leafRows` и значения агрегатов, как
  в серверной модели (ADR 0144). Опубликованная строка не меняется. Два исключения — поля,
  которые TanStack сам объявляет изменяемыми: `columnFilters` и `columnFiltersMeta` пишет стадия
  фильтра (их читают фасеты), `depth` и `parentId` листьев под группами назначает стадия
  группировки и сбрасывает без группировки — так делает и стоковая группировка.
- Копии строк создаёт только то, что меняет состав детей, — фильтр дерева и ответ ленивых детей
  (ADR 0054): строка с пришедшими детьми и её предки — новые строки `constructRow` с полями при
  создании, по объекту на уровень ветки. У фильтра дерева родитель с
  детьми отбора — новая строка `constructRow`, поля при создании. От состава `subRows` зависят API
  строк TanStack — раскрытие, каскад выбора, листья, — поэтому под фильтром они видят отбор, как у
  стоковой модели. Стадии порядка (сортировка) копий не создают: дети показа.
- Значение, которого строка ещё не несёт (стадия переноса между группами, ADR 0186, §3), грид
  показывает через опцию ядра `cellValueOverride`: ячейка и её рендерер получают значение стадии,
  кэши строки не меняются. Ключ группы стадия берёт из стадии переноса.
- Порядок показа детей — структура движка; `subRows` строки — дети в порядке данных, как их
  читают фичи TanStack (каскад выбора, `getCanExpand`, `getLeafRows`).
- Свои кэши (значения сортировки, ключи групп, прошлый порядок) движок держит в своих словарях
  по id строки, а не в полях `Row`.

### 5. Индекс строки

Место строки знает только источник: ни один модуль Tessera не читает `row.index` как позицию.
`index` в `accessorFn(original, index)` — индекс объекта в данных на момент создания строки, как у
стоковой модели TanStack; после вставки в середину он не обновляется. Сигнатура — часть `ColumnDef`
TanStack, убирать её не нужно. Номер строки на экране — отдельная потребность (roadmap); у AG Grid
и MUI X индекса в аксессоре нет.

### 6. Методы моделей на `table`

Слоты моделей TanStack (`coreRowModel`, `filteredRowModel`, `groupedRowModel`, `sortedRowModel`,
`expandedRowModel`, `paginatedRowModel`) отдают ленивые обёртки над движком: `getRowModel`,
`getCoreRowModel`, `getFilteredRowModel`, `getSortedRowModel`, `getGroupedRowModel`,
`getExpandedRowModel`, `getPaginatedRowModel`, `getSelectedRowModel` и `getRow` дают тот же итог,
что стоковые модели, а массив и словарь собираются только при вызове и живут до следующего
пересчёта. Модель, отданная наружу, не меняется и после следующих смен: её `rowsById` — словарь своей версии (текущая — живой словарь хранилища, прежняя — вид на него с обратными записями смен), списки строк — свои; приложение, держащее прежнюю модель, видит прежнее. Ссылка на сам словарь, взятая до смены, — живой словарь: держать нужно модель. Снимка за O(n) не собирается. `table.getRow` и API строк TanStack, которые ищут строку
по id (выбор, раскрытие), читают хранилище движка и снимка не собирают. Стоковые фичи TanStack (выбор и раскрытие всего, число страниц, фасеты, автоматический
выбор `sortingFn` и `aggregationFn`) работают через них. Грид и плагины читают строки только через
источник; в списке стража SD2 остаётся один движок.

### 7. Пересчёт по пути изменения

| Изменение                                            | Что пересчитывается                                                  |
| ---------------------------------------------------- | -------------------------------------------------------------------- |
| Смена колонок или набора стадий                      | всё: строки создаются заново                                         |
| Вход стадии (сортировка, фильтр, поиск, группировка) | эта стадия и стадии ниже                                             |
| Смена `data` (ADR 0194), сдвиги (ADR 0199)           | изменённые, вставленные и удалённые узлы и их ветки на каждой стадии |
| Транзакция клиента, стадия переноса строк            | то же                                                                |
| Приход ленивых детей, пачка ответов (ADR 0066)       | ветка ответа                                                         |
| Раскрытие и сворачивание                             | ветка строки на стадиях раскрытия и страницы                         |

Итог любого инкремента равен полной сборке; при переносе сверх порога (ADR 0194, IU4) — полная
сборка. Подсказку виртуализатору о первом изменённом месте (ADR 0145) даёт движок. Автосбросы
страницы и раскрытия — по правилу TanStack (сброс при смене данных, фильтра и группировки, кроме
`autoResetPageIndex: false` и ручных режимов), без опоры на его микрозадачи.

### 8. Ячейки окна

Тело создаёт объекты `Cell` только для колонок окна виртуализации колонок, а не через
`row.getVisibleCells()` на все видимые колонки ([Body.tsx](../../src/lib/grid/Body.tsx),
[BodyRow.tsx](../../src/lib/grid/BodyRow.tsx)): при 1000 колонках это 1000 объектов на строку и их
пересоздание при смене набора колонок.

### 9. Серверная модель

Хранилище блоков `serverRowModel` (ADR 0138, §4) — второе хранилище движка. Стадии в серверном
режиме на клиенте не идут: порядок, фильтр и группы приходят с сервера (`manual*`). Общими
становятся источник, пересчёт по пути изменения при транзакциях (ADR 0157) и раскрытии веток.

### 10. Внедрение этапами

Сначала оркестрация, потом замена реализаций: с этапа 1 все пять слотов моделей — обёртки над
стадиями движка, а нынешние фабрики — реализации этих стадий без изменения поведения. Каждый
следующий этап заменяет реализацию стадии своей, без опоры на внутренности TanStack. Двух
механизмов строк рядом и внутреннего флага нет: в любой момент строки строит один движок.
Каждый этап — свой коммит с зелёным барьером и `perf:compare` своих кейсов.

Хранилище строк идёт раньше стадий дерева (этап 3, затем 4): ленивые дети и смена `data` правят
строки модели ядра, а стадии дерева берут порядок детей у движка. Фильтр, поиск и сортировка
плоских строк меняются вместе со стадиями дерева: их инкремент читает журнал смен хранилища.

| Этап | Объём                                                                                                                                                                                                                                                        | Снимается                                                                                                 |
| ---- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------- |
| 0    | Подъём TanStack до 9.3.1, сверка таблицы опор с исходниками, peer `>=9.3.1 <9.4`                                                                                                                                                                             | —                                                                                                         |
| 1    | Каркас: стадии из набора фич, постоянный порядок, ручные режимы; пять слотов — обёртки, нынешние фабрики — реализации стадий; плоские строки фильтра без копий; ячейки окна                                                                                  | копии плоских строк в отборе фильтра                                                                      |
| 2    | Группировка и агрегаты: своя стадия для плоского входа, значение стадии переноса через `cellValueOverride`; вход-дерево — прежняя фабрика до этапа 3                                                                                                         | запись стадии переноса в кэши строк, `_aggregationValuesCache` и `_valuesCache` строк-групп               |
| 3    | Хранилище строк: место строки — у хранилища, `index` — при создании; словарь `rowsById` новой модели — слоем поверх прежнего; смена `data`, сдвиги, транзакции и ленивые дети не правят опубликованных строк                                                 | запись `index` и кэшей значений сдвинутых строк, правка словаря прежней модели, MS1, MS5                  |
| 4    | Стадии дерева своими: фильтр, поиск, сортировка, группировка дерева, раскрытие, страница; порядок показа — структура движка, без копий у стадий порядка, копии родителей — только у фильтра; `table.get*RowModel()` собирает стоковый вид лениво; история S1 | своя модель сортировки и раскрытия, прежняя фабрика группировки                                           |

## Границы

- **Воркер** — вне объёма; стадии не трогают DOM и объекты React, чтобы перенос в воркер остался
  возможным.
- **Свой тип строки** — вне объёма: `Row` TanStack — публичный тип хуков, плагинов и
  `definePlugin`.
- **Номера строк на экране** — отдельная потребность.
- **Pivot** — отдельный ADR (roadmap); конвейер оставляет место для стадии сводной таблицы.
- **Серверная группировка вместе с деревом данных** — по-прежнему не совмещаются (ADR 0144).

## Отвергнутые альтернативы

- **Узкий peer, точная зависимость, проверка версии в рантайме** (А, Б, В) — опора на неописанное
  поведение остаётся; цену платит потребитель (`ERESOLVE`, вторая копия, тихая потеря скорости).
- **Свои фабрики на публичном контракте в слотах** (Г-а) — снимает опору, но оставляет два
  механизма строк для клиентского и серверного режимов.
- **Отказ от TanStack целиком** — новая библиотека и ломающий публичный API без выигрыша по
  скорости; пересмотр — по критерию §1.
- **Стадии в ядре** — каждый `DataGrid` платил бы за все стадии; бюджет LB4.
- **Отдельный npm-пакет стадий** — гранулярность уже даёт сборка модулем на файл.

## Последствия

- **+** Опоры на неописанное поведение TanStack нет; peer снова `^9`, обновление TanStack — без
  нашего выпуска.
- **+** Клиентский и серверный режимы стоят на одном источнике и одном пересчёте; паритет моделей
  (ADR 0187) во многом обеспечен устройством.
- **+** Конвейер — шов для воркера и стадии сводной таблицы.
- **+** Удалённые строки уходят из памяти сразу, поиск строки по id — обычный словарь
  (этап 5, [замер против AG Grid](../research/tessera-vs-ag-grid-2026-11-09.md)).
- **−** Объём: пять этапов, несколько недель; 0.1.0 выходит после этапа 5.
- **−** До этапа 4 стадии фильтра, поиска и сортировки — прежние фабрики: опора на внутренности
  уходит постепенно, с этапами 2–4.
- **Ломающее:**
  - `index` в `accessorFn` — индекс при создании строки, а не живой (снимает MS5 ADR 0199);
  - `table.get*RowModel()` собирает массив при первом вызове после пересчёта: приложение, которое
    зовёт его на каждый рендер, платит O(n) на каждый пересчёт.

  - Сортировка у плоского входа искала детей показа каждой строки по цепочке стадий; плоский вход —
    без поиска. Замена на месте собирает плоский список вторым указателем и срезами прежнего, а
    уровень с несколькими сменами правит `splice`. Строка, у которой не стало детей, теряет запись
    детей показа (ошибка была скрыта: смены ленивой модели сюда не доходили).
  - Смена ответа ленивых детей — смена на месте (`inPlace`): прочие строки — прежние объекты на
    прежних местах; сортировка на приходе идёт заменой на месте, а не общим путём.
  - Модель раскрытия при корнях на прежних местах заменяет участки затронутых корней в копии
    прошлого списка, без словаря по всем корням (`patchRootsInPlace`).
  - Фильтр `filterFromLeafRows` копирует строку, только когда её дети другие: лист и строка с
    прежними детьми — сама строка входа. Позиция переходит копии, только если записана
    (`copyPosition`); место, равное `index`, записи не держит.

  `perf:compare` рабочей копии против `eebb55f4` под ×4 CPU, 11 раундов: IU13 ×1,06 (38,5 → 40,6 мс,
  было 272 мс), SF25 ×1,13 (не определено, было ×1,82), MS9 ×0,84, MS10 ×0,88, MS11 ×1,22

  `perf:compare` с выключенной полосой (`windowBand.enabled = false`) против `eebb55f4` — RE38 ×1,01,
  RE73 ×1,01, база ×1,05. Требование для движка выполнено. Покой и рост полосы — поправка ADR 0202
