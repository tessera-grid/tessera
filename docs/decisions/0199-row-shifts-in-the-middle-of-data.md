# 0199 — Вставка, удаление и перенос в середине `data`: живой индекс строки

- **Статус:** Принято (прожарка 2026-11-08), внедрено 2026-11-08
- **Дата:** 2026-11-08
- **Слой:** ядро — разница `data` и модель ядра (`core/dataChanges.ts`), места строк клиентской
  транзакции (`core/rowTransactions.ts`) и её итог на строках (`core/transactionOutcome.ts`); модель сортировки (`plugins/columnSortingModel`). Это не
  плагин: модель данных и её смена принадлежат ядру, модели строк ниже по конвейеру — их потребители.
- **Изменяет:**
  - [ADR 0194](0194-incremental-data-changes-and-client-transactions.md) — «Границы»: вставка,
    удаление и перенос в середине больше не стоят полной сборки; перестановка — полная сборка
    только сверх порога. IU2: прежняя модель не меняется, кроме `index` сдвинутых строк; IU4:
    перенос в пределах порога — инкремент. Гарантии прихода ленивых детей (IM6 ADR 0067, IM10
    ADR 0069, SM11 ADR 0072) не меняются: приход не сдвигает строки.
- **Связано:**
  - [ADR 0145](0145-first-changed-row-hint.md) — подсказка виртуализатору.
  - [ADR 0006](0006-dnd-with-dnd-kit.md), [ADR 0186](0186-row-move-between-client-groups.md) —
    перетаскивание строк в клиентском режиме: бросок — перенос в `data`.
  - [ADR 0099](0099-perf-gates-and-ab-compare.md) — гейт против базы того же теста.
  - [ADR 0157](0157-ssrm-row-transactions.md) — вид транзакции у серверной модели (RT9–RT10): клиент
    повторяет вспышку добавленных, уход удалённых и объявление (§7).

## Контекст

Смена `data` собирает модель ядра из прежней (ADR 0194). Без сдвигов — замена на месте и
дописывание в конец — модели работают только с изменёнными строками. Вставка, удаление и перенос в
середине сдвигают индексы строк ниже: их объекты строк пересоздавались, модели перекладывали их по
`id`, а перестановка выживших шла полной сборкой. На 100 000 строк при сортировке под ×4 CPU вставка
100 строк в середину — 479–517 мс против 79–87 мс у дописывания тех же строк в конец; удаление —
~490 мс; перенос одной строки через 50 000 позиций — 360 мс, дороже полной сборки (320 мс).
Перетаскивание строки на большой клиентской таблице платит эту цену на каждый бросок.

### Как у других

|                 | Индекс строки                                     | Вставка в середину              |
| --------------- | ------------------------------------------------- | ------------------------------- |
| AG Grid         | `rowIndex` узла изменяемый, узлы переживают смену | транзакция правит узлы на месте |
| MUI X Data Grid | строки по `id`, индекс считается по списку        | `updateRows` по `id`            |
| TanStack Table  | `row.index` задаётся при создании строки          | новый `data` — полная сборка    |

Tessera берёт изменяемый индекс AG Grid: строка — прежний объект, у сдвинутой меняется `index`.

## Решение

### 1. Живой индекс

Строка с прежним объектом данных — прежний объект строки модели ядра, где бы она ни стояла. У
сдвинутой строки меняется поле `index` того же объекта, у колонок, чей `accessorFn` принимает
индекс, значения считаются заново. Сдвиг ниже по конвейеру — не изменение: сортировка, фильтры,
поиск, группировка и раскрытие сдвинутые строки не перекладывают. Индекс ставится, только когда
смена собрана: при отказе (порог, повтор id) — полная сборка, прежняя модель не тронута.

### 2. Перенос

Строка, чьё место нарушает порядок выживших, перенесена: новый объект строки с прежними данными и
поддеревом, в смене — изменённая. Ниже по конвейеру её место ищется заново. Перенесённых, изменённых,
вставленных и удалённых строк больше порога (доля от числа строк, ADR 0194) — полная сборка.

### 3. Как находится смена

Плоские данные: общее начало и общий конец списков сверяются по объектам данных без `getRowId`,
середина — двумя указателями с шагом вперёд, id считается только у несовпавших строк. Строки
конца — прежние объекты с новым индексом, словарь `rowsById` переходит новой модели (ADR 0069).
Смена помечена «порядок выживших прежний» (`inPlace`): модель сортировки берёт прежний порядок,
убирает уходящие объекты и ставит новые одним проходом по уровню. Уходящий объект — с прежним
индексом, а сдвинутые соседи — уже с новым, поэтому среди равных значений сортировка ищет его по
тождеству. Дерево (`subRows`) и сбитые шаги вперёд — общий путь по `id`: те же прежние объекты с
новым индексом, перенесённые — по наибольшей возрастающей цепочке прежних мест.

### 4. Клиентская транзакция

`applyRowTransaction` в клиентском режиме берёт места удаляемых и обновляемых строк из модели ядра
по `id` — индекс живой — и собирает следующий `data` кусками между ними, без `getRowId` на каждой
строке. Модель не сходится с уровнем — прежний проход по уровню.

### 5. Список строк в dev-сборке React

Dev-сборка React 19 после коммита записывает отрисовку каждой перерисованной компоненты и
сравнивает её пропсы, спускаясь в объекты на три уровня и по сотне ключей на уровень. Массив строк
в пропсах, чьё начало сдвинулось, она обходит поэлементно вместе с полями строк. Вставка в окно на
100 000 строк стоила так ~2,3 с до кадра против ~50 мс вне окна; в prod-сборке этого журнала нет.
Внутренние компоненты рендера получают список строк геттером, созданным раз на список в `DataGrid`:
функцию журнал сравнивает по ссылке и внутрь не спускается.

### 6. Итог клиентской транзакции на строках

Транзакция выглядит так же, как у серверной модели (ADR 0157, RT9–RT10): добавленные строки
вспыхивают «пришла» (`arrived`, ADR 0134), удалённая в окне сперва гаснет на месте, затем строки
ниже закрывают щель, а таблица объявляет «Добавлено / удалено N строк» ключами словаря ядра
`announceRowsAdded` и `announceRowsRemoved`. Транзакция только строит `data` — показать итог
можно, когда приложение положило его: таблица помнит добавленные и удалённые `id` и со следующим
новым `data` вспыхивает теми добавленными, что в нём есть, и объявляет. Приложение положило не тот
`data` — показывается то, что в нём есть, ожидание снимается. Новый `data` от приложения без
транзакции не вспыхивает: таблица не знает, что в нём ново для пользователя, а что — пересборка
данных приложением. Уход удалённой рисует движение строк для любого источника (ADR 0107).

### 7. Ломающее изменение

Объект строки, сохранённый с прошлого рендера, после вставки или удаления выше него показывает
новый `index`. Прежняя модель не меняется, кроме `index` сдвинутых строк и кэша индексных колонок.
До 1.0 это допустимо (AGENTS.md, «Публичный API»), изменение названо в CHANGELOG при выпуске.

## Отвергнутые альтернативы

- **Неизменная прежняя модель, дешевле только перекладка.** Объекты сдвинутых строк всё равно
  пересоздавались бы: половина цены — сама сборка ядра по всем строкам ниже места.
- **Индекс по запросу через словарь мест.** Каждое чтение `row.index` — поиск; TanStack и свои
  модели читают индекс в сравнении и разметке на каждой строке.
- **Только вставка и удаление.** Перенос — тот же механизм, без него бросок перетаскивания на
  большой таблице остаётся полной сборкой.

## Границы

- Серверная модель строк — без изменений (ADR 0157).
- Произвольная перестановка всего массива — полная сборка, как прежде.
- Цена пересчёта позиций виртуализатором от места первого сдвига (ADR 0143, ADR 0145) остаётся: она
  растёт с числом строк ниже места.

## Последствия

- Вставка и удаление 100 строк в середине 100 000 при сортировке стоят как дописывание тех же строк
  в конец: ×1,11 и ×1,22 под ×4 CPU (MS9, MS10); перенос строки через 50 000 позиций — ×0,15 полной
  сборки (MS11).
- Мемоизация по объекту строки переживает вставку и удаление выше строки.
- Код, запоминающий что-то по `row.index` прежней модели, видит новый индекс.

## Сценарии

| №   | Сценарий                                                                                                            | Требования    | История                             |

Видимое поведение то же, что у таблицы поменьше, меняется цена: история показывает, что на ста
тысячах строк вставка, удаление и перенос отвечают без задержки; новые строки вспыхивают, удалённые
гаснут на месте (§6). Скорость доказывают MS9–MS11.

## Внедрение

Один этап. Тесты: модульный `rowShifts.dom` (MS1–MS8), перф MS9–MS11 — в `interaction`, визуальный
`row-shifts-dev` (MS12: в окне 48–49 мс против 29–36 мс вне окна, было 2299 мс). Замер
2026-11-08 под ×4 CPU: вставка 131 против 118 мс у дописывания, удаление 149 против 123, перенос 84
против 580 мс полной сборки. Итог транзакции на строках (§6) — модульный `clientTransactions.dom`
(MS13–MS14), визуальный `client-transactions` (MS15) и `play` гайда S1. TQ1: без ожидания итога в
`core/dataFollow.ts` падают MS13–MS15, с вспышкой всех добавленных без проверки по `data` — MS13,
без ветки ухода в `RowMotion` — MS15.
