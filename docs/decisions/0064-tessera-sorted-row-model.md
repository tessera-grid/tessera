# 0064 — Своя отсортированная модель строк

- **Статус:** Принято (решения — по итогам прожарки 2026-10-08)
- **Дата:** 2026-10-08
- **Связано:**
  - [ADR 0012](0012-column-sorting.md) — плагин `columnSorting`; меняется фабрика
    отсортированной модели, поведение — нет.
  - [ADR 0063](0063-option-label-sorting.md) — сортировка по подписи переходит на
    контракт `constructSortFn`.
  - [ADR 0004](0004-core-on-tanstack-table.md), [ADR 0026](0026-migrate-to-tanstack-v9.md)
    — TanStack Table v9 и точки расширения фич.

## Контекст

Первый клик сортировки 100 000 строк — ~800 мс под ×4 CPU одной задачей (OS11-base).
Профиль (2026-10-08): ~610 мс — `createSortedRowModel` TanStack. Его сравнение пары
строк читает значение колонки четыре раза: дважды для `sortUndefined` и дважды внутри
функции сортировки (`row.getValue` с проверкой кэша), а встроенные функции на каждой
паре заново приводят значение (`toString(...).toLowerCase()`). Пар — около 1,7 млн.

Кроме того, модель TanStack отдаёт в `rowsById` оригиналы строк, которые заменила
копиями (обход CS24, «Обходы апстрима» в
[upstream-foundations.md](../architecture/upstream-foundations.md)).

Решено (прожарка 2026-10-08):

- своя фабрика в слот `sortedRowModel` (публичная точка расширения фич v9), без
  патчей TanStack;
- быстрый путь — только для функций сортировки по контракту `constructSortFn`; свой
  `sortFn` приложения работает как раньше;
- совпадение порядка с TanStack доказывают сравнительные тесты на обеих фабриках.

## Решение

### 1. Фабрика

`createTesseraSortedRowModel` повторяет устройство модели TanStack на публичном API:
`tableMemo` с теми же зависимостями (срез `sorting`, модель до сортировки), сброс
страницы `table.autoResetPageIndex()` после пересчёта (`skipFirstRun`), функция колонки
— `column.getSortFn()`, доступность — `column.getCanSort()`, копирование строки с
переставленными детьми — `copyInstancePropertiesWithoutMemos`. Порядок равных — по
`row.index`, как у TanStack.

### 2. Значения один раз на строку

Перед сортировкой уровня для каждой строки один раз читаются значения сортируемых
колонок. Функция по контракту `constructSortFn` (есть поле `sort`) получает значения,
уже приведённые её `resolveDataValue`, — `sort(a, b, rowA, rowB, columnId)` вызывается
с ними и с настоящими строками. Иначе — `sortFn(rowA, rowB, columnId)`, как у TanStack.
Проверка `sortUndefined` берёт прочитанное значение.

Встроенные функции TanStack (`text`, `alphanumeric`, `basic`, `datetime` и варианты)
собраны через `constructSortFn`, поэтому идут быстрым путём без изменений.

### 3. `rowsById`

Модель отдаёт `rowsById`, где копии родителей с переставленными детьми заменяют
оригиналы. Обёртка CS24 удаляется; требование CS24 остаётся и проверяет то же.

### 4. Сортировка по подписи

`optionLabelSortFn` (ADR 0063) собирается через `constructSortFn`: ключ значения
(группа и место, массив — поэлементно, пустое — отдельная отметка) — в
`resolveDataValue`, сравнение ключей — в `sort`. Кэш ключей на проход сортировки
больше не нужен: ключ считается один раз на строку.

## Границы

- **Ускорение своего `sortFn` приложения** — не входит: он принимает строки; путь —
  собрать его через `constructSortFn`.
- **Нарезка сортировки по кадрам, Worker** — не входят.
- **Перерисовка после сортировки** (~220 мс на 100 000 строк) — не входит.

## Отвергнутые альтернативы

- **PR в TanStack** — решение за upstream и его релизом; модель нужна сейчас.
- **Новая опция колонки `compareValues`** — расширение публичного API ради того, что
  уже даёт `constructSortFn`.
- **Строки-заместители `{ getValue }` для встроенных функций** — объект на строку и
  вызов `getValue` на паре; `resolveDataValue` + `sort` дают то же без них.

## Последствия

- **+** Построение модели на 100 000 строк — вдвое быстрее и больше (SM7).
- **+** Обход CS24 не нужен: `rowsById` верен по построению.
- **−** Своя копия устройства модели: при обновлении TanStack паритет держат SM1–SM4
  (одни сценарии через обе фабрики).
- **Публичный API:** не меняется.

Модульные — `__tests__/sortedRowModel.test.ts`, перформанс — `performance/interaction`.

| ID  | Требование                                                                                                                     | Вид  |
| --- | ------------------------------------------------------------------------------------------------------------------------------ | ---- |
| SM1 | Порядок совпадает с моделью TanStack для встроенных функций по одной колонке и при мультисортировке, по возрастанию и убыванию | unit |
| SM2 | Порядок совпадает с TanStack при `sortUndefined` (`1`, `-1`, `'first'`, `'last'`, `false`) и `invertSorting`                   | unit |

| SM4 | Свой `sortFn` колонки получает настоящие строки (`row.original` доступен), порядок совпадает с TanStack                        | unit |
| SM5 | `rowsById` указывает на строки модели, в том числе на копии родителей с переставленными детьми                                 | unit |
| SM6 | Без сортировки модель — исходная; при тех же входах — тот же объект; смена сортировки сбрасывает страницу, как у TanStack      | unit |
| SM7 | Перф: построение модели на 100 000 строк — не дольше половины модели TanStack на тех же данных                                 | perf |

## План внедрения

1. Фабрика в `plugins/columnSorting/sortedRowModel.ts` вместо обёртки CS24.
2. `optionLabelSortFn` — через `constructSortFn`.
3. Тесты SM1–SM7; CS24 и OS1–OS12 — зелёные.
4. Документация: ADR 0012, «Обходы апстрима», roadmap.
