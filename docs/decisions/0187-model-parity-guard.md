# 0187 — Страж паритета клиентской и серверной моделей строк

- **Статус:** Принято и внедрено (решения — по итогам прожарки 2026-11-05)
- **Дата:** 2026-11-05
- **Слой:** только тесты (`src/lib/__tests__`): страж читает публичные типы и диагностику плагинов и в
  сборку не входит.
- **Связано:**
  - [ADR 0138](0138-server-side-row-model.md) — серверная модель строк.
  - [ADR 0151](0151-scenario-completeness.md), [ADR 0117](0117-story-controls.md) — стражи полноты с
    перечнем и причиной.
  - [ADR 0036](0036-plugin-contract-diagnostics-and-a11y.md) — `diagnose`.
  - [ADR 0163](0163-layer-boundaries-and-guards.md) — базы с причиной.

## Контекст

Фичи ложатся на две модели строк: клиентскую и серверную. Аудит паритета 2026-11-05 нашёл расхождения
вручную: `scrollToRow`, выгрузка страницы, редактор `object`, приход ветки, новые строки в SSRM.
Часть различий решена осознанно, но записаны они по разным ADR, а новое расхождение автоматически не
ловится: аргумент фабрики появляется, а что он делает в другой модели, никто не решал.

## Решение

### 1. База

`__tests__/modelParity.baseline.ts`: для каждой фабрики `/plugins` записан каждый её публичный аргумент
— `same` или различие. Запись вынуждает автора нового аргумента решить про обе модели.

- **`same`** — аргумент работает в обеих моделях.
- **`differs`** — осознанное различие: причина и номер ADR. Постоянное, только с решением.
- **`debt`** — различие, которое надо закрыть: причина и строка из «Известных проблем» roadmap. На момент
  принятия таких записей нет.

Фабрика, инертная в одной из моделей целиком, записывается полем `inertOnServer` с причиной и ADR, или
`onlyOnServer`: её аргументы отдельно не решаются.

Различия поведения без своего аргумента (пункт меню, анимация, счётчик) — раздел `BEHAVIOUR_DIFFERENCES`
с теми же полями. Осознанные различия аудита записаны в базу.

### 2. Сверка

- Аргументы фабрик берутся из публичных типов, как в реестре исходов ADR 0151: новый аргумент без
  записи и запись без аргумента роняют страж.
- Каждая фабрика монтируется на обеих моделях, и её `diagnose` сверяется с базой: инертна только в SSRM
  без записи `inertOnServer` — падение; запись есть, а фабрика активна — падение.

### 3. Что страж не ловит

Расхождение внутри уже записанного аргумента: если `same`-аргумент перестал работать в одной модели,
страж этого не увидит. Его дело — заставить принять решение, а поведение доказывают тесты фичи.

## Отвергнутые альтернативы

- **Прогон сценариев на обеих моделях со сравнением DOM.** Ловит и скрытые расхождения, но различия по
  замыслу дают много шума, а цена — ещё один большой набор.
- **Таблица в ADR, как реестр исходов.** 182 строки не читаются, а база в TS проверяется компилятором.
- **База только из различий, без `same`.** Новый аргумент не отличить от проверенного.
- **`debt` «только сокращается» по числу записей.** Автоматически устаревание видно только у
  инертности; ссылка на «Известные проблемы» держит долг на виду и работает для любого случая.

## Последствия

- **+** Новый аргумент плагина требует решения про обе модели; различия собраны в одном файле.
- **−** Правка базы на каждый новый аргумент.
- **Публичный API:** не меняется.

## Требования

| ID  | Требование                                                                                                | Тест      |
| --- | --------------------------------------------------------------------------------------------------------- | --------- |
| PY1 | Каждый публичный аргумент каждой фабрики `/plugins` есть в базе, запись без аргумента роняет страж        | модульный |
| PY2 | Запись `differs` несёт причину и существующий ADR                                                         | модульный |
| PY3 | Запись `debt` ссылается на строку «Известных проблем» roadmap                                             | модульный |
| PY4 | Каждая фабрика монтируется на обеих моделях; инертность только в SSRM требует записи, запись — инертности | модульный |
| PY5 | Различия поведения без аргумента несут те же поля, имена не повторяются                                   | модульный |

## Внедрение

Этап один. База собрана по типам и по диагностике на обеих моделях, различия — из ADR. Стражи проверяют
и настоящую базу, и нарочно испорченную: `modelParity.check.ts` — чистые функции, тест кормит их
примерами с ошибкой.
