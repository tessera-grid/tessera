# 0009 — Покрытие тестами: визуальные + перформанс

## Контекст

Правила покрытия визуальными тестами жили в `docs/architecture/visual-tests.md`.
Но `docs/architecture/` описывает, _как устроена_ Tessera, а не _что обязательно_;
нормативному правилу («каждый плагин обязан иметь тесты») там не место — его дом
реестр решений. Правило уже цитируется как норма из [ADR 0001](0001-spec-driven-development.md),
[ADR 0005](0005-virtualization-tanstack-virtual.md), [ADR 0006](0006-dnd-with-dnd-kit.md)
и [ADR 0010](0010-invert-core-plugins-registry.md) — то есть де-факто это решение,
оформленное не как ADR.

При этом визуальное покрытие — только **половина** гарантии. Поведение Tessera не
только визуальное, но и **перформансное**: виртуализация ([ADR 0005](0005-virtualization-tanstack-virtual.md)),
fast-scroll ([ADR 0008](0008-fast-scroll.md)), стоимость монтирования плагинов на
кадр. Зелёный визуальный тест доказывает, что грид _выглядит_ и _размечен_ как
обещано, но ничего не говорит о том, держит ли он бюджет кадра под нагрузкой.
Значит, полное покрытие плагина или компонента складывается из **двух видов**
тестов, и оба должны быть закреплены нормой.

## Решение

**Покрытие каждого плагина и каждого UI-компонента таблицы состоит из двух видов
тестов — визуальных и перформанс.** Оба обязательны, оба запускаются через
`npm test`, оба следуют spec-driven дисциплине ([ADR 0001](0001-spec-driven-development.md)):
требования живут в ADR потребности, а каждый тест реализует ровно одно требование
и назван по нему.

**Два вида физически разделены по папкам.** Визуальные тесты живут в `visual/`,
перформанс — в `performance/` (под `src/lib/stories/__tests__/`). Файл не смешивает
виды: тест-файл целиком принадлежит одному виду и лежит в его папке. Это делает
границу видимой в дереве и позволяет гонять любой вид точечно (`npm test -- visual`
/ `npm test -- performance`).

### Визуальные тесты

Проверяют **внешний вид** грида: вёрстку, стили, расположение и размеры элементов,
роли и атрибуты доступности, визуальные состояния (hover, зебра, sticky-шапка,
overlay перетаскивания) — компонентов и плагинов таблицы.

- **Запуск через `npm test`.** Раннер — Vitest browser mode: тесты выполняются в
  реальном Chromium через Playwright против **реальной раскладки**, а не в jsdom
  (который не воспроизводит layout и тайминг кадров). Истории Storybook
  переиспользуются как фикстуры через `composeStories`.
- **Полное покрытие.** Каждый плагин и каждый рендерящийся UI-компонент обязан
  иметь визуальные тесты. Ни один не поставляется без них.
- **Одно требование на тест.** Тест проверяет ровно одно требование из
  спецификации плагина/компонента. Тест, проверяющий две вещи, — это два теста.
- **Самовосстановление.** Если тест мутирует данные, состояние, выбор, раскрытие,
  порядок и т. п., он обязан вернуть таблицу в исходное состояние по завершении.
  Тесты не протекают состоянием друг в друга; порядок выполнения не меняет исходы.
- **Никакого хардкода мок-данных.** Тест не привязывается к содержимому дефолтных
  моков (`__mocks__/columns`, `__mocks__/data`) — ни к текстам заголовков, ни к id
  колонок, ни к значениям ячеек, ни к их числу. Такой хардкод делает тест
  ложно-красным при правке моков, не связанной с проверяемым требованием, и
  маскирует настоящую регрессию за шумом. Вместо этого:
  - **готовность грида и адресация элементов — через контракт вёрстки**, а не через
    текст мока: ждать монтирования по селектору (появились `.data-grid__head-cell`),
    а не по `getByText('Country')`; целиться в столбец/ячейку через контрактные
    атрибуты (`data-*`, `aria-colindex`, `role`), а не через захардкоженный ярлык;
  - **если требованию нужны конкретные значения — фикстура задаётся в самом тесте**
    (`dataOverride`, явные колонки), чтобы тест владел своими данными и был
    самодостаточным (как `R5`), а не читал их из общих моков;
  - **ожидаемое выводится, а не дублируется**: сравнивается с тем, что тест сам подал
    на вход или прочитал из контракта, а не с копией значения из мока.

  Требования формулируются об **инвариантах поведения** («i-я ячейка выровнена по
  ширине и позиции с i-м заголовком», «после сортировки по столбцу значения
  монотонны»), а не о конкретных строках дефолтного мока. Когда контракт вёрстки не
  даёт стабильной точки привязки и тест вынужден опираться на мок — это сигнал, что
  в DOM не хватает атрибута; заводится потребность на его добавление, а не хардкод.
- **Именование по требованию с ID-префиксом.** Имя теста начинается с ID
  требования из таблицы требований соответствующего ADR, за которым идёт краткое
  имя, в формате `<ID>: <краткое имя>` (например, `D7: ручка проявляется при
  наведении на строку`). Префикс из ADR фичи (`R<n>` для ядра, `V<n>` для
  виртуализации, `D<n>` для drag & drop) обязателен и единообразен: отчёт
  `npm test` называет точное требование, а ID даёт прямую ссылку на его
  определение. Отсюда **одно требование = один ID = один тест**: тест, который
  нельзя пометить единственным ID, покрывает больше одного требования и должен
  быть разбит.

### Перформанс-тесты

Проверяют **производительность** таблицы во всех условиях — под разным объёмом
данных, в разных режимах и при разных комбинациях параметров.

- **Запуск через `npm test`** тем же раннером: тайминг кадров имеет смысл только в
  реальном браузере.
- **Что измеряют.** Реальную работу главного потока на кадр (script/style/layout),
  снятую CDP-трейсом (Playwright `Tracing`), а не rAF по стенным часам, — поэтому
  метрика не зависит от частоты дисплея.
- **Пороги — абсолютные, из RAIL / Core Web Vitals**, а не измеренные потолки:
  - прокрутка → **RAIL Animation**: `p95` работы на кадр ≤ `1000/60` ≈ 16.7 мс;
  - первая отрисовка → **RAIL Load**: самая длинная задача монтирования ≤ 1000 мс;
    плюс long tasks (> 50мс) и TBT как прокси готовности к отзывчивости (CWV INP).
  - LCP/INP/CLS — полевые метрики страницы; на изолированном компоненте меряются
    их лаб-прокси (кадр, long tasks/TBT, время до интерактивности).
- **Замер под ×4 CPU-троттлингом** (стиль Lighthouse): пороги RAIL/CWV заданы под
  средний девайс, и троттлинг заставляет их «кусаться» относительно референса, а не
  быстрой dev-машины.
- **Известный недостиг = xfail.** Кейс, не укладывающийся под троттлингом в свой
  абсолютный порог, помечается `knownShortfall` и гоняется через `test.fails`:
  сборка зелёная, цель зафиксирована; когда грид оптимизируют — xfail покраснеет и
  напомнит снять метку. Неожиданный выход за порог (не помеченный) — красная
  регрессия.
- **Покрытие во всех условиях** — куб 2×2×2: **объём** (30×500 / 1000×1000) ×
  **режим** (без плагинов / все) × **операция** (отрисовка / прокрутка). Комбинации
  не должны молча выпадать из покрытия.
- **Дашборд.** Каждый кейс пишет результат (команда `perfRecord`), генератор
  `scripts/perf-report.mjs` рендерит локальный `performance-results/index.html` со
  статусом (в бюджете / xfail / регрессия) и статистикой (p95/p99/longest/long
  tasks/TBT). Команды `npm run perf` (прогон + борд) / `npm run perf:report`.
- **Та же spec-driven дисциплина.** Перформанс-требования (`P1`–`P8`) живут в ADR
  фичи ([ADR 0004](0004-core-on-tanstack-table.md)), один именованный тест на кейс.

## Как это ложится на текущую настройку

Тесты живут в `src/lib/stories/__tests__/` и **физически разложены по виду в две
папки** — `visual/` и `performance/`. Покрытие меряется относительно
**спецификации** (ADR), а не строк кода: фича «покрыта», когда каждое её требование
— визуальное и перформансное — имеет соответствующий тест. Общие фикстуры
(`helpers.tsx`) и инфраструктура измерений (`perf.commands.ts`) лежат в корне
`__tests__/`, рядом с обеими папками.

- **`visual/`:** `core-*` (структура, размеры, роли, состояния, раскладка),
  `virtualization`, `row-dragging`, `column-dragging`, `column-pinning`
  ([ADR 0011](0011-column-pinning.md)), `column-sorting`
  ([ADR 0012](0012-column-sorting.md)).
- **`performance/`:** матрица-куб 2×2×2 (операция × объём × плагины, требования
  P1–P8 из [ADR 0004](0004-core-on-tanstack-table.md)), разложенная по операции:
  `first-render` (P1/P3/P5/P6 — работа монтирования) и `scroll` (P2/P4/P7/P8 —
  работа на кадр при прокрутке). Измерители — `measureRenderWork` и
  `measureScrollWork` через CDP-команды (`perf.commands.ts`).

**Перф-дашборд.** Каждый перф-кейс записывает свой результат (команда `perfRecord`)
в `performance-results/latest.json` — хранится только последний прогон. Скрипт
`scripts/perf-report.mjs` рендерит из него самодостаточный `performance-results/index.html`
с таблицей кейсов, барами «значение vs бюджет» и детальной статистикой (p95/p99/
longest/над-бюджетом). Команды: `npm run perf` (прогон + генерация) или
`npm run perf:report` (только генерация). Каталог `performance-results/` в `.gitignore`
— борд локальный и пересобирается прогоном.

## Последствия

- **+** Оба вида покрытия закреплены как обязательные: обещание фичи honest by
  construction и по внешнему виду, и по производительности.
- **+** Норма покрытия живёт там, где ей место, — в реестре решений, а не в
  описательной `architecture/`, и цитируется другими ADR по стабильной ссылке.
- **+** Диагностируемость сохраняется по обоим видам: красный тест называет точное
  сломанное требование (визуальное или перформансное) через его ID.
- **−** Больше входного трения: фича не «покрыта», пока не имеет обоих видов тестов,
  даже если перформанс кажется очевидно достаточным. Это намеренная цена дисциплины.
- **Заменяет** `docs/architecture/visual-tests.md`: файл удалён, все ссылки ведут на
  этот ADR.
