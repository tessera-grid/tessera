# 0067 — Инкрементальная исходная модель ленивых детей

- **Статус:** Принято (решения — по итогам прожарки 2026-10-08)
- **Дата:** 2026-10-08

- **Связано:**

  - [ADR 0066](0066-lazy-children-answer-batching.md) — пачка ответов до кадра.

## Контекст

Ответ `loadChildren` меняет срез `loadedChildren`, и ленивая модель
([`lazyCoreRowModel`](../../src/lib/plugins/rowExpanding/lazyCoreRowModel.ts))
пересобирает исходную модель TanStack целиком: на 100 000 корней — 100 000 вызовов
`constructRow` и `getSubRows`, хотя изменились дети одной строки. Профиль прихода
(2026-10-08, RE73): ~200 мс из ~500 под ×4 CPU — сборка модели, ещё ~55–70 мс — сборка
мусора от новых объектов строк.

Строки TanStack переживают смену модели: кэш значений зависит от `original`, кэш
листовых строк — от массива `subRows`, индекс отображения пересчитывается на каждой
модели. Инкрементального API у TanStack нет.

Решено (прожарка 2026-10-08):

- инкремент — только при смене ответов при тех же `data`;
- родитель с новыми детьми и его предки — новые объекты строк, прежняя модель не
  меняется;
- `rowsById` — честная копия; доказательство — паритет с полной сборкой и перф
  (заменено [ADR 0069](0069-rowsbyid-handover.md): словарь переходит новой модели).

## Решение

### 1. Когда инкремент

Ленивая модель помнит последнюю модель, её `data` и срез ответов. Если `data` те же, а
срез ответов другой, модель собирается из прежней; иначе — полная сборка TanStack, как
раньше (смена `data` запускает автосбросы TanStack, смена ответов — нет).

### 2. Как

Изменённые строки — те, чей ответ в срезе другой (пришёл, заменён, удалён), есть в
прежней модели и чьи дети берутся из ответа (своих `subRows` в данных нет). Из них
берутся верхние: строка, предок которой тоже изменён, пересобирается вместе с ним.

- Изменённая строка — новый объект (`constructRow` с теми же `id`, `original`, `index`,
  `depth`, `parentId`), её дети собираются из ответа тем же обходом, что у TanStack
  (`getSubRows` — свой из данных, иначе ответ).
- Предки — новые объекты с тем же содержимым и массивом `subRows`, где заменён
  изменённый потомок.
- `rows` — копия прежних корней с заменёнными; `flatRows` — копия прежнего массива,
  где участок изменённого поддерева заменён целиком, а предки — на своих местах
  (порядок TanStack: строка, затем её потомки); `rowsById` — словарь прежней модели,
  правленный на месте ([ADR 0069](0069-rowsbyid-handover.md)). Остальные строки —
  прежние объекты.

## Границы

- **Смена `data`** — из прежней модели по тождеству строк
  ([ADR 0194](0194-incremental-data-changes-and-client-transactions.md)).
- **`rowsById` без копии** — решено отдельно ([ADR 0069](0069-rowsbyid-handover.md)).
- **Рендер и виртуализатор** — не меняются.

## Отвергнутые альтернативы

- **Править `subRows` прежнего объекта строки** — дешевле, но прежняя модель меняется
  задним числом: ловушка для мемоизации по модели и строке.
- **Инкремент и при смене `data`** — индексы, `getRowId` от индекса, автосбросы
  TanStack; другой масштаб риска.

## Последствия

- **+** Приход ответа не создаёт 100 000 новых строк: сборка модели вдвое быстрее
  полной без рендера (IM8, ~70 против ~135 мс под ×4 со штатными фичами TanStack); в
  гриде RE38 ~480–620 → ~350–360 мс, один асинхронный ответ (RE73) ~550 → ~290 мс,
  пачка из пяти ~1000 → ~320 мс.
- **−** Больше половины цены инкремента была в новом `rowsById` на все строки (~50 мс);
  убрано передачей словаря ([ADR 0069](0069-rowsbyid-handover.md)).
- **−** Своя сборка рядом с TanStack: расхождение ловит паритет IM1–IM5.
- **Публичный API:** не меняется.
