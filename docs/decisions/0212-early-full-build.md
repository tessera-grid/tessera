# 0212 — Ранний переход к полной сборке при смене `data`

- **Статус:** Принято (решение автора 2026-11-11)
- **Дата:** 2026-11-11
- **Слой:** ядро — смена `data` из прежней модели (`core/dataChanges.ts`). Не плагин: модель ядра
  строит ядро.
- **Дополняет:** [ADR 0194](0194-incremental-data-changes-and-client-transactions.md) — смена `data`
  из прежней модели и порог полной сборки; [ADR 0199](0199-row-shifts-in-the-middle-of-data.md) —
  сдвиги в середине `data`.
- **Связано:** [ADR 0211](0211-deferred-row-positions.md) — отложенные места строк.

## Контекст

Смена `data` собирает модель ядра из прежней (ADR 0194). Если изменённых, вставленных,
перенесённых и удалённых строк больше четверти — полная сборка. Путь до этого решения для данных,
пришедших новыми объектами (ответ сервера, `map` с копией строк), — три попытки подряд:

1. замена на месте (`patchFlat`) — отказ на первой перенесённой строке;
2. сдвиг (`patchShifted`) — две указки идут по спискам, пока несовпадений не станет вдвое больше
   бюджета;
3. сборка по уровням (`level`) — словарь прежних строк, id каждой новой строки, поиск перенесённых
   (наибольшая возрастающая цепочка мест) и создание строк, пока не кончится бюджет — около 25 000
   строк на 100 000.

Только после третьей попытки идёт полная сборка. Замер без троттлинга (2026-11-11, 100 000 строк,
перенос строки и копия всех объектов): смена `data` — 133 мс, из них полная сборка ~45 мс, остальное
— попытки. Под ×4 CPU — MS11-base, 376 мс.

## Решение

Когда сдвиг отказал по бюджету, ядро считает объекты нового `data`, которых нет в прежнем (`Set`
прежнего `data`). Их больше бюджета — полная сборка сразу, без сборки по уровням.

Отказ строгий: объект, которого не было в прежнем `data`, сборка по уровням оплачивает из бюджета —
это вставленная строка, строка с новыми данными или перенесённая строка. Больше таких объектов, чем
бюджет, — сборка по уровням откажет всегда. Меньше — она идёт, как прежде.

Проверка — только после отказа сдвига по бюджету: сдвиг отказывает раньше на данных с деревом и на
мелких сменах, а успешные инкременты её не платят.

## Отвергнутые альтернативы

- **Отказ сразу по отказу сдвига** — сдвиг с шагом вперёд на одну строку сбивается на нескольких
  разнесённых вставках, а сборка по уровням с ними справляется: отказ сдвига не доказывает отказ
  сборки по уровням.
- **Выборочная проверка части строк** — не строгая: решение зависело бы от выборки.

## Последствия

- **+** Данные новыми объектами собираются полной сборкой без трёх попыток впереди.
- **−** При отказе сдвига по бюджету — `Set` прежнего `data` (~3 мс на 100 000 без троттлинга), даже
  если сборка по уровням затем пройдёт.
- **Публичный API** не меняется.

## Требования

| ID  | Требование                                                                                                                                                                 | Тест                 |
| --- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------- |
| EB1 | `data` новыми объектами, которых больше бюджета инкремента, после отказа сдвига собирается полной сборкой без сборки по уровням; модель — как у полной сборки              | модульный            |
| EB2 | Разнесённые вставки и перенос, на которых сдвиг отказывает, а новых объектов не больше бюджета, собираются по уровням из прежней модели: прежние объекты строк сохраняются | модульный            |
| EB3 | `perf:compare` MS11, MS11-base, IU13, IU14 против ревизии до внедрения — без регрессии; итог записан в «Внедрение»                                                         | отчёт `perf:compare` |

## План внедрения

Один этап: решение, EB1–EB2, затем EB3.

## Внедрение

2026-11-11. EB1 — красный без раннего отказа (`getRowId` вызывается дважды на строку), EB2 — красный
при отказе по одному отказу сдвига (разнесённые вставки уходят в полную сборку). Без троттлинга
смена `data` новыми объектами на 100 000 строк — 133 → ~49 мс.

EB3 — `perf:compare` против `a92bdd52` (рабочая копия с ADR 0208–0211), до 15 раундов, ×4 CPU:

| Случай                                  | A, мс | B, мс | B/A       | Вердикт       |
| --------------------------------------- | ----- | ----- | --------- | ------------- |
| MS11-base — полная сборка 100 000 строк | 376,7 | 184,4 | 0,490     | улучшение     |
| MS11 — перенос строки                   | 44,6  | 33,7  | 0,756     | улучшение     |
| IU14                                    | 46,0  | 32,1  | 0,697     | улучшение     |
| IU13, IU13-base, IU14-base              | —     | —     | 0,98–1,02 | без изменений |

Доля этого ADR — MS11-base: в замере ADR 0211 против той же ревизии она была 376,5 → 390,4 мс.
Остаток полной сборки — `constructRow` TanStack на каждую строку и сборка мусора.
