# 0201 — Быстрый поиск по склеенному тексту строки

- **Статус:** Принято (прожарка 2026-11-09)
- **Дата:** 2026-11-09
- **Изменён:** 2026-11-10 — текст строки без `row.getValue` и форматтер колонки без типа и
  вариантов без проверок на каждое значение (§1, §4, QT11): первый поиск на стенде против AG Grid
  — 1,1 с → 0,49 с.
- **Слой:** плагин `quickSearchModel` — склеенный текст строки и его кэш (`search.ts`); стадия
  фильтра в `shared/rowModels/filteredRowModel.ts` — проверка строки, подготовленная функцией
  поиска один раз на проход; ядро — форматтер колонки в `core/dataTypeFormat.ts`. Форматтер — в
  ядре, потому что показанный текст типа принадлежит ядру (ADR 0172, §3): им же пишут ячейка и
  выгрузка. Стадия остаётся в `shared/`: она общая у `columnFilteringModel` и `quickSearchModel`
  и о плагине поиска не знает (ADR 0163).
- **Изменяет:**
  - [ADR 0172](0172-column-data-type.md) — DT15: текст кэшируется на строку — один склеенный
    текст по колонкам поиска, а не текст на строку и колонку.
- **Связано:**
  - [ADR 0045](0045-filtering.md), §6 — что и как ищет быстрый поиск; здесь не меняется.
  - [ADR 0200](0200-own-row-engine.md) — стадия фильтра движка и её паритет с
    `createFilteredRowModel` (EN11).
  - [ADR 0099](0099-perf-gates-and-ab-compare.md) — гейт против базы того же теста и
    `perf:compare`.
  - Замер `docs/research/tessera-vs-ag-grid-2026-11-09.md`, пункт 2.

## Контекст

Поиск по 100 000 строк × 10 колонок под ×4 CPU занимает 1,57 с против 0,72 с у AG Grid
Community. Стадия фильтра зовёт функцию поиска на каждую пару «строка × колонка» — миллион
вызовов. Каждый вызов ищет колонку по `id`, достаёт кэш строки и сверяет его ключи, ищет текст
колонки в `Map` и разрешает тип колонки. Кроме того, на каждую строку создаются объекты
`columnFilters` и `columnFiltersMeta`, а на каждую пару — замыкание `addMeta`. По профилю:
`quickSearchFilter` — 228 мс, `getValue` — 98 мс, `textsOf` — 97 мс, `checkRow` — 94 мс,
формат и разрешение типа — около 90 мс.

### Как у других

|                 | Что проверяет поиск                                 | Кэш                                 |
| --------------- | --------------------------------------------------- | ----------------------------------- |
| AG Grid         | склеенный текст строки по колонкам, одно `includes` | текст на узел, сброс при смене узла |
| MUI X Data Grid | функция на колонку (`getApplyQuickFilterFn`)        | —                                   |
| TanStack Table  | `globalFilterFn` на каждую пару «строка × колонка»  | нет                                 |

Tessera берёт склеенный текст AG Grid: показанный текст строки по колонкам поиска считается один
раз и проверяется одним `includes`.

## Решение

### 1. Склеенный текст строки

Текст строки — показанные тексты колонок поиска в нижнем регистре, склеенные разделителем
U+0000, в порядке колонок. Разделитель не даёт запросу совпасть на стыке двух колонок. Колонка
без типа с нетекстовым значением (ADR 0172, DT15) даёт пустую часть. Нижний регистр берётся у
каждой части отдельно, до склейки.

Запрос, в котором есть сам U+0000, проверяется прежним путём — по каждой колонке.

### 2. Проверка, подготовленная на проход

У функции поиска появляется необязательное свойство `prepareRowCheck(table, columns, value)`.
Стадия зовёт его один раз на проход с колонками поиска и значением запроса; оно возвращает
проверку строки или `undefined` — тогда стадия идёт прежним путём по колонкам. Своя `globalFilterFn` без этого свойства — её задаёт плагин автора опцией таблицы — работает
как прежде, с `addMeta`. Стоковая
`createFilteredRowModel` свойство не знает и зовёт `quickSearchFilter` по колонкам: так паритет
(EN11) сверяет склеенный путь с путём по колонкам.

### 3. Кэш

Кэш — `WeakMap` по объекту строки: склеенный текст и подпись прохода. Подпись — колонки поиска
с их `columnDef`, `locale`, `timeZone` и реестр `dataTypes`; одинаковая подпись подряд — тот же
объект, поэтому сверка с кэшем строки — одно сравнение ссылок и сверка `original`. Смена
`data` даёт изменённым строкам новые объекты (ADR 0200, EN32), и их кэш сбрасывается сам. Кэша
текста на колонку больше нет: путь по колонкам (§1) считает текст без кэша.

### 4. Форматтер колонки

`columnFormatter(table, column)` в `core/dataTypeFormat.ts` разрешает тип колонки один раз и
возвращает функцию `(value, row) => string`. `formatDataTypeValue` идёт через то же тело
форматирования с уже разрешённым типом, поэтому ячейка, поиск и выгрузка показывают один текст.
У колонки без типа и вариантов форматтер — строка значения: варианты и тип не проверяются на
каждое значение, текст тот же (QT6).

### 4а. Значение ячейки при сборке текста

Текст строки читает значение функцией доступа колонки `accessorFn(original, index)` — то же,
что `row.getValue`, но без поиска колонки по id и записи в кэш значений строки на каждую ячейку;
колонка без функции доступа читается `row.getValue`. Нижний регистр — раз на склеенный текст:
разделитель U+0000 не буква и не меняет перевод соседних частей. Причина — профиль первого поиска
на стенде против AG Grid 2026-11-10 (100 000 × 10, «bravo 1», ×4 CPU): из ~970 мс прохода 750 мс
уходило на сборку текста — `row.getValue` TanStack (~400 мс) и `formatTyped` (~250 мс) на миллион
ячеек. После правки первый поиск — ~0,49 с против ~1,1 с; AG Grid Community 36.3 на том же стенде
в прошлых сериях — 0,44–0,46 с.

### 5. Вердикты строки

Когда активен только поиск, без фильтров колонок, строки ссылаются на два общих замороженных
объекта `columnFilters` — `{ __global__: true }` и `{ __global__: false }` — и на общий пустой
замороженный `columnFiltersMeta`. С фильтрами колонок у каждой строки свои объекты, как прежде.
Фасеты TanStack эти объекты только читают; пишет в них только стадия. Копия родителя в дереве
переиспользуется, когда вердикт строки — тот же объект (ADR 0200, §5): при повторном поиске с
тем же вердиктом копий становится меньше.

## Отвергнутые альтернативы

- **Импорт плагина в стадию фильтра.** Запрещён ADR 0163: код `shared/` плагины не импортирует.
- **Отдельная опция таблицы для подготовленной проверки.** Лишний публичный API ради
  внутреннего контракта стадии и функции поиска.
- **Сужение при удлинении запроса** — проверять только строки, прошедшие прошлый запрос. Это
  отдельная оптимизация со своими краями (выход из поиска, смена колонок и данных); вне объёма.
- **Ранняя остановка на совпадении в первой колонке.** Кэш с неполным текстом
  сократил медиану QT9 с 595 до 348 мс в трёх парных диагностических замерах.
  Следующий запрос FL35 дополнял кэш и вырос со 125 до 351 мс.
- **Значение ячейки мимо `row.getValue`.** Аксессор колонки напрямую быстрее, но `getValue`
  держит кэш значений строки для ячеек и даёт `accessorFn` тот же вход.

## Границы

- Серверный поиск — без изменений: ищет сервер (ADR 0053).
- Что ищется и как — без изменений (ADR 0045, §6; ADR 0172, DT15).
- Своя `globalFilterFn` плагина автора — прежний путь по колонкам.

## Последствия

- Цена поиска почти не растёт с числом колонок поиска: одна проверка на строку (QT8).
- Память: одна строка текста на строку таблицы вместо `Map` текстов по колонкам.
- Код, который пишет в `row.columnFilters` при одном поиске, упадёт на замороженном объекте;
  в библиотеке таких писателей нет (страж EN3, ADR 0200).

## Сценарии

Новых сценариев нет: видимое поведение поиска не меняется, меняется цена. Сценарии поиска —
истории «Filtering» (ADR 0045) и «Columns/Data types» (ADR 0172, S5).

## Внедрение

Один этап. Тесты: модульный `quickSearchJoined` (QT1–QT7), перф QT8–QT9 — в `interaction`,
паритет склеенного пути с путём по колонкам — EN11 (`npm run test:parity`). TQ1, мутации по
одной: части текста без нижнего регистра — падает QT1; склейка без разделителя — QT2; без кэша
строки и стадия без `prepareRowCheck` — QT3; подпись прохода без `locale` и без сверки колонок —
QT4; запрос с разделителем склеенным путём — QT5; форматтер колонки без разрешённого типа — QT6;
вердикты строки объектом на строку — QT7.

QT9 использует два свежих монтирования. Запрос `a` сохраняет все строки и
историческую серию построения текста. Запрос `jamaica` записывается как
`QT9-narrow`; тест проверяет уменьшение числа строк после измерения.

QT8 сравнивает новый путь с ним же: база — тот же поиск, в котором ищется одна колонка, а девять
исключены `enableGlobalFilter: false`. Поэтому замер с десятью колонками на базу не опережает, а
показывает, сколько стоят ещё девять колонок: склеенный текст длиннее, `includes` идёт по нему
дольше. Ускорение против прежнего кода показывает QT10. Потолок QT8 сначала стоял ×1,3, и мутация
«стадия без `prepareRowCheck`» (прежний путь по колонкам) его не роняла: 949 мс при потолке 957
(×1,29 базы). Требование ужесточено до ×1,2. Замер 2026-11-09 под ×4 CPU: склеенный путь —
734 мс против базы 643 мс (×1,14, потолок 772); мутация — 920 против 672 мс и 997 против 696 мс
(×1,37 и ×1,43, обе попытки красные). Первый поиск после монтирования (QT9) — 1847 мс: тексты
всех строк считаются в этом проходе.

QT10 (2026-11-10): `perf:compare -- 9ad41d35 --cases FL35` под ×4 CPU, 5 раундов — поиск на 100 000
строк 1107,8 → 759,7 мс, ×0,69 (0,63–0,85), «улучшение». Прогон — на master с ADR 0202–0203 и
работой 2026-11-10; регрессии против 9ffb4ef1 (ревизия внедрения) нет: FL35 ×1,04 (0,95–1,12).

Поправка 2026-11-10 (§4, §4а, QT11): TQ1 — QT11 на прежнем `search.ts` падает (`getValue` строки
зовётся при первом поиске). Стенд против AG Grid, только Tessera, ×4 CPU, четыре прогона: первый
поиск «bravo 1» на 100 000 × 10 — 1,02–1,16 с → 0,47–0,57 с. `perf:compare -- 47a2b0bb`, 15 раундов,
машина шумная: QT9 (первый поиск после монтирования, все плагины) 1412,9 → 709,0 мс, ×0,50
(0,37–1,01); FL35 ×1,05 и DT16 ×0,98 — без вердикта, повторный поиск читает текст из кэша.

26 ноября четыре контрольных прогона QT9 дали 541–589 мс. Прямое добавление
строк без типа и вариантов в поисковый текст дало 479–565 мс в трёх повторах.
Медиана сместилась с 555 до 512 мс, диапазоны пересеклись, а FL35 почти не
изменился. Эксперимент снят, целевой бюджет первого поиска остаётся открытым.
