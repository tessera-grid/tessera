## Контекст

В клиентском режиме любая смена массива `data` собирает модель ядра заново и пересчитывает всю
цепочку: сортировку, фильтры, поиск, группировку, раскрытие (ADR 0067, IM7). На 100 000 строк под
×4 троттлингом это полная сборка ядра ~150–240 мс (IS16, IM8), сортировка ~660 мс (SM7), поиск
~850 мс (FL35). Правка одной ячейки при включённой сортировке — порядка 0,8–1 с (~200–250 мс
вживую), далеко за целью отклика 100 мс. До ~10 000 строк цена незаметна.

Транзакций в клиентском режиме нет: `table.applyRowTransaction` работает только с серверной
моделью (ADR 0157), в клиентском — предупреждение «change data instead». Приложение меняет `data`
целиком.

### Как у других

|                 | Изменения данных                                                                            | Транзакции                                                                   |
| --------------- | ------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| AG Grid         | неизменяемый `rowData` с `getRowId`: изменения по идентификаторам, правка на месте не видна | `applyTransaction` правит хранилище грида; новый `rowData` затирает его      |
| MUI X Data Grid | новый `rows` — пересборка                                                                   | `apiRef.updateRows` правит внутреннее состояние; смена `rows` его сбрасывает |
| TanStack Table  | новый `data` — полная сборка                                                                | нет                                                                          |

У AG Grid и MUI X два источника правды: транзакция и проп данных конфликтуют, документация
предупреждает. Tessera берёт неизменяемый режим AG Grid, а транзакцию делает надстройкой над ним.

## Решение

### 1. Разница по тождеству

Новый `data` сравнивается с прежним одним проходом: объект строки тот же — строка не менялась;
id строки (`getRowId` или поле `id` — умолчание Tessera) связывает новый объект с прежней строкой —
строка заменена; нового `id` не было — вставлена; прежнего нет — удалена. Повторяющийся id на уровне
дерева — полная сборка: связать строки нельзя. Строка, чей индекс сдвинула вставка или удаление выше,
— новый объект с прежним поддеревом и прежними значениями ячеек, кроме колонок, чей `accessorFn`
принимает индекс строки; ниже по конвейеру это не работа, модели находят её по id.

Перестановка строк (нарушен порядок выживших) или изменённых, вставленных и удалённых строк больше
порога (доля от числа строк) — полная сборка: она тогда не дороже.

### 2. Модель ядра

Строки с прежним объектом данных — прежние объекты строк, изменённые и вставленные — новые,
удалённые уходят; `rowsById`, индексы, `parentId` и `flatRows` — как у полной сборки (паритет с
TanStack). Прежняя модель не меняется (как ADR 0067, ADR 0069). Дерево из `subRows` — инкремент
поддерева изменённой строки.

### 3. Подсказка вниз по конвейеру

Модель ядра отдаёт смену: изменённые, вставленные и удалённые строки. Каждая модель строк
перекладывает только их:

- **сортировка** — изменённые и вставленные встают на свои места, удалённые уходят, порядок
  равных — как у полной сортировки (из прошлой модели, ADR 0072);
- **фильтры колонок и быстрый поиск** — перепроверяют только изменённые и вставленные;
- **группировка** — строка переезжает между группами, пустая группа уходит, новая появляется;
  агрегаты и число строк группы (ADR 0184) пересчитываются у затронутых групп;
- **раскрытие** — модель раскрытия из прошлой (ADR 0070);
- **виртуализатор** — подсказка первой изменённой позиции списка (ADR 0145); движению строк
  (ADR 0107) подсказка не нужна: план FLIP строится по видимым строкам.

Автосбросы TanStack при смене `data` — те же, что при полной сборке. Выделение ячеек смена `data`
не сбрасывает (§6).

### 4. Клиентская транзакция

`table.applyRowTransaction({ add, index, update, remove, parentId })` в клиентском режиме строит
следующий `data`: прежние объекты нетронутых строк, новые — у изменённых и вставленных, и отдаёт
его опции ядра `onDataChange(next, transaction)`. Приложение кладёт его в `data`, инкремент идёт
по §1. Итог — `'applied'`. Без `onDataChange` транзакция не применяется: итог `'unavailable'` и
dev-предупреждение. Форма транзакции — та же, что у серверной модели (паритет, ADR 0187);
транзакция — действие ядра в канале действий (ADR 0125).

Источник правды один — `data` приложения, как у контролируемых срезов (ADR 0120, ADR 0171).

### 5. Правка на месте — ломающее изменение

Объект строки, изменённый на месте (`row.age = 31; setData([...data])`), остаётся прежним
объектом: грид не видит изменения и показывает прежнее значение (кэш значений ячеек строки).
Обновление `data` должно быть неизменяемым: новый объект у изменённой строки. Так же устроен
неизменяемый режим AG Grid; React требует того же от состояния. **Ломающее изменение** до 1.0:
прежде полная сборка перечитывала все строки. Обнаружить правку на месте дёшево нельзя —
предупреждения нет; README и документация сайта говорят о неизменяемом обновлении.

### 6. Строки держат своё в клиентском режиме

Новый `data` — транзакцией или от приложения — оставляет на своих строках то, что на них стоит,
как серверная модель после транзакции (ADR 0157, §3): активная ячейка переходит за строкой по её
`id`, у удалённой строки — к строке на её месте; углы выделения ведут их `id` (ADR 0180), угол,
ушедший из данных, снимает диапазон; прокрутка держит первую строку экрана, кроме начала списка;
правка открытой ячейки продолжается, у удалённой строки — отменяется с причиной. Смену `data`
таблица замечает после рендера и сообщает слушателям списки строк до и после неё. Смена порядка
без нового `data` (сортировка, фильтр) прокрутку и активную ячейку не держит — как прежде.

## Границы

- Серверная модель строк — без изменений, у неё свой кэш и транзакции (ADR 0157).
- Перестановка строк приложением — полная сборка.
- Вставка и удаление в середине сдвигают индексы строк ниже: их объекты строк пересоздаются, и
  модели ниже перекладывают их по `id` — цена близка к полной сборке модели ядра. Без сдвигов —
  замена на месте и дописывание в конец — модели работают только с изменёнными строками.
- Строки до сохранения (ADR 0178) — слой над источником строк, не трогается.
- Транзакция в ветке (`parentId`) пишет детей в поле `subRows` новых объектов ветки и предков —
  только при `getSubRows` по умолчанию; со своим `getSubRows` итог `'unavailable'` и
  предупреждение. Ветки нет в `data` — `'branchNotLoaded'`. Порядок внутри транзакции —
  обновление, удаление, вставка; `add` без `index` — в конец уровня.

## Отвергнутые альтернативы

- **Копия данных в гриде, как у AG Grid.** Транзакция работала бы без обработчика в приложении,
  но новый проп `data` затирал бы её: два источника правды.
- **Слой транзакций над `data`, как строки до сохранения.** Снимать слой при новом `data` пришлось
  бы по угадыванию, учтён ли он.
- **Инкремент по флагу (`immutableData`).** Правка на месте продолжала бы работать без флага, но
  флаг нужно объяснять, а полная сборка остаётся умолчанием с её ценой.
- **Только ядро и сортировка в первом этапе.** Фильтр, поиск и группировка оставили бы правку
  ячейки на 100 000 строк дорогой.

## Последствия

- Правка ячейки и транзакция на больших таблицах стоят перекладки изменённых строк, а не сборки
  всей цепочки.
- Строки и ячейки нетронутых строк сохраняют объекты: мемоизация по строке не сбрасывается.
- Приложение, менявшее объекты строк на месте, перестанет видеть изменения — нужно неизменяемое
  обновление.
