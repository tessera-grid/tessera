# 0091 — Совместимость окружений: React 18, StrictMode, SSR и пакет глазами потребителя

- **Статус:** Принято (решения — по итогам прожарки 2026-10-11; уточнения внедрения — в «Внедрении»)
- **Дата:** 2026-10-11
- **Связано:**
  - [ADR 0003](0003-formalize-tech-stack.md) — стек, peer-зависимости, сборка `dist`.
  - [ADR 0009](0009-test-coverage-visual-and-performance.md),
    [ADR 0043](0043-honest-test-coverage.md) — виды тестов и честное покрытие.
  - [ADR 0084](0084-cross-browser-support.md) — образец шага «перед публикацией»
    (`test:engines`) и списка исключений с причиной.
  - [ADR 0010](0010-invert-core-plugins-registry.md) — `check:tree-shaking`, единственная
    сейчас проверка поверх `dist`.

## Контекст

В roadmap, в разделе «Не покрыто тестами», перечислены области, которые барьер не
проверяет вовсе. Четыре из них касаются того, в каком окружении грид окажется у
потребителя.

### React 18

Пакет обещает `react ^18 || ^19`, а тесты идут только на React 19. Зависимости 18
поддерживают: Base UI — `^17 || ^18 || ^19`, TanStack Table — `>=18`, TanStack Store и
Virtual, dnd-kit. Расхождение уже есть в коде: `Tooltip` берёт `ref` ребёнка-триггера
из `children.props.ref`. В React 19 ref — обычный проп, а в React 18 он лежит в
`element.ref`, поэтому под React 18 ref триггера теряется.

### StrictMode

StrictMode не включён ни в историях, ни в тестах. Пробный прогон 11 визуальных наборов
(ядро, выбор, раскрытие, закрепление, клавиатура, меню, фильтры, тема, подсветка,
пагинация — 170 тестов) с `configure({ reactStrictMode: true })` прошёл без падений;
пробный тест подтвердил двойной запуск эффектов.

### SSR и гидратация

`renderToString` грида с выбором, сортировкой и пагинацией в node работает без ошибок и
предупреждений. Гидратация не проверялась. Виртуализатору на сервере не на что опереться
(элемента прокрутки нет), поэтому тело на сервере и в первом кадре клиента может
различаться — это кандидат на расхождение гидратации.

### Пакет глазами потребителя

`package.json` отдаёт `exports` с `types`, `import` и `require` для `.`, `/plugins` и
`/ui` и отдельно `./style.css`. Поверх `dist` собирает приложения только
`check:tree-shaking`. Не проверяются: `require` CJS в Node, `.d.ts` в проекте с другим
`moduleResolution`, типы с `@types/react@18`, импорт `style.css`. Директивы
`'use client'` в `dist` нет: импорт грида из серверного компонента Next.js App Router
падает на первом хуке.

### Как это сделано у других

- **MUI** гоняет CI-матрицу по версиям React, тестовый рендер у неё по умолчанию в
  StrictMode, входы пакетов помечены `'use client'`.
- **AG Grid** (`ag-grid-react`) помечает входы `'use client'`.
- **publint** и **arethetypeswrong** — общепринятые проверки опубликованного пакета:
  поля `exports`, соответствие форматов и типов для ESM и CJS.

## Решение

### 1. `test:react18`

Отдельная команда прогоняет все браузерные наборы на React 18. React 18 живёт в
отдельном проекте `tools/react18` со своими `node_modules`, конфиг
`vitest.react18.config.ts` подменяет `react` и `react-dom` в разрешении модулей. Наборы, которые на React 18 не имеют смысла
или зависят от поведения 19, вынесены в список исключений с причиной — как
`engines.ts` у `test:engines` (ADR 0084). Шаг — «перед публикацией», а не барьер.

Оба браузерных проекта React 18 включают сборку мусора перед каждым файлом,
как основной Chromium-прогон. Иначе отложенная очистка iframe накапливает память
до разрыва соединения браузера с Vitest.

Найденное под React 18 чинится в коде так, чтобы работало в обеих версиях. Первое —
`Tooltip`: ref триггера читается из `props.ref` (19) или `element.ref` (18).

### 2. StrictMode по умолчанию

`vitest.setup.ts` включает StrictMode для всех браузерных тестов
(`configure({ reactStrictMode: true })` у `vitest-browser-react`). Перф-тесты идут в
своём конфиге и StrictMode не включают: он удваивает работу рендера. Страж-тест
проверяет, что эффекты в тесте запускаются дважды, — выключить StrictMode тихо нельзя.

### 3. SSR и гидратация

- Модульный тест рендерит основные истории `renderToString` в node без DOM и требует
  ни одного `console.error`/`warn`.
- Модульный тест импортирует все входы в среде, где `window`, `document` и `navigator`
  пусты: проверка `typeof` их видит, а незащищённое обращение уронило бы импорт.
- Визуальный тест вставляет серверный HTML в страницу и гидрирует его `hydrateRoot`:
  ни одной ошибки гидратации (`onRecoverableError`, `console.error`), после гидратации
  грид отвечает на нажатие сортировки и рисует строки при прокрутке.

Если тело на сервере расходится с первым кадром клиента, сервер рендерит то же окно
строк, что и первый кадр клиента без измерений.

### 4. `check:package`

Скрипт собирает архив `npm pack` и проверяет его:

- **publint** и **arethetypeswrong** — без ошибок;
- **фикстуры** во временной папке ставят архив и зависимости из npm:
  - Vite-приложение на ESM со строгим TS (`moduleResolution: bundler`): типы и сборка
    проходят, `style.css` импортируется;
  - TS с `moduleResolution: node16` — ESM; CJS — с `nodenext`: TanStack Table v9
    поставляется только в ESM, а `require(esm)` в типах понимает лишь `nodenext`;
  - Node: `require` CJS и `import` ESM всех входов;
  - типы проходят с `@types/react@18`, грид и `Switch` рендерятся на сервере под React 18
    из ESM- и CJS-входов установленного архива;
- **`'use client'`** стоит первой строкой во входах `dist` (`index`, `plugins`, `ui`, ESM
  и CJS). Rollup директивы модулей при сборке выбрасывает, поэтому сборка ставит её
  баннером входа.

Шаг — «перед публикацией»: фикстурам нужна установка из npm.

## Границы

- Фикстура на Next.js — нет: главную ловушку (`'use client'`) закрывает §4.
- Утечки памяти, визуальная регрессия по скриншотам — следующая волна.
- RTL — отдельная прожарка как фичи.
- Живые скринридеры — ручной гайд `docs/testing/screen-readers.md`.
- React 17 и ниже — не поддерживаются (peer `^18 || ^19`).

## Отвергнутые альтернативы

- **Дымовой поднабор на React 18 в каждом `npm test`.** Дешевле, но ловит не всё; полный
  прогон перед публикацией надёжнее и не замедляет ежедневный барьер.
- **Убрать React 18 из peer.** Проверять нечего, но многие приложения ещё на 18.
- **Отдельный проект StrictMode.** Удваивает время тестов; StrictMode в основном прогоне
  ничего не стоит потребителю и ловит то же.
- **Только `renderToString`.** Не ловит расхождения гидратации — главную беду SSR у
  виртуализированных таблиц.

## Последствия

- **+** Обещание `react ^18 || ^19` проверено; найденный дефект `Tooltip` исправлен.
- **+** Побочные эффекты, не переживающие двойного запуска, ловятся в каждом прогоне.
- **+** Грид рендерится на сервере и гидрируется; пакет проверен так, как его
  поставит потребитель; импорт из серверного компонента Next.js работает.
- **−** Новые devDeps: `publint`, `@arethetypeswrong/cli`; React 18 — в отдельном
  проекте `tools/react18`.
- **−** Два новых шага перед публикацией: `test:react18` и `check:package`; второму нужна
  сеть.
- **−** Входы `dist` получают директиву `'use client'` (без неё в RSC импорт падал).

## Внедрение

Находки — дефекты, которых барьер не видел:

- **`Tooltip` под React 18 терял `ref` триггера** — читал его только из `props`. Теперь из
  `props` в React 19 и из `element.ref` в 18 (`core/reactVersion`).
- **`inert` под React 18 не попадал в DOM**: React 18 атрибута не знает и булево значение
  выбрасывает с предупреждением — шапка-скелет, скелет тела и призрак перетаскивания не
  были инертны. `core/inertProp` отдаёт булево в 19 и пустую строку в 18.
- **`onTransitionCancel` под React 18 игнорировался**. Бабл кнопки теперь слушает
  `transitionend` и `transitioncancel` в DOM во время ухода ([ADR 0129](0129-button-active-state.md), AV12).
- **`useLayoutEffect` при серверном рендере на React 18** — предупреждение на каждый хук
  (в 19 его нет). Хуки грида идут через `core/useIsomorphicLayoutEffect`: без DOM —
  `useEffect`; `react-hooks/exhaustive-deps` проверяет его как `useLayoutEffect`. Тем же
  хуком — и обвязка историй, которую EV4 рендерит на сервере: среда каталога, панель
  гайда, консоль и её запись аргументов (EV4 падал в `test:react18`, найдено
  2026-10-22).
- **Половина изменения на кадр под React 18** (найдено 2026-10-22, двенадцать тестов
  `test:react18`). React 18 коммитит обновления атомов TanStack (`useSyncExternalStore`)
  в синхронной полосе, а `setState` вне событий React — в полосе по умолчанию, отдельной
  задачей; React 19 сводит их в один коммит. Грид видел полизменения:
  - срез с сужением (ADR 0039) ядро хранило в `useState` — теперь в атоме TanStack
    (`core/effectiveState`): LT7, LT8, SA12, истории RowDraggingCollapsedGroups и
    RowDraggingLazyTree;
  - запись атома и состояния приложения из таймера или промиса — раскрытие паузой
    (ADR 0109), итог `loadChildren` и `onExpandRow`, итог промиса `onRowDragEnd` —
    идёт через `util/oneCommit` (`flushSync` в React 18): NX1, NX3, NX7, LT3, AL10;
  - старт перетаскивания dnd-kit коммитится позже атома `rowDragging`: слот-скелет
    строки следует `isDragging` dnd-kit, как `data-row-draggable` (RM27);
  - `setOver` dnd-kit — в полосе по умолчанию, место броска из `onDragOver` в атоме —
    раньше: в React 18 смена места применяется в layout-эффекте коммита `over` со
    сдвигом последнего движения (PV5). Отпустили до этого коммита — бросок по видимому
    превью, как у dnd-kit: сценарий истории RowDraggingLazyTree отпускает, когда слот
    встал под группой.
- **`reorderRows` менял данные приложения на месте** (`subRows` и `parentId`).
  Обновитель `onRowOrderChange` в StrictMode вызывается дважды — второй вызов отменял
  перенос подстроки (DN2). Теперь копирует затронутые группы и строки (EV10).
- **`<DataGrid table={table} />` не проходил проверку типов у потребителя**: таблица с
  конкретными плагинами и данными не подходит к `Table<any, any>` — в репозитории это
  скрывали приведения `as never`. Проп `table` теперь — форма `DataGridTable` (таблица с
  `getPluginDiagnostics`), экспортирована из пакета; число или таблица без Tessera —
  по-прежнему ошибка.
- **Декларации не разрешались в `node16`**: импорты `.d.ts` без расширений, для
  `require` — типы ESM. Сборка дописывает `.js` или `/index.js` и пишет рядом дерево
  `.d.cts` (`scripts/declarations.ts`), `exports` разводит `types` по `import` и
  `require`. `attw --profile node16` без проблем; `node10` (устаревшее разрешение без
  `exports`) не проверяется.

Уточнения решения:

- **React 18 — отдельный проект `tools/react18`, а не алиасы в корне**: пиры
  `react-dom@18` разрешаются от корня, где React 19, и npm их не ставит. Серверный
  рендер на React 18 в node — проект `react18-unit`: зависимости проходят через Vite, а
  нативные `require` CJS-пакетов (`use-sync-external-store`) направляет к React 18
  `vitest.react18.setup.ts` — иначе два экземпляра React.
- **StrictMode в тестах**: из 1075 тестов под ним упали три. SF12 и SF13 считали вызовы
  `loadOptions` поштучно, а StrictMode запускает эффект дважды и первый запрос отменяет
  — тесты считают живые запросы; DN2 — дефект `reorderRows` выше.
- **EV5 в браузере** имитирует сервер `renderToString` при живом `document`, поэтому
  предупреждение React 18 про `useLayoutEffect` там неизбежно и отфильтровано; без DOM
  его ловит EV4. Гидратация расхождений не дала — правка тела на сервере не нужна.
- **`check:package`**: `tsc` фикстуры падает только на ошибках её кода и деклараций
  пакета — у dnd-kit декларации ссылаются на глобальный `JSX`, которого нет в
  `@types/react@19`.
- **TQ1** — мутациями: без чтения `element.ref` падает EV2 (React 18); без StrictMode —
  EV3; со старым `useLayoutEffect` — EV4 (React 18); с булевым `inert` на 18 — EV5; с
  обращением к `window` при импорте — EV4 и EV6; без фильтра ошибок `tsc` — EV7; без
  `/index.js` для папок — EV8; с баннером на всех модулях — EV9; без алиаса React 18 —
  EV1; со старой `reorderRows` — EV10 и DN2. До правок `check:package` падал на типах
  `DataGrid` и `attw` — на 35 ошибках разрешения.
