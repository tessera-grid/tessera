# 0228 — Движение строк серверной модели при смене выборки с пересечением окон

- **Статус:** Принято (прожарка 2026-11-14, решение автора: строки едут, когда прежнее и новое
  окно пересекаются; сортировка остаётся мгновенной)
- **Дата:** 2026-11-14
- **Слой:** грид — `grid/rowMotion/RowMotion.tsx` и `grid/Body.tsx`: движение строк — механика
  рендер-слоя (ADR 0107), ей нужен только номер поколения источника строк, который ядро уже
  отдаёт (`RowSource.epoch`); плагин `serverRowModel` не меняется
  ([ADR 0163](0163-layer-boundaries-and-guards.md)).
- **Изменяет:**
  - [ADR 0107](0107-row-motion.md) — снимает часть осознанного ограничения «в SSRM строки не едут
    при смене сортировки, фильтра и поиска»: остаётся «не едут, когда окна не пересекаются».
  - [ADR 0138](0138-server-side-row-model.md) — §6: приход новой выборки двигает уцелевшие строки
    окна.
- **Связано:**
  - [ADR 0157](0157-ssrm-row-transactions.md) — движение строк при транзакциях (RT9).
  - [ADR 0116](0116-async-server-actions.md) — серверное действие, откат при отказе.
  - [ADR 0158](0158-ssrm-pagination.md) — страницы серверной модели.

## Контекст

Смена сортировки, фильтра или поиска в серверной модели строк запускает новое поколение кэша:
тело сразу прокручивается к началу, прежние строки стоят под свечением, по ответу окно
подменяется за один коммит (SD20). Движения нет — и не потому, что его запрещает правило «замена
целиком» (ADR 0107, §2): `RowMotion` снимает позиции строк, только когда сменился массив строк
или версия раскладки источника, а при смене поколения не меняется ни то, ни другое
(`RowMotion.tsx`, `getSnapshotBeforeUpdate`). До плана движения дело не доходит.

Прожарка 2026-11-06 записала ограничение так: «прежние и новые строки почти не пересекаются».
Для сортировки это верно. Для фильтра и поиска, которые сужают выборку, — нет: начало нового
списка — подмножество прежнего начала в том же порядке. В клиентском режиме такие строки едут.

### Как у других

- **AG Grid**: при смене сортировки в серверной модели строки заменяются строками загрузки;
  движение при серверной смене выборки не документировано.
- **MUI X**: источник данных очищает видимые строки и показывает наложение загрузки; движения
  строк нет вовсе.

## Решение

### 1. Смена поколения — повод снять позиции

`Body` передаёт `RowMotion` номер поколения, чьи строки сейчас на экране. Смена этого номера
снимает позиции строк окна, как смена массива строк или версии раскладки.

`rowSource.epoch` растёт уже при запросе новой выборки, а не при её приходе, поэтому сырой номер
не годится: пока источник обновляется (`rowSource.refreshing`), `Body` передаёт `undefined`, и
`RowMotion` держит номер поколения, чьи строки в DOM. Номер меняется в коммите, который ставит
новую выборку на экран.

### 2. План при новом поколении

Прежнего места строки в прежнем поколении нет — его хранилище уничтожено. Поэтому:

- **уцелевшая строка** (её `id` есть в прежнем окне и в новом) едет от позиции в DOM к новому
  месту — обычный FLIP;
- **вошедшая строка** проявляется на месте: «издалека» её не привезти;
- **ушедшая строка**: если её `id` есть в загруженном блоке новой выборки за окном — уезжает
  призраком к краю окна (ADR 0107, §4), иначе гаснет на месте;
- **нет ни одной уцелевшей** — движения нет, всё встаёт сразу (RM6): сортировка и фильтр,
  выдавший другие строки, остаются мгновенными.

Журнал изменений раскладки прежнего поколения к новому не применяется: при новом поколении план
строится только по окну, без `changesSince`.

### 3. Что не меняется

Тело по-прежнему сразу прокручивается к началу (SD20). Отказ серверного действия оставляет
прежнее поколение — движения нет. Скелеты незагруженных строк не едут. Уменьшенное движение и
`enableRowAnimation: false` гасят движение, как всюду.

## Границы

- **Движение при сортировке «издалека»** — не входит: прежнее место строки неизвестно.
- **Момент прокрутки к началу** — не меняется; перенос прокрутки на момент ответа отвергнут.

## Отвергнутые альтернативы

- **Держать прокрутку до ответа и прокручивать с движением:** прокрутка в момент ответа обрывает
  движение (RM12), нужна координация плагина и окна ради сомнительного выигрыша.
- **Плавное проявление всего окна:** противоречит §2 ADR 0107 — мигает всё окно.
- **Снимок прежнего окна в плагине:** позиции уже есть в DOM, плагин трогать незачем.

## Последствия

- **+** Поиск и фильтр в серверной модели выглядят как в клиентской: оставшиеся строки
  подтягиваются, отфильтрованные гаснут.
- **Публичный API:** не меняется.
- **Перф:** EM10.
- **Роадмап:** ограничение переписывается — «в SSRM строки не едут, когда прежнее и новое окно
  не пересекаются».

| EM9  | Транзакция в прежнем поколении, пришедшая во время загрузки нового, не даёт сдвигов по журналу прежнего поколения: план нового поколения строится только по окну | модульный  |

воспроизводится — требование снимается с записью причины здесь.
